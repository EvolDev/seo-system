# 14. Как работать с этим пакетом

Проблема, которую решает этот документ: у меня нет памяти между чатами.
Каждый новый чат начинается с нуля. Значит вся накопленная информация
должна жить в файлах, а не в истории переписки.

Отсюда всё остальное.

---

## 1. Разовая настройка

### 1.1. Репозиторий и рабочее место

Распаковать пакет в файловую систему WSL, завести git, поставить
Claude Code и подключить PyCharm — пошагово в `16-AGENT-SETUP.md`.

Дальше репозиторий этого же проекта станет репозиторием кода: папка
`docs/` останется на месте, рядом появятся `src/`, `tests/` и прочее.
Документы и код версионируются вместе — это принципиально, иначе они
разъедутся.

Для агента в пакете уже лежат `CLAUDE.md` (загружается в каждую сессию),
`.claude/settings.json` (права) и команды `/start-task` и `/close-task`.

### 1.2. Промпт аудитора — держать копию в актуальном виде

В `source/audit-system-prompt.md` лежит снапшот системного промпта из
Project по SEO-аудиту на 23.09.2026. Источник правды — инструкции того
Project. Поменял промпт там — обновить файл тем же коммитом, иначе две
копии разъедутся.

### 1.3. Создать отдельный Project

**Новый Project, не тот, где идёт SEO-аудит.** У них разные задачи и
разные инструкции; смешивание приведёт к тому, что при аудите площадки
я буду вспоминать про миграции, а при написании кода — про анкоры.

Название: «Разработка SEO-системы».

### 1.4. Что загружать в Project Knowledge

**Не архивом, а отдельными файлами** — архив не читается как текст.

Загружать **не всё**. Постоянное ядро, которое нужно почти в любом
разговоре:

```
PROGRESS.md            ← самый важный, обновляется чаще всех
README.md
docs/01-GLOSSARY.md
docs/02-ARCHITECTURE.md
docs/03-DATA-MODEL.md
docs/08-DECISIONS.md
docs/09-OPEN-QUESTIONS.md
docs/13-CONFIG.md
docs/15-USER-DOCS.md   ← нужен в конце каждой задачи
docs/templates/spec.md
schema.sql
```

**Не загружать в Project Knowledge:** файлы эпиков из `backlog/`,
`11-PROMPTS.md`, `12-IMPORT-MAPPING.md`, длинные исходники из
`source/`. Они нужны точечно — прикрепляются к конкретному чату.

Смысл: ядро занимает примерно треть от полного пакета. Загрузишь всё —
каждый чат будет стартовать с лишним весом, а нужные детали всё равно
утонут среди ненужных.

### 1.5. Инструкции Project

Вставить в настройки Project (можно целиком):

```
Мы вместе разрабатываем внутреннюю систему автоматизации линкбилдинга
для convertio.co. Я — единственный разработчик, пишу на Python/Django,
язык изучаю по ходу: опыт в PHP-легаси, Python на уровне джуна.
Объясняй питоновские вещи, которые неочевидны человеку из PHP.

ПЕРЕД ОТВЕТОМ всегда сверяйся с PROGRESS.md: что уже сделано, что в
работе, какие решения приняты. Не предлагай то, что уже отклонено в
08-DECISIONS.md.

В КОНЦЕ каждой рабочей сессии, когда я пишу «закрываем сессию»,
выдавай готовые блоки для вставки: обновление PROGRESS.md, новые
записи в 08-DECISIONS.md, изменения в 09-OPEN-QUESTIONS.md, а если
задача поменяла то, что видит пользователь, — страницы user-docs/ и
строку для user-docs/changelog.md. Блоки должны быть готовы к
копированию без правок.

Если для ответа не хватает документа из пакета — скажи, какой
прикрепить, вместо того чтобы догадываться.

Работаем по бэклогу: 62 задачи в 11 эпиках, файлы в docs/backlog/.
Задачи имеют ID вида E1-04. Дорожная карта — 07-ROADMAP.md.

ТЗ пиши по шаблону docs/templates/spec.md. Раздел «Влияние на
документацию» заполняй всегда: нет / обновить такие-то страницы /
создать такие-то. Правила пользовательской документации — 15-USER-DOCS.md.
```

## 2. Типы чатов и что в них прикреплять

Правило: **один чат — одна задача**, не один эпик.

| Тип чата | Когда | Что прикрепить сверх ядра |
|---|---|---|
| Разворачиваем ТЗ | перед началом задачи | файл эпика, профильные документы по ссылкам «Смотри также» |
| Архитектурный вопрос | развилка, не покрытая ADR | ничего, ядра хватает |
| Разбор проблемы | что-то не работает | ТЗ задачи, код, логи |
| Ревью | задача готова | ТЗ, diff |
| Закрытие сессии | конец работы | ничего |

**Код пишется не здесь.** Для написания кода — Claude Code прямо в
репозитории: он читает `docs/` с диска, ничего прикреплять не надо и
контекст не раздувается. Чат нужен для проектирования, ТЗ и разбора
решений.

## 3. Цикл работы над одной задачей

```
1. Новый чат: «Разворачиваем E1-04 в ТЗ»
   → прикрепить docs/backlog/E1-CORE-DATA.md и docs/12-IMPORT-MAPPING.md
   → на выходе: ТЗ по шаблону docs/templates/spec.md,
     включая раздел «Влияние на документацию»

2. Сохранить ТЗ:  docs/specs/E1-04.md  → коммит

3. Claude Code в репозитории, режим plan: /start-task E1-04
   → агент собирает контекст и выдаёт план, ты его правишь и одобряешь
   → пишем по ТЗ, коммиты по ходу

4. Проверка по критериям приёмки из файла эпика
   → все пункты отмечены? если нет — возврат к шагу 3

5. Claude Code: /close-task (чек-лист docs/templates/task-close.md)
   → пишет или обновляет страницы user-docs/ по разделу
     «Влияние на документацию»
   → строка в user-docs/changelog.md с ID задачи
   → python tools/check_user_docs.py — ноль ошибок
   → обновляет PROGRESS.md, 08-DECISIONS.md, 09-OPEN-QUESTIONS.md
   → коммит; ты читаешь diff документации, как читаешь diff кода

6. Перезалить PROGRESS.md в Project Knowledge

7. Следующая задача — /clear в Claude Code и новый чат для ТЗ
```

Шаг 5 — единственное, что нельзя пропускать. Именно он переносит знание
в файлы — и для следующей сессии (PROGRESS, решения), и для
пользователей системы (документация и журнал изменений).

Шаг 5 делает агент в репозитории, а не чат: у него перед глазами код,
тесты и ТЗ, он пишет файлы сам. Если задача закрывается в чате —
попроси те же блоки текстом и вставь руками.

## 4. Когда начинать новый чат

Начинать новый:
- сменилась задача (даже внутри одного эпика);
- сменился тип работы (проектировали — стали отлаживать);
- чат стал длинным и я начала повторяться, путать детали или забывать
  сказанное в начале;
- прошло больше пары дней.

Не начинать новый:
- посреди разворачивания одного ТЗ;
- когда обсуждение прямо продолжает предыдущее сообщение.

Признак, что пора: если в ответах появляются ошибки в деталях, которые
обсуждались выше, — контекст переполнен. Закрывай сессию и начинай
заново, приложив PROGRESS.

## 5. Как знание переходит между чатами

Три файла несут состояние, и у каждого своя роль:

**`PROGRESS.md`** — что сделано, что в работе, что дальше. Обновляется
каждую сессию. Самый важный файл в пакете после бэклога.

**`08-DECISIONS.md`** — решения, которые больше не пересматриваются.
Сюда переезжает всё, о чём договорились в чате. Без этого через месяц
я предложу то, что мы уже отклонили, а ты не вспомнишь почему.

**`09-OPEN-QUESTIONS.md`** — закрытые вопросы не вычёркиваются, а
переезжают в ADR. Новые дописываются.

Плюс `docs/specs/` — папка с готовыми ТЗ по задачам. Создаётся по ходу.

И четвёртый слой — `user-docs/`: что умеет система, для тех, кто ей
пользуется. Он растёт с каждой задачей, меняющей видимое поведение
(`15-USER-DOCS.md` §5).

## 6. Ритуал закрытия сессии

Пишешь `закрываем сессию`. Получаешь блоки:

1. Обновление для `PROGRESS.md` — готовое к вставке.
2. Новые записи для `08-DECISIONS.md`, если решения были.
3. Изменения в `09-OPEN-QUESTIONS.md`, если вопросы закрылись или
   появились.
4. Страницы `user-docs/` и строка журнала изменений — если задача
   поменяла то, что видит пользователь.

В Claude Code то же самое делает команда `/close-task` по чек-листу
`docs/templates/task-close.md`, только файлы агент пишет сам.

Вставляешь, коммитишь, перезаливаешь `PROGRESS.md` в Project Knowledge
(заменой файла).

Занимает две минуты. Пропуск одной сессии стоит получаса на следующей —
придётся пересказывать, что делали.

## 7. Что делать, если план разошёлся с реальностью

Это нормально и случится. Правила:

- **Задача оказалась больше оценки** → не растягивать, а разбить.
  Новая задача получает ID вида `E1-04a`.
- **Задача не нужна** → не удалять из бэклога, а пометить
  `отменена` с причиной. Через полгода кто-то спросит почему.
- **Появилась новая задача** → в конец эпика со следующим номером.
- **Решение пересмотрено** → старый ADR помечается `пересмотрено`,
  пишется новый со ссылкой на старый. Не править старый на месте.
- **Контрольная точка не пройдена** (например, совпадение аудита с
  человеком ниже 80%) → не двигаться дальше по плану, чинить. Это
  прямо прописано в `07-ROADMAP.md`.

---

## 8. Чего не делать

- **Не держать один чат неделями.** Он переполнится, и я начну терять
  детали, обсуждённые в начале.
- **Не грузить весь пакет в каждый чат.** Прикрепляй то, что нужно
  задаче.
- **Не полагаться на историю переписки как на память.** Всё важное —
  в файлы.
- **Не пропускать закрытие сессии.** Это единственный механизм, за счёт
  которого знание накапливается.
- **Не писать код в чате.** Для этого Claude Code в репозитории.
- **Не редактировать документы только в Project Knowledge.**
  Источник — git, Project получает копию.
