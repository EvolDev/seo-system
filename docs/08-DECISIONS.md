# 08. Журнал решений (ADR)

Каждая запись: контекст, решение, альтернативы, последствия.
Новые решения дописывать сюда, а не держать в голове или в переписке.
Через полгода именно этот файл ответит на вопрос «почему мы сделали так».

Формат статуса: `принято` / `пересмотрено` / `отменено`.

## ADR-001. Источник правды — Postgres, а не Excel
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** 568 строк, 33 колонки, два человека, параллельные версии
файла, 530 строк без статуса.

**Решение.** Единственный источник правды — база. Excel остаётся форматом
экспорта для отчётов.

**Альтернативы.** Google Sheets с скриптами — отвергнуто: логика в
таблице не тестируется и не версионируется; надстройки над Excel —
отвергнуто по той же причине.

**Последствия.** Любой модуль пишет в базу, а не в файл. Требуется
импорт и экспорт. Excel перестаёт быть рабочим инструментом.

## ADR-002. Python + Django вместо PHP + Laravel
**Дата:** 17.09.2026 · **Статус:** принято (пересмотр предыдущей рекомендации)

**Контекст.** Разработчик имеет опыт легаси-PHP 5.6/7 без фреймворков,
немного Go, Python не знает. Первоначально рекомендовался PHP как
«знакомый».

**Решение.** Python 3.12 + Django.

**Обоснование.**
- Фреймворк придётся учить в любом случае — аргумент «бери знакомое»
  обнуляется примерно на 60%, переносится только синтаксис и общие
  инстинкты.
- Вторая половина системы (E8, проверка уникальности через эмбеддинги,
  статистика по вариантам промпта) — питоновская территория.
- Официальный SDK Anthropic для Python — первого класса; PHP SDK в бете.
- Карьерная ценность: SEO-автоматизация + LLM-пайплайны — питоновская
  экосистема.
- Явный питоновский код проще ревьюить, чем магию Laravel, что важно при
  разработке с ИИ-помощником.

**Цена решения.** Плюс 2–3 недели до первого рабочего модуля.

**Альтернативы.** PHP+Laravel — было бы правильным выбором при наличии
боевого опыта Laravel. Go — слишком много ручной работы, нет админки.
FastAPI — отвергнуто: ничего не даёт из коробки, слишком много развилок
для человека, изучающего язык.

## ADR-003. ORM для объектов, сырой SQL для отчётов
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** Известная критика ORM («выстрел в ногу») справедлива в Go,
где ORM слабые и пишутся нагруженные сервисы.

**Решение.** Django ORM для жизненного цикла объектов (создать площадку,
обновить статус, записать проверку, отрисовать карточку). Сырой SQL и
представления — для отчётов, агрегаций и дашбордов.

**Обоснование.** Объём данных мизерный (тысячи строк), бюджет задержек
съедают внешние API (секунды и минуты), а админка генерируется из моделей
ORM — отказ от ORM убивает главную причину выбора Django.

**Обязательные меры против классических граблей.** Логирование SQL в
разработке, django-debug-toolbar со счётчиком запросов, явные
`select_related`/`prefetch_related`, просмотр `sqlmigrate` перед
применением миграций, индексы вручную.

## ADR-004. Своя LLM не используется
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Только внешние API.

**Обоснование.** Локальная модель слабее по качеству оценки текста,
требует GPU, стоимость которого сопоставима с годом оплаты API, вся
поддержка на одном человеке. Единственный аргумент за локальную модель —
приватность — неприменим: анализируются публичные сайты.

## ADR-005. Никакого fine-tune, «обучение» через библиотеку
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** Запрос звучал как «повышать вес при положительном вердикте».

**Решение.** Веса модели не меняются. Веса живут на уровне библиотеки
примеров, анкорных конструкций и вариантов промпта.

**Обоснование.** Параметры модели меняются только градиентным спуском на
большом датасете; одна принятая статья их не двигает. Fine-tune Claude
доступен фактически только для старой модели Claude 3 Haiku через Amazon
Bedrock в одном регионе — отдавать ей генерацию статей хуже, чем брать
топовую модель с хорошим промптом. Правила ТЗ меняются часто, и правка
строки в базе несравнимо дешевле переобучения.

**Уточнение 23.09.2026.** Claude 3 Haiku, для которой дообучение было
доступно в Bedrock, дошла до конца жизненного цикла 10.09.2026 (карточка
модели в документации AWS). Публично известного пути дообучения Claude
на эту дату нет. Решение не меняется, аргумент стал сильнее.

**Пересмотр.** Вернуться к вопросу при 100+ принятых статей с разметкой —
и только если к тому моменту появится доступный путь дообучения.

## ADR-006. Роутинг моделей по задачам через конфиг
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Слой абстракции над провайдером с первого вызова; модель для
каждой задачи задаётся конфигом, не кодом.

**Обоснование.** Дешёвая модель для классификации и извлечения фактов,
сильная — для аудита, генерации и критика. Смена модели или добавление
второго вендора не должны затрагивать код модулей.

## ADR-007. Продукт — сущность первого класса
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** В старой таблице Clideo присутствует как колонка «Пример
статьи на Clideo».

**Решение.** Таблица `products`; Convertio и Clideo равноправны.
Старая ссылка на Clideo — это обычное размещение другого продукта.

**Последствия.** Проверка живости старых ссылок выполняется тем же
чекером. Система готова к третьему продукту без переделки схемы.

**Уточнение 23.09.2026.** В первой версии было записано, что удаление
ссылки на любой продукт — стоп-фактор для остальных. Это расходилось с
промптом аудитора: удалённая ссылка на Clideo — «не формальный жёсткий
стоп-фактор, но весомый негативный сигнал». Исправлено: стоп —
только удаление ссылки на основной продукт (Convertio), Clideo — сильный
минус в гибкой зоне. В самом промпте есть противоречие между двумя
разделами, трактовка вынесена в Q12.

**Уточнение 27.09.2026.** К продукту привязаны не только размещения и
ключи, но и решение по площадке: статус, аудит, соответствие тематике.
Правила, настройки и знания бывают общими и локальными. См. ADR-030.

## ADR-008. Снапшоты вместо перезаписи
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Метрики, цены и позиции пишутся новой строкой с датой.
Перезапись запрещена.

**Обоснование.** Тренд важнее текущего значения; сейчас истории нет
вообще. Стоимость хранения ничтожна.

**Уточнение 27.09.2026 (E1-01).** Как это выглядит в админке. Новый
замер вносится кнопкой «Сохранить как новый объект»: форма открывается
с данными последнего снапшота, сохранение создаёт новую строку, прежняя
остаётся в истории. Править можно только последний снапшот — это
исправление ошибки ввода, а не новый замер. Более старые снапшоты
открываются только на чтение.

## ADR-009. Деньги в центах, итоговая цена вычисляется
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Целые числа в центах + код валюты. Итоговая цена не
хранится: плановая считается до размещения, фактическая — после.

**Обоснование.** Float для денег даёт накопительную ошибку. В текущей
таблице поле «Итог цена» местами некорректно, что подтверждает
нежизнеспособность хранимого агрегата.

**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Docker Compose, один сервер, без Kubernetes и микросервисов.

**Обоснование.** Два пользователя, сотни задач в сутки. Сложность

## ADR-011. Три раздельных слоя наблюдаемости
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Технические логи (stdout, JSON, 3 недели) ≠ доменный аудит
(таблицы в Postgres, вечно) ≠ ошибки (Sentry).

**Обоснование.** Смешение этих слоёв — главная причина, по которой
системы наблюдаемости ставят и не используют. В интерфейс выводится
только доменный слой.

---

## ADR-012. Без Prometheus, Grafana и Jaeger на старте
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Не ставим.

**Обоснование.** Prometheus решает задачу временных рядов при высоком
RPS на многих инстансах — не наш случай. Jaeger решает трассировку через
множество сервисов — у нас монолит. Полезная идея из Jaeger (сквозной
идентификатор) реализуется колонкой `run_id`.

**Пересмотр.** Если понадобятся графики — Grafana умеет ходить в Postgres
напрямую, слой метрик не нужен.

## ADR-013. Sentry берём сразу
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Единственный внешний сервис наблюдаемости с первого дня.

**Обоснование.** Разница между «что-то упало ночью» и «вот точное место
и входные данные» — часы времени на каждом инциденте.

**Уточнение (26.09.2026).** До выкладки на прод события принимает
GlitchTip — совместимый с Sentry сервис, sentry.io с машины разработчика
недоступен. См. ADR-026.

## ADR-014. Django Admin как интерфейс версии 1
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Первый интерфейс — админка. SPA не делаем.

**Обоснование.** Требование «потрогать на второй день» выполняется

## ADR-015. Критик — отдельный вызов с чистым контекстом
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Проверка статьи выполняется отдельным LLM-вызовом, который
не видит историю генерации.

**Обоснование.** Модель, только что написавшая текст, — плохой судья

## ADR-016. Детерминированные проверки делает код, не LLM
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Позиции ссылок, rel, количество ссылок, структура, объём,
индексируемость — кодом. LLM оставляем тест на извлечение и оценку
естественности.

**Обоснование.** Код не галлюцинирует, не замыливается, стоит ноль.
Отдавать LLM то, что решается парсером, — самая частая ошибка в таких
проектах.

## ADR-017. Уникальность контента — критичное требование
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** 50 статей в месяц из одного пула фактов.

**Решение.** Ротация фактов, ротация структур, проверка косинусной
близости, вариативность анкорных конструкций — всё обязательно, с первой
версии генератора, а не «допилим потом».

**Обоснование.** Это единственный риск проекта, способный навредить
основному бизнесу, а не просто потратить время.

## ADR-018. Человек остаётся в цикле
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Финальное «да/нет» по площадке и «принято» по статье —
за человеком. Автопостинг не делаем.

**Обоснование.** Одна статья с выдуманным фактом на дорогой площадке
дороже всех сэкономленных часов.

## ADR-019. Пороги и списки — отдельно от правил проверки
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Пороги аудита (зоны DR, трафика) и контентные настройки
были записаны в таблицу `rules`. Проверка схемы на живом Postgres
показала, что вставка падает: у правила обязательны критичность и тип
проверки, а у порога их нет.

**Решение.** Таблица `domain_settings` (ключ → JSONB) для порогов,
списков и настроек. `rules` — только проверки статьи с критичностью.

**Альтернативы.** Сделать `severity` необязательным — отвергнуто:
смешение двух разных сущностей в одной таблице, и валидаторам пришлось
бы отличать правило от порога по пустому полю.

## ADR-020. Предфильтр по полям выгрузки до любых API и LLM
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Пул кандидатов на 23.09 — 1494 площадки. Аудит каждой
через краулер, SERP и LLM стоит денег и времени.

**Решение.** Массовый аудит начинается с детерминированного шага по
полям Collaborator: основной язык английский, нет пометки «реклама»,
dofollow. Затем очередь сортируется по тематикам проекта и метрикам —
сортируется, а не отсекается.

**Обоснование.** Эти условия — жёсткие правила промпта аудитора, их
проверка ничего не стоит. На пуле они убирают 646 площадок из 1494 до
первого платного вызова. Тематику сайта в фильтр не ставим: промпт
говорит, что тематика статьи важнее тематики сайта.

**Уточнение 27.09.2026 (ADR-034).** Пометка «реклама» из карточки — не
стоп и не условие предфильтра. Условий два: английский основной язык и
dofollow. Число 646 посчитано с третьим условием — пересчитать в E4-05.

## ADR-021. Пользовательская документация — docs-as-code
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Нужна документация по функциям системы, которая
пополняется с каждой завершённой задачей и открывается в разделе
«Документация» интерфейса.

**Решение.** Markdown-файлы с YAML-заголовком в папке `user-docs/` того
же репозитория. Структура по Diátaxis (обучение, инструкции, справочник,
объяснения), журнал изменений по Keep a Changelog, навигация в
`mkdocs.yml`. Интерфейс рендерит те же файлы. Подробно — `15-USER-DOCS.md`.

**Обоснование.**
- Документация меняется в том же коммите, что и код: её пишет тот же
  агент, который сделал задачу, и она проходит то же ревью.
- Markdown с заголовком читают все распространённые движки: MkDocs,
  Docusaurus, VitePress и Python-библиотеки для рендера внутри Django.
  Смена движка не требует переписывать тексты.
- История правок бесплатно — это git.

**Движок.** MkDocs 1.6 + Material for MkDocs 9.7, версия MkDocs
ограничена `<2`: вышедший в 2026 году MkDocs 2.0 несовместим с Material.
Запасной путь — Zensical от авторов Material: на версии 0.0.64 собирает
наш `mkdocs.yml` без изменений (проверено 23.09.2026). Переход — когда
Zensical выйдет в 1.0.

**Альтернативы.** Вики в Notion или Confluence — отвергнуто: живёт
отдельно от кода и неизбежно отстаёт. Страницы в базе с редактором в
админке — отвергнуто: нет ревью, нет истории вместе с кодом, агенту
неудобно писать.

## ADR-022. Эмбеддинги — Voyage AI
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Проверка уникальности статей (E6-06) и поиск дублей фактов
(E5-03) требуют векторов текста. Независимое ревью пакета заметило, что
в конфиге был только ключ Anthropic, а своей модели эмбеддингов у
Anthropic нет — задача была нереализуема.

**Решение.** Voyage AI через API, модель `voyage-4-lite`. Для других
языков — `voyage-4`, он мультиязычный. Вызовы учитываются в `api_usage`.

**Обоснование.** Документация Anthropic по эмбеддингам прямо называет
Voyage AI. Поток — десятки статей в месяц, расход копеечный.

**Альтернативы.** Локальная модель (sentence-transformers или
открытая `voyage-4-nano`) — бесплатно, но тянет в образ PyTorch и
гигабайты зависимостей на VPS с 4 ГБ памяти. Имеет смысл, если внешний
провайдер станет проблемой; интерфейс эмбеддингов делается общим, чтобы
замена была правкой конфига.

## ADR-023. Пакеты — uv, проверки — в контейнере
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** `02-ARCHITECTURE.md` оставлял выбор «uv или poetry, на
вкус». На машине разработчика системный Python 3.10, проекту нужен 3.12.

**Решение.** Менеджер пакетов — uv, lock-файл `uv.lock`, версия Python —
`.python-version` и `requires-python = ">=3.12,<3.13"`. Тесты, линтер и
типы запускаются в контейнере `app` через `make test` и `make check`.
В контейнере окружение пакетов лежит в `/opt/venv`; `.venv` на хосте
нужен только PyCharm для подсказок.

**Обоснование.**
- uv сам ставит нужную версию Python — не надо собирать 3.12 рядом с
  системным. Один инструмент вместо pyenv + poetry, быстрый lock.
- Проверки в контейнере идут в том же окружении и с теми же переменными
  из `.env`, что и приложение: тест не пройдёт локально и не упадёт на
  сервере из-за разницы версий.

**Альтернативы.** Poetry — работает, но Python ставить отдельно и
медленнее разрешает зависимости. Проверки на хосте через `uv run` —
быстрее на запуск, но настройки Django требуют переменных окружения,
и пришлось бы дублировать их вне `.env`.

## ADR-024. Приложения в `apps/`, настройки по `DJANGO_ENV`
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** E0-02 требует деления приложений по доменам и разделения
настроек local/prod. `02-ARCHITECTURE.md` при этом говорит, что окружения
отличаются только переменными окружения.

**Решение.**
- Шесть доменных приложений лежат в пакете `apps/`: `apps.sites`,
  `apps.placements`, `apps.keywords`, `apps.content`,
  `apps.observability`, `apps.integrations`. Метка приложения (label) —
  последняя часть имени: `sites`, `placements` и т.д.
- Настройки — пакет `config/settings/`: `base.py` — общее, `local.py` и
  `prod.py` импортируют всё из base и дописывают своё. Модуль выбирает
  `DJANGO_ENV` (`local` | `prod`) через `config.env.settings_module()` в
  `manage.py`, `wsgi.py`, `asgi.py`. Значения по умолчанию нет.
- `prod.py` — минимум, который нельзя забыть: `DEBUG = False` независимо
  от `DJANGO_DEBUG`, secure-куки сессии и CSRF. HTTPS, HSTS, статика —
  E10-01, когда будет понятно устройство VPS.
- mypy и pytest работают с `config.settings.local`.

**Обоснование.**
- `apps/` держит корень чистым: там уже `config`, `docs`, `user-docs`,
  `source`, `tools`, `tests`.
- Выбор модуля переменной окружения сохраняет правило из архитектуры:
  между машинами отличается только `.env`, развилок по окружению в коде
  настроек нет.
- Без значения по умолчанию прод не может тихо стартовать с локальными
  настройками.

**Альтернативы.** Приложения в корне — короче импорты, но корень
смешивает код и документацию. Один `settings.py` с `if` по `DJANGO_ENV` —
меньше файлов, но условия расползаются по всему модулю. Отдельный
модуль настроек для тестов — пока не нужен: отличий от local нет.

**Последствия.** Метка `sites` совпадает с меткой `django.contrib.sites`.
Мы его не подключаем; если понадобится пакет, который его требует
(например, allauth), нашему приложению придётся задать другую метку до
появления миграций, после — это болезненная переделка.

## ADR-025. Логи, `run_id` и Sentry — в `config/`, stdlib `logging`
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** E0-03 вводит технические логи, `run_id` и Sentry до того,
как появились очередь (E2-01) и первые цепочки. Код нужен всем
приложениям сразу.

**Решение.**
- Код лежит в `config/`, рядом с `env.py`: `run_id.py`, `logs.py`,
  `sentry.py`. Это инфраструктура, а не домен: если положить её в
  `apps/observability`, каждое приложение импортировало бы другой
  доменный модуль. `apps/observability` — таблицы блока 6 модели данных
  и команда `observability_check`.
- Логи — stdlib `logging`, JSON — `python-json-logger`. Формат выбирает
  модуль настроек: `base.py` — JSON, `local.py` — читаемая строка.
  Фильтры `run_id` и маскировки висят на обработчике, чтобы через них
  проходили записи всех логгеров.
- Маскировка секретов — по значению (переменные окружения с секретными
  именами, от 8 символов) и по имени ключа в словарях (`api_key`,
  `password`, `token`…). Та же функция обрабатывает события Sentry в
  `before_send`.
- `run_id` внутри процесса — `ContextVar`, привязывается
  `with bind_run_id(run_id):`. Между процессами передаётся явно.
  **Для E2-01:** базовый класс задачи Celery принимает `run_id`
  аргументом (строкой — аргументы идут через JSON) и выполняет задачу
  внутри `bind_run_id`; задача, запускающая следующую, передаёт
  `current_run_id()` дальше.
- Sentry: `environment = DJANGO_ENV`, без PII и без трейсинга
  производительности, тег `run_id` на каждом событии. Пустой
  `SENTRY_DSN` — выключен. Тесты выключают Sentry принудительно
  (`init(dsn="")`: при `None` SDK берёт `SENTRY_DSN` из окружения сам).

**Альтернативы.** structlog — удобнее контекст и цепочки процессоров,
но второй способ логировать рядом с `logging`, который всё равно нужен
Django и библиотекам; для наших объёмов избыточен. Свой JSON-форматтер
без зависимости — короче, но разбор `extra` и исключений пришлось бы
писать и сопровождать самим. JSON и локально — единообразно, но логи
читаются глазами хуже; JSON-формат покрыт тестами.

**Последствия.** Секрет короче 8 символов, попавший в текст сообщения,
не маскируется по значению — только по имени ключа. Локальный пароль
базы короткий, поэтому это осознанный компромисс; прод-секреты длинные.

## ADR-026. GlitchTip до прода, sentry.io — в проде
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** При проверке E0-03 sentry.io не открылся с машины
разработчика ни напрямую (соединение рвётся на TLS-рукопожатии), ни
через VPN-сервер (выход NEW-VPS). Открывается только через встроенный
VPN Firefox, через который WSL и Docker не ходят. Проверить доставку
ошибок локально нельзя.

**Решение.**
- До выкладки на прод ошибки принимает облачный GlitchTip
  (app.glitchtip.com, бесплатный тариф). Он принимает события от того же
  `sentry-sdk`: код не меняется, переменная остаётся `SENTRY_DSN`.
- При выкладке на прод (E10-02) — sentry.io: на прод-сервере задаётся
  DSN проекта Sentry и выполняется `manage.py observability_check
  --raise`. Если sentry.io с сервера недоступен, остаёмся на GlitchTip
  (Q15).

**Обоснование.** Смена сервиса — замена DSN в `.env`, в обе стороны.
Проверка на реальной отправке сейчас ценнее, чем удобство Sentry,
которое понадобится только в проде.

**Альтернативы.** Отложить проверку доставки до деплоя — до фазы 2
ошибки не отслеживались бы нигде. Sentry на своём сервере — Kafka,
ClickHouse, от 16 ГБ памяти, на VPS не влезает. Bugsink — лёгкий, но
рассчитан на свой сервер. Hawk.so — свой SDK, переписывать интеграцию.
Ошибки логгером сразу в Telegram — без группировки, одна ошибка в цикле
даёт сотню сообщений.

**Последствия.** История ошибок из GlitchTip в Sentry не переносится —
не нужна: ошибки важны, пока их чинят. Правила алертов и участников
проекта при переходе заводим заново. Лимит бесплатного тарифа — баг в
цикле может его исчерпать, тогда новые события до конца месяца не
принимаются; на работу приложения это не влияет.

## ADR-027. convertio-ai-editor — отдельная система, читает наш срез
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** Параллельно с seo-system разрабатывается convertio-ai-editor —
редактор статей со своей базой, интерфейсом и авторизацией (отдельный
репозиторий). Ему для выбора темы и задания на статью полезны данные
площадок, которые собирает seo-system. Нужно было решить, как системы
связаны и не станет ли одна зависеть от другой.

**Решение.**
- Системы независимые. Общей базы и API seo-system → ai-editor нет.
  E6 и E7 проектируются без стыковки с ai-editor.
- ai-editor может читать из нашей базы данные площадок, **только на
  чтение**: отдельная роль Postgres с правом `SELECT` на один объект —
  view `ai_editor_sites` (`03-DATA-MODEL.md`, «Срез для
  convertio-ai-editor»). К рабочим таблицам роль доступа не имеет.
- Поля view — контракт с ai-editor. Наши миграции переписывают тело
  view, а имена и смысл полей не меняются. Меняются — только по
  согласованию, с записью в этот журнал.
- Зависимость необязательная: базы нет или площадки в ней нет —
  ai-editor заполняет задание вручную. Для seo-system отказ или
  отсутствие ai-editor ничего не меняет.
- Связь в обратную сторону — максимум кнопка в seo-system, которая
  открывает ai-editor с заранее заполненным заданием (площадка,
  требования, анкоры с URL, идея) через ссылку с параметрами.
  Необязательная надстройка, проектируется позже.
- Реализация — E10-07, способ доступа к базе — Q16.

**Обоснование.** View — стабильный срез поверх `v_site_latest`, откуда
и так берутся все производные признаки. Схема seo-system свободно
меняется, пока тело view поддерживается. Роль только на чтение
исключает запись в базу со стороны другой системы.

**Альтернативы.** Общая база — связала бы миграции двух проектов.
API в seo-system — лишний код и сопровождение ради одного читателя.
Прямой доступ к таблицам — любая наша миграция ломала бы ai-editor.
JSON-выгрузка — остаётся запасным вариантом, если системы окажутся на
разных серверах (Q16).

**Последствия.** Появляется внешний потребитель схемы: при правке
`v_site_latest`, досье (E4-02) или слотов (E3-02) проверять, что
`ai_editor_sites` отдаёт те же поля. Задача E10-07 добавляет тест на
состав полей.

**Уточнение 27.09.2026.** После ADR-030 статус площадки и «пишем мы»
зависят от продукта. View строится поверх `v_product_site_latest` по
продукту Convertio; имена и смысл полей контракта не меняются.

## ADR-028. pre-commit и проверка документации в контейнере
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** E0-04 требует, чтобы коммит с битой пользовательской
документацией не проходил. Проверщик `tools/check_user_docs.py` и сборка
`mkdocs build --strict` раньше запускались только на хосте, с
зависимостями из отдельного `requirements-docs.txt`; в контейнере не было
ни MkDocs, ни PyYAML. Проверки по ADR-023 идут в контейнере.

**Решение.**
- Хуки git — фреймворк pre-commit, конфиг `.pre-commit-config.yaml`.
  Сам pre-commit ставится в хостовый `.venv` (группа `dev`):
  `uv sync && uv run pre-commit install`.
- Хук `user-docs` запускает `make docs-check`: в контейнере `app` без
  базы и Redis (`--no-deps`) — проверщик, затем `mkdocs build --strict`
  во временную папку контейнера. Срабатывает, только если в коммите есть
  `user-docs/`, `mkdocs.yml`, `docs/06-BACKLOG.md`, `docs/15-USER-DOCS.md`,
  сам проверщик или файлы зависимостей.
- Зависимости документации — группа `docs` в `pyproject.toml`,
  `requirements-docs.txt` удалён. Группа ставится по умолчанию
  (`default-groups = ["dev", "docs"]`), то есть в образ тоже.

**Обоснование.**
- pre-commit перед запуском хука прячет неиндексированные правки, поэтому
  проверяется ровно то, что уходит в коммит. Самописный скрипт в
  `.git/hooks` проверял бы рабочую копию и в git не хранится.
- Одна команда `make docs-check` для хука, ручной проверки и `/close-task`,
  то же окружение, что у остальных проверок.
- Проверщик ловит битые ссылки на страницы, но не якоря; якоря ловит
  только `mkdocs build --strict`, поэтому в хуке нужны обе проверки.
- MkDocs в образе всё равно нужен: в E9-07 сайт собирается при сборке
  образа.

**Альтернативы.** Хук на хосте через `uv run` без Docker — быстрее и
работает при остановленном Docker, но это второе окружение для проверок
вопреки ADR-023. Самописный хук с `core.hooksPath` — без зависимости,
но проверяет рабочую копию, а не коммит.

**Последствия.** При коммите изменений документации должен быть запущен
Docker; прогон — несколько секунд на старт контейнера. Хук работает
только при коммите из WSL: он запускает хостовый `.venv/bin/python`,
git для Windows (например, из PyCharm) его не выполнит. Служебные файлы
pre-commit лежат в `~/.cache/pre-commit`. Обойти хук —
`git commit --no-verify`, только осознанно. Состав зависимостей
прод-образа решается в E10-01.

## ADR-029. Django-миграции и `schema.sql`: что совпадает, что нет
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** `schema.sql` — эталон, миграции Django должны давать ту
же схему. Django 5.2 строит DDL сам: часть конструкций схемы он
повторяет только при явных настройках модели, часть не повторяет
вовсе. E1-01 — первые модели, решение нужно один раз для всех эпиков.

**Решение. Добиваемся совпадения:**
- **Имена таблиц** — из схемы, `Meta.db_table` (`sites`, а не
  `sites_site`). Текстовые колонки — `TextField` (`text`), не
  `CharField` (`varchar(n)`). Колонка, которая в схеме допускает
  `NULL`, — `null=True` и у текстовых полей: «нет данных» и пустая
  строка различаются. Правило ruff `DJ001`, запрещающее это, выключено.
- **Перечисления** — типы Postgres. Тип создаётся в миграции
  (`CREATE TYPE`), колонка объявляется этим типом через поле
  `config.db.PgEnumField`, значения в модели — `TextChoices`, те же,
  что в типе. Новое
  значение — отдельная миграция `ALTER TYPE … ADD VALUE`; данные с
  новым значением — в следующей миграции: Postgres не даёт
  использовать значение в той же транзакции, где его добавили.
- **Значения по умолчанию — в базе** (`db_default`). `INSERT` мимо
  Django получает те же значения, что и через ORM. Время —
  `config.db.PgNow`, то есть `now()`, как в схеме: штатный `Now` у
  Django на Postgres — `STATEMENT_TIMESTAMP()`, у строк одной транзакции
  время было бы разным. У статусов, флагов и валюты рядом с
  `db_default` задан и `default` с тем же значением: его подставляют
  форма админки и ORM, `db_default` форма не видит.
- **Индексы и ограничения — ровно как в схеме.** Автоиндекс Django на
  внешний ключ выключен (`db_index=False`). Индексы, `UNIQUE` и `CHECK`
  объявлены в `Meta` с именами из схемы; у безымянных ограничений схемы —
  имена, которые дал бы Postgres (`sites_domain_key`,
  `product_sites_site_id_product_id_key`, `site_audits_score_check`).
  Уникальность — через `UniqueConstraint`, не `unique=True`: для
  текстового поля Django добавил бы лишний индекс `…_like`.
- **Удаление — `on_delete=PROTECT` у всех внешних ключей.** Удалить
  строку, на которую ссылаются, Django не даст. Физически мы ничего не
  удаляем (ADR-008), поэтому попытка удаления с историей — ошибка кода,
  а не сценарий.
- **Представления** — миграцией `RunSQL` с текстом из схемы.

**Не совпадает, и это принимаем:**
- `id` — `GENERATED BY DEFAULT AS IDENTITY` вместо `bigserial`. Ведёт
  себя так же; это стандартный для Postgres способ автоинкремента.
- Внешние ключи — `DEFERRABLE INITIALLY DEFERRED` и без `ON DELETE`.
  `ON DELETE CASCADE` из схемы в базе нет, удалением управляет
  `PROTECT` в Django. Имена ограничений внешних ключей генерирует
  Django, задать их нельзя.
- `char(3)` у валюты — `varchar(3)`. Для кодов `EUR`/`USD` разницы нет.
- Порядок колонок: внешние ключи Django ставит в конец таблицы. На
  запросы с именами колонок не влияет; `SELECT *` в представлениях
  выдаёт колонки в другом порядке.

**Проверка.** `sqlmigrate` перед применением (ADR-003). Тест
`tests/test_schema_parity.py` разворачивает `schema.sql` в отдельной
схеме Postgres и сравнивает с тем, что построили миграции: колонки с
типами и значениями по умолчанию, индексы, ограничения, внешние ключи,
значения перечислений. Лишний или пропавший индекс роняет тест;
расхождения из списка выше нормализуются. Задача, добавляющая модели,
дописывает свои таблицы в список теста.

**Уточнение 28.09.2026 (E1-05).** Текст представлений тест сравнивает
после той же нормализации. Два принятых расхождения видны в нём
по-своему: `SELECT *` в подзапросе Postgres разворачивает в порядке
колонок таблицы, а у `char(n)` и `varchar(n)` печатает приведения
по-разному (`'US'::bpchar` и `(kp.country)::text = 'US'::text`). Тест
сортирует колонки подзапросов и сводит приведения к `::text` в обеих
схемах; типы колонок сверяются отдельно.

**Альтернативы.**
- Модели `managed = False` и миграции руками из `schema.sql` — модели
  и база расходятся без предупреждения, `makemigrations` перестаёт
  помогать, каждая правка делается дважды.
- Настройки Django по умолчанию — лишние индексы, дублирующие
  составные, имена с хешами; каждое такое место пришлось бы перечислять
  здесь и учитывать при каждой сверке.
- `on_delete=CASCADE`, как в схеме, — ошибка в коде тихо стёрла бы
  историю площадки.
- Подогнать `schema.sql` под вывод Django — схему читают как документ,
  хеши в именах и `DEFERRABLE` её зашумят. Расхождения короче
  перечислить здесь.

**Последствия.** В `Meta` каждой модели больше строк: индексы,
ограничения, `db_table`. Ошибка «ссылка на несуществующую строку»
всплывает при коммите транзакции, а не на строке с `INSERT` — при
отладке место падения может быть не там, где ошибка. Пока объект не
сохранён, в полях с `db_default` лежит служебная заглушка, а не
значение; после сохранения Django получает значение из базы. Стереть
мусорную площадку можно, только удалив сначала её дочерние строки —
осознанно, скриптом.

**Уточнение 01.10.2026 (E1-07, ADR-043).** Таблицы ссылаются на
пользователей Django (`auth_user`): автор заметки, сотрудник у
размещения. Таблицу пользователей создаёт Django, в схеме её нет. Чтобы
`schema.sql` применялся сам по себе, в нём заглушка `auth_user (id
integer PRIMARY KEY)` — только колонка, на которую ссылаются. Тип
`integer`: у `django.contrib.auth` своё `AutoField`, не `BigAutoField`.
Тест сверки заглушку не сравнивает: её нет в списке таблиц.

## ADR-030. Несколько продуктов: факты о площадке общие, решение — у продукта
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** ADR-007 сделал продукт сущностью, но привязал к нему
только размещения и ключи. Статус площадки, причина отказа,
соответствие тематике, вердикт аудита, пороги, правила и знания были
одни на всю систему — то есть молча считались решениями для Convertio.
Площадка, подходящая Convertio, может не подойти продукту из другой
ниши, а ценовой ориентир и порог написания у продуктов разные. Вопрос
поднялся при планировании E1-01: после первых миграций и импорта
(E1-04) исправление стоило бы переноса данных, а не правки схемы.

**Решение.** Три слоя данных (`03-DATA-MODEL.md`, принцип 8):
- **Площадка сама по себе** — факты, которые от продукта не зависят:
  `sites`, `site_metrics`, `site_prices`, `gray_scans`. Хранятся и
  покупаются у API один раз.
- **Площадка для продукта** — решение по ней: `product_sites` (статус,
  причина отказа, `content_profile`, `imported_undecided`) и
  `site_audits` с `product_id`. Строка `product_sites` есть для каждой
  пары продукт × площадка со статусом `new` по умолчанию; создаёт их
  одна функция, повторный вызов ничего не дублирует.
- **Правила, настройки и знания** — `rules`, `domain_settings`,
  `prompt_templates`, `facts`, `examples`, `anchor_patterns`,
  `golden_set` с `product_id`: пусто — общее для всех продуктов,
  заполнен — локальное. Где выбирается одно значение (правило,
  настройка, промпт задачи), локальное перекрывает общее с тем же кодом
  или ключом; выключить общее правило для продукта — локальная строка
  с `is_active = false`. Где нужен набор (факты, примеры, конструкции,
  эталонные задания), общее и локальное объединяются. Выбор — в одном
  месте кода на таблицу.

Следом за этим:
- Производные признаки делятся по тем же слоям. `v_site_latest` —
  только факты и `reference_total`. `we_write` и `expected_spend`
  считаются в `v_product_site_latest` по порогу написания продукта
  (`writing_eur` в настройке `PRICE_REFERENCE`); настройки нет —
  `expected_spend` пусто, порог не угадываем.
- `keywords.tool` и `anchor_patterns.tool` — текст, а не перечисление:
  разделы сайта у каждого продукта свои, список — локальная настройка
  `TOOL_CATEGORIES`.
- Код правила уникален вместе с продуктом: `(code, product_id)` с
  `NULLS NOT DISTINCT`. Поэтому `examples.rule_code` — без внешнего
  ключа, проверка в приложении.
- Стоп-факторы, не зависящие от продукта (nofollow, пометка о
  рекламе), при аудите под каждый продукт находятся заново: это
  проверка кодом, она бесплатна.
- Продукт заводит человек в админке. Там же, на странице продукта, он
  вводит и правит локальные настройки продукта (E1-05).
- Общего чёрного списка («не работаем ни под каким продуктом») нет.
  Понадобится — колонка в `sites`, без переделки.

**Альтернативы.**
- `product_id` в `sites`, строка площадки на каждый продукт — метрики
  и цены дублируются и покупаются у API повторно, домен перестаёт быть
  уникальным.
- Статус в `sites` плюс исключения для других продуктов — два места
  правды для одного решения.
- Строки `product_sites` только по мере работы с площадкой — каждый
  запрос «площадки продукта со статусом `new`» учитывал бы отсутствие
  строки: `LEFT JOIN` и `coalesce` в каждом потребителе.
- Отдельная база на продукт — факты о площадках и покупка метрик
  дублируются, общие правила копируются руками.
- Отложить до появления второго продукта — после импорта E1-04 это
  перенос данных вместо правки схемы.

**Последствия.** `schema.sql` 1.2: 29 таблиц, 8 представлений.
E1-01 выросла с M до L. Всё, что читает или меняет статус площадки, —
предфильтр, аудит (E4), список и карточка в админке (E9-01), воронка
`v_site_funnel`, срез для ai-editor (ADR-027) — работает под выбранным
продуктом через `product_sites` и `v_product_site_latest`. Решения из
Excel при импорте (E1-04) ложатся в `product_sites` продукта Convertio.
Ключи `domain_settings` делятся на общие и локальные (`13-CONFIG.md`).

## ADR-031. Таблицы промптов — вместе с наблюдаемостью; `run_id` по умолчанию из цепочки
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** В `schema.sql` у `llm_calls.prompt_variant_id` есть
внешний ключ на `prompt_variants`. Ни одна задача бэклога не создавала
`prompt_templates` и `prompt_variants`: E5-01 делает факты, правила и
примеры, а E4-01 уже берёт промпты из `prompt_variants`, завися только
от E1-03. Внешний ключ на таблицу, которой нет, миграция не создаст.
Вопрос всплыл при планировании E1-03.

**Решение.**
- `prompt_templates` и `prompt_variants` делает E1-03, в `apps/content`,
  строго по `schema.sql`: только модели и миграция, без админки и
  логики выбора варианта. Внешний ключ из `llm_calls` — сразу.
- `run_id` в `checks`, `llm_calls`, `task_runs`, `api_usage` по
  умолчанию берётся из текущей цепочки: `default=current_run_id`
  (ADR-025). Строка, созданная внутри `with bind_run_id(...)`, получает
  его сама, вне цепочки — пусто, явно переданное значение главнее.
  Это значение по умолчанию на стороне Python: в схеме базы его нет,
  `INSERT` мимо Django `run_id` не получит.

**Альтернативы.**
- `prompt_variant_id` без внешнего ключа до задачи, которая создаст
  таблицы вариантов, — такой задачи нет; в журнал можно было бы
  записать номер несуществующего варианта, и статистика E8 «какой
  промпт лучше» тихо испортилась бы; в тест сверки со схемой пришлось
  бы вписать исключение.
- `run_id` только явным аргументом — каждый вызывающий должен помнить
  его передать; забытый `run_id` не виден до разбора инцидента.

**Последствия.** E1-03 выросла на две таблицы (по-прежнему S).
Админка промптов и выбор варианта («локальный перекрывает общий») в
E1-03 не входят, понадобятся к E4-01 — записано в технический долг
`PROGRESS.md`. Тест сверки со схемой
сравнивает и текст представлений (`pg_get_viewdef`).

**Уточнение 27.09.2026 (E1-02).** Так же заполняется `placements.run_id`:
размещение, созданное импортом (E1-04) или задачей, получает `run_id`
цепочки само, заведённое руками в админке — пусто. После импорта по
нему видно, какие размещения создал именно этот запуск, и в логах
находятся его записи. `site_audits.run_id` — по-прежнему только явно,
технический долг к E4.

## ADR-032. Позиция ссылки в статье — как «Статистика» Word, два числа
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** Правила `LINK_POSITION_FIRST` и `LINK_POSITION_SECOND`
(первая ссылка не дальше 1000 знаков, вторая — 2000) считают позицию
ссылки «в символах с пробелами от начала статьи». Не было сказано, что
делать с переносами строк и отступами в HTML, входит ли заголовок и
что именно считать позицией. Краулер (E2-04) и проверка черновика
(E7-01) могли посчитать по-разному, а в исходнике страницы с глубокой
вложенностью отступы набегают на сотни символов — хорошая статья
провалила бы правило. Вопрос всплыл при планировании E1-02.

**Решение.** Позиция считается так, как её видит человек, вставив текст
статьи в Word и открыв «Статистику»:
- текст статьи — с самого начала документа, заголовок входит; меню,
  подвал и сайдбар не входят (что такое текст статьи на странице,
  решает одна функция для E2-04 и E7-01);
- теги HTML и разметка Markdown (`**`, `#`, `[…](…)`) не считаются;
- границы абзацев, заголовков, пунктов списка, переносы строк, маркеры
  и номера списков не считаются — Word не считает знаки абзаца;
- пробелы между словами — как их показывает браузер: несколько подряд
  в исходнике — один;
- позиция — число знаков перед первым символом анкора.

Хранятся оба числа, как в Word: `placement_links.char_offset` — знаков
с пробелами (неразрывный пробел — тоже пробел), по нему проверяются
правила; `char_offset_no_spaces` — без пробелов, для сверки с Word.
Колонка `char_offset_no_spaces` добавлена в `schema.sql` 1.3.

Пример: заголовок «How to convert video», абзац «Converting is easy.»,
абзац «Use mp4 to mp3 …» с анкором «mp4 to mp3» — 43 знака с пробелами,
37 без.

**Альтернативы.**
- Считать символы исходника без тегов буквально, с отступами и
  переносами — число зависит от вёрстки площадки, а не от текста.
- Граница абзаца — один пробел, заголовок не считается (первое
  предложение при планировании) — расходится с тем, как считает
  человек в Word.
- Хранить только число с пробелами — человеку, сверяющему с Word по
  знакам без пробелов, нечем свериться.

**Последствия.** Краулер (E2-04) и проверка статьи (E7-01) считают и
показывают оба числа по одному определению, одной функцией. Тест на
конкретном примере — в E2-04. Определение — в докстринге
`PlacementLink` и в `03-DATA-MODEL.md`.

## ADR-033. Регулярный импорт таблицы, рабочие списки площадок
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** ADR-001 делает базу единственным источником правды, а
импорт из Excel задумывался разовым. При планировании E1-04 выяснилось
(Q11): таблицу ведут и дальше, пока площадки не пойдут из API Ahrefs и
Collaborator (Q1, Q2), — импорт регулярный, поверх уже загруженного.
Одно и то же можно поправить и в таблице, и в админке, и нужно
правило, чья правка остаётся. Кроме того (Q18), работу хотят начинать
каждый месяц с нового списка площадок, не теряя истории по старым. В
таблице новые подгрузки отмечали вручную колонкой «Новая?».

**Решение.** Главнее админка. Импорт обращается с данными по-разному
в зависимости от того, откуда они:
- **Факты из внешних источников** — карточка Collaborator (адрес
  карточки, языки, тематики, особые тематики, тип сайта, сколько
  ссылок разрешено, тип ссылки, пометка «реклама») и объёмы ключей из
  Ahrefs — берутся из таблицы с перезаписью непустыми значениями:
  пустая ячейка значение в базе не стирает, чтобы битая ячейка не
  затёрла хорошие данные. Что поменялось, показывает отчёт.
- **Замеры** — метрики, цены, позиции — снапшот на дату файла (её
  передают параметром: в файле даты выгрузки нет). Повторная загрузка с
  той же датой обновляет замер этой даты, а не создаёт второй; новая
  дата — новая строка (ADR-008).
- **Решения и работа** — статус площадки по продукту и причина отказа,
  заметки, размещения и ссылки, раздел сайта, тип страницы и адрес
  ключа — импорт только дополняет: создаёт недостающее, заполняет
  пустое, продвигает вперёд. Статус площадки — только из «Новая» или по
  цепочке «Новая» → «Одобрена» → «Размещались»; статус размещения — по
  цепочке «Запланировано» → «Заявка отправлена» → «Опубликовано».
  Принятое решение, заполненное поле, откат назад — не трогаются;
  расхождение с таблицей попадает в отчёт.

Пометку «импортирована без решения» получает площадка, которая пришла
из таблицы без решения по продукту; снимается, когда решение
появляется.

**Рабочие списки.** Каждая загрузка идёт в список с именем
(«Сентябрь 2026»): таблицы `site_lists` и `site_list_items`,
`schema.sql` 1.4. Имя уже существующего списка — загрузка дополняет
его. Площадка в базе одна; в новый список она попадает со всей
историей. Площадки, которых до этой загрузки в базе не было, помечаются
в списке `first_seen` — это замена колонке «Новая?», сама колонка не
импортируется. Список общий для всех продуктов. «Уже работали» для
продукта — статус не «Новая», есть аудит или размещение этого продукта;
статья другого продукта (Clideo) сюда не входит и показывается ссылкой.
Фильтры по списку и по «уже работали / новые для нас» — E9-01.

Файл от 27.09.2026 загружается одним списком «Сентябрь 2026».

**Альтернативы.**
- Таблица главнее во всём — админка только для просмотра, правки в ней
  затираются следующим импортом. Отвергнуто пользователем.
- Побеждает последняя правка — у ячеек таблицы нет времени изменения,
  сравнивать не с чем.
- Отдельная копия площадок на каждый список — отказ в одном списке не
  виден в другом, от этого и уходим (ADR-001, Q18).
- Брать пометку «новая» из колонки «Новая?» — ручная замена спискам,
  при следующей подгрузке она бы уже не значила «новая для базы».

**Последствия.** Отменить решение импорт не может — только админка.
Отчёт импорта — канал для расхождений: пока таблицу ведут, её сверяют
с базой по нему. `schema.sql` 1.4: 31 таблица, 8 представлений. В
E9-01 — фильтр по списку и «уже работали». ADR-001 остаётся в силе:
таблица — канал ввода до подключения API, правда — в базе.

## ADR-034. Пометка «реклама» в карточке Collaborator — не стоп-фактор
**Дата:** 27.09.2026 · **Статус:** принято

**Контекст.** Промпт аудитора называет жёстким стопом пометку
«реклама» «не по нашему запросу», «без нашего согласия». При
формализации (`04-DOMAIN-RULES.md` §1.0, §1.1, ADR-020) источником
стопа сделали поле карточки Collaborator «Пометка о рекламе статья»
(`sites.marks_as_ad`), и маппинг импорта велел сразу отклонять такие
площадки. При планировании E1-04 данные это опровергли: в файле от
27.09 поле равно «Да» у 164 площадок, вручную отклонены 9, а на трёх
вышли статьи и на одну отправлена заявка.

Пользователь пояснил (27.09.2026): поле означает, что площадка по
своим условиям помечает статьи как рекламу. Это оговорено заранее,
такие площадки нормально проходят аудит. Нарушение — пометка на нашей
статье, когда её не обговаривали; такую заявку в Collaborator не
принимают.

**Решение.**
- `sites.marks_as_ad` — факт из карточки. Не стоп, не условие
  предфильтра, не минус в гибкой зоне. Импорт его только записывает.
- Пометка на нашей опубликованной статье — нарушение, если она не была
  оговорена: ни мы её не заказывали (`placements.ad_label_requested`),
  ни площадка не объявляла её в карточке (`sites.marks_as_ad`). Это
  проверка статьи `AD_LABEL` (`04-DOMAIN-RULES.md` §3.1).
- Остаётся ли стоп на уровне площадки — например, площадка уже ставила
  неоговорённую пометку на нашу статью — открытый вопрос Q19, решить
  до E4-03.

**Альтернативы.** Отклонять по полю карточки — отсекает площадки, с
которыми работают, и расходится с промптом: «без нашего согласия», а
здесь согласие есть с самого начала.

**Последствия.** Предфильтр — два условия: английский основной язык и
dofollow. Контрольные числа предфильтра (848 из 1494 в
`10-BASELINE-STATS.md` §8.3, ADR-020, E4-05) посчитаны с этим условием
и по выгрузке 23.09 — пересчитать в E4-05. Исправлены
`04-DOMAIN-RULES.md`, `03-DATA-MODEL.md`, E4-03, E4-05, маппинг импорта
и страница «Как система оценивает площадку».

## ADR-035. Настройки продукта: любую можно переопределить, локальная удаляется
**Дата:** 28.09.2026 · **Статус:** принято

**Контекст.** E1-05 делает `domain_settings` и блок «Настройки
продукта» на странице продукта. В `13-CONFIG.md` локальными отмечены
четыре ключа: ценовой ориентир, тематики, разделы сайта, белый список
доменов. Пользователь уточнил при планировании (28.09.2026): продукты
разные, и под общие пороги подходят не все — например, нишевому
продукту с маленьким трафиком нужны свои зоны. И второй вопрос: что
значит стёртое поле, если «ничего не удаляем физически».

**Решение.**
- Продукт может переопределить **любую известную настройку**. На
  странице продукта — поля для четырёх основных и таблица «Другие
  настройки продукта» для остальных; рядом с каждой строкой видно
  общее значение.
- Список ключей — в коде (`apps/content/domain_settings.py`,
  `SETTING_KEYS`, по `13-CONFIG.md` §2.2–2.3). Произвольный ключ в
  админке не ввести: настройку, которую не читает код, никто не
  заметит. Новая настройка — строка в списке вместе с кодом, который
  её читает.
- Стёртое поле или удалённая строка **удаляет локальное значение**,
  продукт снова работает по общему, а где общего нет — признак не
  считается. Это исключение из «ничего не удаляем физически» (ADR-008):
  настройка — конфигурация, а не история работы, прошлые значения не
  нужны. Общие значения не удаляются.
- Какое значение действует для продукта, решает одна функция —
  `get_setting(key, product_id)`: локальное, иначе общее, иначе пусто.
  Потребители (E2-06, E3, E4) читают через неё; SQL-представления
  повторяют то же правило у себя (`v_product_site_latest`).

**Альтернативы.**
- Локальными оставить только четыре ключа — продукт, которому не
  подходят общие зоны, пришлось бы подгонять под них.
- Стёртое поле хранить строкой с пустым значением — для белого списка
  это «авторитетных доменов нет», и общий список уже не подставится:
  локальный список полный (`13-CONFIG.md` §4). Легко получить не то,
  что ожидали.
- Запретить стирать — к общему значению не вернуться.

**Последствия.** Удаление в админке разрешено только у локальных
настроек на странице продукта. Истории изменений настроек нет: кто и
когда поменял — видно только по `updated_at` и журналу админки Django.

## ADR-036. Продукт, заведённый по ошибке, можно удалить
**Дата:** 28.09.2026 · **Статус:** принято

**Контекст.** Удаление в админке отключено везде (ADR-008). При
проверке E1-05 пользователь завёл тестовый продукт и не смог его
убрать: снять «активен» можно, но продукт остаётся в списке, а вместе
с ним — строки «продукт × площадка», которые создались сами под каждую
площадку (1978 строк).

**Решение.**
- Продукт удаляется со страницы продукта, пока с ним **не работали**:
  все его строки «продукт × площадка» нетронуты (статус «Новая», нет
  причины отказа, соответствия тематике, пометки импорта), и нет ни
  аудитов, ни размещений, ни ключей, ни шаблонов промптов.
- Вместе с продуктом удаляются его нетронутые строки «продукт ×
  площадка» и его настройки (ADR-035). Площадки не трогаются.
- С продуктом уже работали — кнопки удаления нет, его выключают
  флагом «активен». Массового удаления нет.
- Проверка — `Product.has_history()`, удаление — `Product.delete_unused()`.

**Альтернативы.**
- Удалять только из консоли разработчиком — для ошибки, которую
  человек сам заметил сразу, лишняя зависимость от разработчика.
- Разрешить удаление всегда — стёрлась бы история решений и
  размещений, ради которой ничего не удаляем (ADR-008).

**Последствия.** Новая таблица со ссылкой на продукт должна попасть в
`has_history()`, иначе продукт с такой историей удалить не даст
`PROTECT`: страница упадёт ошибкой вместо понятного отказа.

## ADR-037. Тема админки django-unfold, список площадок поверх представления
**Дата:** 28.09.2026 · **Статус:** пересмотрено — тема заменена на Admin
Interface (ADR-038); список поверх представления, что открыто по умолчанию и
пусто вместо 0 — в силе

**Контекст.** E9-01 делает из админки рабочий экран вместо таблицы на
33 колонки: около двух тысяч площадок, фильтры по диапазонам DR и
трафика. Штатная админка Django не умеет фильтровать по диапазону, и
на такой ширине её трудно читать. 26.09.2026 решено взять тему
django-unfold и её фильтры, но сначала проверить совместимость с mypy
strict.

**Решение.**
- **Тема — django-unfold** (0.108, Django 5.2). Подключена для всей
  админки через базовые классы `config/admin.py` (`NoDeleteAdmin`,
  `SnapshotAdmin`) и инлайны unfold. Фильтры — из
  `unfold.contrib.filters`: диапазоны чисел, выпадающие списки,
  переключатели. Свои фильтры по диапазону не пишем.
- **mypy.** У unfold нет маркера `py.typed`, но код аннотирован.
  Override `follow_untyped_imports = true` для `unfold.*` заставляет
  mypy читать эти аннотации, так что классы админки не наследуются
  от `Any`. Где аннотации unfold неточны, стоит `type: ignore` с
  причиной. Сейчас таких мест два: `save_model` (unfold объявляет
  `Form`, а на деле приходит `ModelForm`) и `all_option = None` у
  выпадающих фильтров.
- **Список «Площадки продукта»** — модель только для чтения
  `ProductSiteLatest` (`managed = False`) поверх `v_product_site_latest`.
  Все колонки приходят одной строкой представления, так что N+1 нет.
  Фильтры «рабочий список» и «уже работали» — подзапросы внутри того же
  запроса. Страница — 7–8 запросов при любом числе площадок.
  Миграция модели в базе ничего не делает (`sqlmigrate`: no-op).
- **Что открыто по умолчанию:** первый активный продукт (пункта «все
  продукты» нет — у площадки было бы две строки с разными статусами)
  и самый новый рабочий список. Все площадки — пункт «Все площадки» в
  фильтре списка.
- **Плановые расходы и «размещение + анонс» без замера цен** — пустая
  ячейка. Представление через `coalesce` даёт 0, и это читалось бы как
  «бесплатно». Правим только показ, представление не трогаем.
- **django-debug-toolbar** — только в `config/settings/local.py`,
  показывается при `DEBUG`. В тестах его нет: pytest-django выключает
  `DEBUG`.

**Альтернативы.**
- Штатная админка и свои фильтры по диапазону. Больше кода, и хуже
  выглядит на двух тысячах строк.
- Другие темы (Jazzmin, Grappelli). Не сравнивались на деле:
  пользователь хочет выбирать из четырёх и более вариантов, выбор темы
  пересматривается в E9-08.
- Список поверх `Site` с аннотациями подзапросами. Повторяет логику
  представления, а «пишем мы» и плановые расходы считаются только в
  представлении.
- Пусто вместо 0 прямо в представлении (`schema.sql` 1.5). Честнее
  для отчётов и экспорта, но это правка схемы ради случая, которого в
  данных нет: цены замерены у всех 1978 площадок. Вернуться к этому,
  если такие площадки появятся, например при загрузке из API.

**Последствия.** Новые классы админки наследуются от `NoDeleteAdmin`
или `SnapshotAdmin` и тему получают сами. Инлайны — от классов
`unfold.admin`. Перевода unfold на русский нет: кнопки фильтров
(**Filters**, **Apply Filters**) — по-английски.

## ADR-038. Тема Admin Interface, расцветки на выбор, меню по работе человека
**Дата:** 28.09.2026 · **Статус:** принято

**Контекст.** После E9-01 (ADR-037, unfold) админкой было неудобно
пользоваться: почти одинаковые названия в меню («Площадки», «…в списке»,
«…продукта», «…продуктов»), моргание при переходах, переключатель темы не
находился. E9-08 — сравнить темы на одинаковых экранах и выбрать. На
временном стенде сравнивались шесть тем (unfold, Jazzmin, Admin Interface,
SimpleUI, Daisy, Grappelli), у трёх — расцветки на выбор, демо метрик на
живых данных. Пользователь выбрал Admin Interface: «легко, всё на виду,
ничего лишнего»; у unfold «цвета мимо» и «чего-то не хватает». Ориентир по
виду — интерфейс Ahrefs (его собственная разработка на React/OCaml, готовым
шаблоном не поставить). Моргание воспроизводилось только в Opera, в Edge тех
же страниц — нет.

**Решение.**
- **Тема — django-admin-interface** (0.32, Django 5.2): тонкий слой поверх
  штатной админки. Классы админки штатные (`config/admin.py`), фильтры
  штатные, диапазоны DR и трафика — django-admin-rangefilter (поля «С» и
  «До»). unfold удалён.
- **Четыре расцветки: «Apple — светлая», «Google — тёмная», «Изумрудная»,
  «Ahrefs — тёмная».** Наш слой `config/static/seo/admin-palettes.css`:
  расцветка — набор переменных темы (`--admin-interface-*`) и штатной
  админки (`--body-bg` и др.). Включённую выбирает атрибут `data-palette`
  у `<html>`; его ставит скрипт в `<head>` шаблона
  `config/templates/admin/base_site.html` до первой отрисовки. Тёмного
  режима у темы нет — для тёмных расцветок в слое заплатки там, где она
  зашила светлый цвет. Цвета «Ahrefs» сняты со скриншотов его интерфейса.
- **Переключатель «Оформление» в шапке.** Выбор — в хранилище браузера, у
  каждого свой; без выбора — по настройке системы: светлая → «Apple»,
  тёмная → «Google». Штатный переключатель светлой/тёмной темы Django
  спрятан. Активная тема Admin Interface в базе одна (запись «Django»), её
  цвета слой перекрывает; раздел «Темы» не в меню.
- **Переходы без моргания** — View Transitions
  (`@view-transition { navigation: auto; }`): браузер плавно сменяет
  страницу. JS и SPA не нужны (ADR-014). С E9-09 переходы внутри админки
  идут подгрузкой (ADR-046) с той же плавной сменой внутри страницы;
  правило для переходов между страницами осталось для обычных переходов
  (вход, ошибка, новая вкладка).
- **Меню по работе человека** — свой сайт админки `config/admin_site.py`
  (`SeoAdminConfig` вместо `django.contrib.admin` в INSTALLED_APPS). Группы:
  «Работа» (Площадки, Размещения, Ключи), «Справочники» (Каталог площадок,
  Рабочие списки, Продукты), «Настройки», «Служебное» (решения по площадкам,
  снапшоты, позиции ключей; свёрнуто по умолчанию). Таблица, которой нет в
  `MENU`, попадает в «Служебное». Не в меню: строки рабочих списков
  (открываются числом площадок у списка) и темы. Главная — карточки группы
  «Работа» с числами, ниже остальные группы.
- **Названия.** Модели переименованы (миграция `sites.0005`, без SQL):
  «Площадки» — рабочий экран, «Каталог площадок», «Решения по площадкам»,
  «Рабочие списки», «Строки рабочих списков». Заголовок списка — название во
  множественном числе, записи — название модели (вместо «Выберите
  площадка…», «Изменить площадка»). Хлебные крошки без уровня приложения
  Django, заголовки фильтров без «По …». Короткие text-поля — однострочные
  (`LONG_TEXT_FIELDS` — где пишут абзац).
- Прочее: язык интерфейса только русский (`LANGUAGES`), ссылки «Открыть
  сайт» нет, панель debug-toolbar свёрнута, `X_FRAME_OPTIONS = "SAMEORIGIN"`
  (окно связанного объекта тема открывает во фрейме).

**Цвета графиков — к E9-03.** На стенде подобраны и проверены валидатором
навыка dataviz (различимость соседних цветов при дальтонизме, контраст с
фоном). Правило: у оттенка на странице один смысл. Статусы площадок —
только своими цветами и всегда со значком; две группы («пишем мы / пишет
площадка») — синий и бирюзовый; всё про размещения — фиолетовый; стадии и
позиции — порядковой шкалой одного синего оттенка. В стопке статусы идут в
проверенном порядке — соседи различимы.

| Расцветка | Две группы | Одобрена · отклонена · на аудите · размещались | Чёрный список · новая | Порядок в стопке |

«Ahrefs — тёмная» проверить тем же способом при E9-03.

**Альтернативы.**
- unfold (ADR-037). Пользователю не понравились цвета и общий вид, в Opera

  задан его собственными стилями на Tailwind — расцветку сменить можно,
  раскладку — только переписывая шаблоны; для mypy нужны обходы.
- Daisy — понравились расцветки, но часть подписей не переведена, нет
  графиков и фильтра диапазона. Две темы сразу с переключателем — каждый
  экран пришлось бы делать и проверять дважды.
- Jazzmin, SimpleUI (оболочка со вкладками, ближе к SPA), Grappelli (нет
  тёмного режима и бокового меню) — пользователь не выбрал.
- Своя расцветка у каждого через тему Admin Interface в базе — тема одна
  на всех, пришлось бы подменять её внутреннюю функцию. Слой CSS проще и
  не зависит от её устройства.

**Последствия.**
- Новые классы админки — от `NoDeleteAdmin` / `SnapshotAdmin`, инлайны —

  добавить в `MENU` (`config/admin_site.py`), иначе она окажется в
  «Служебном».
- Таблица темы `admin_interface_theme` — из миграций пакета. `schema.sql`
  её не описывает: тест сверки смотрит только наши таблицы.
- Тёмные расцветки держатся на нашем слое: после обновления Admin
  Interface посмотреть экраны в «Google — тёмной» и «Ahrefs — тёмной».
- Переопределены два шаблона пакетов (выпадающий фильтр темы, фильтр
  диапазона) — при обновлении сверить с оригиналом.
- mypy: для `admin_interface`, `colorfield`, `rangefilter` —
  `ignore_missing_imports` (аннотаций у пакетов нет, наш код их классы не
  наследует).

источника расцветки (Apple и Google — «таблетки», Emerald и Ahrefs —
8 px). Кнопки форм правки Django не тронуты — их рисует тема.

## ADR-039. Очередь: Celery и Redis, базовый класс задачи, журнал запусков
**Дата:** 29.09.2026 · **Статус:** принято

**Контекст.** E2-01 — фундамент фоновых задач: проверки индексации,
живости ссылок, серости идут в фоне. Нужно: каждый запуск в `task_runs`,
`run_id` между процессами (договорённость ADR-025), повторы с паузой и
алерт после третьей неудачи, ограничение скорости внешних API на уровне
очереди, без потерь при остановке воркера. Telegram-бота ещё нет (E9-04).

**Решение.**
- **Celery 5.6 + Redis** (тот же Redis из compose, `REDIS_URL`). Воркер и
  beat — отдельные сервисы compose из того же образа. Приложение —
  `config/celery.py`, загружается вместе с Django (`config/__init__.py`),
  настройки — `CELERY_*` в `config/settings/base.py`. Логи воркера — через
  наш `LOGGING`: Celery не перехватывает корневой логгер (получатель
  сигнала `setup_logging`) и не перенаправляет print.
- **Базовый класс `QueueTask`** — `config/queue.py`, наследует `DjangoTask`
  Celery (есть `delay_on_commit`). Задача:
  `@shared_task(base=QueueTask, name="...")`.
  - `run_id`: `apply_async` дописывает `run_id` текущей цепочки в аргументы
    задачи (`run_id=`), воркер выполняет её внутри `bind_run_id`. Без него
    (задачу поставил beat) — новый; он же записывается в аргументы запроса,
    из которых Celery строит повтор, — у повторов тот же. У
    `delay_on_commit` `run_id` берётся в момент вызова, а не фиксации.
    Сверку аргументов с функцией задачи класс делает сам, без `run_id`
    (у Celery она падала бы на нём). Цепочки canvas (`chain`, `group`)
    `run_id` не передают — следующую задачу ставят из тела предыдущей.
  - **Одна строка `task_runs` на задачу, а не на попытку.** Строка
    «Выполняется» до конца всех попыток; повтор и сообщение, вернувшееся в
    очередь после остановки воркера, продолжают её (поиск по id задачи
    Celery в `payload`, за последние двое суток). `payload`: `task_id`,
    `args`, `kwargs` (секреты по имени ключа — `***`), `attempt`, `errors`
    прежних попыток, `redelivered`. `error` — текст последней ошибки без
    трассировки. Время старта — из Python: `now()` внутри транзакции — время
    её начала.
  - **Повторы:** любое исключение — повтор; всего 3 попытки, первая и два
    повтора через 60 и 120 с, без случайного разброса. «3 попытки» бэклога
    и «упала 3 раза подряд» правил алертов — одно и то же.
  - **Алерт:** после последней попытки строка «Ошибка» и запись ERROR с
    исключением — событие в Sentry/GlitchTip с тегом `run_id`. Интеграция
    Sentry с Celery ловит то же исключение ещё раз, дубль отбрасывает её же
    дедупликация: событие одно (тест). Промежуточные неудачи — WARNING, без
    события. В Telegram упавшие задачи отправит E9-04 по строкам «Ошибка».
  - `Ignore` из задачи — «Успешно»: задача сама решила остановиться.
  - Тело задачи вызывается напрямую (`self.run`): штатный `Task.__call__`
    подменяет контекст запроса пустым, и повторы молча перестают работать.
- **Ограничение скорости** — `Throttle` (`config/throttle.py`), атрибут
  задачи: группа, запусков в секунду, ключ из аргументов (домен). Перед
  запуском класс занимает ключ в Redis на интервал (`SET NX PX`). Занят —
  задача отложена на остаток: та же, с тем же id, номером попытки и
  `run_id`; попытка не тратится, строки в журнале нет. Без очереди (eager,
  прямой вызов) — ждёт на месте. Отложенные задачи одного ключа
  просыпаются вместе и спорят снова, поэтому на ключ должно ждать немного
  задач сразу (домены краулера). Общий лимит API на большие пачки —
  встроенный `rate_limit` Celery (на воркер, воркер у нас один), выбирает
  задача клиента API.
- **Без потерь:** `acks_late` — сообщение подтверждается после выполнения;
  `prefetch_multiplier=1`; `visibility_timeout` час — больше лимита
  времени задачи и самой длинной паузы перед повтором;
  `reject_on_worker_lost=False`; Redis с журналом AOF на томе `redisdata`.
  Штатная остановка воркера ждёт начатые задачи (60 с на остановку в
  compose), отложенные сразу возвращаются в очередь; задачу жёстко
  убитого воркера Redis отдаёт через час.
- **Лимит времени:** мягкий 10 минут — исключение внутри задачи, дальше
  повтор и алерт, как у любой ошибки; жёсткий 12 минут — процесс убивается.
  Задача может задать свои.
- Результаты задач Celery не хранит (`task_ignore_result`): итог — строки в
  базе.
- **Расписание** — в коде (`CELERY_BEAT_SCHEDULE`, `13-CONFIG.md` §3).
  Пульс очереди — каждый час в :00; пропущенный не копится (`expires`
  50 минут).
- **Тесты** — eager (`tests/conftest.py`): задача сразу, в процессе теста,
  повторы без пауз. Ключи — с префиксом `CELERY_`: без префикса значение
  из настроек Django не перекрыть. Брокер в тестах — в памяти: задача,
  ушедшая мимо eager, не попадёт в Redis запущенного приложения.
  `task_eager_propagates=False` везде: с True Celery в eager выбрасывает
  наружу сам сигнал повтора, и повторы не работают.
- Проверка руками и после деплоя — `manage.py queue_check`; журнал —
  экран «Запуски задач» в «Служебном», только просмотр.

**Альтернативы.**
- Строка `task_runs` на попытку — нужен статус «повтор» (правка схемы и
  перечисления), а «упало за сутки» пришлось бы считать с оглядкой на
  повторы.
- `run_id` в заголовках сообщения — задача не видела бы лишнего аргумента,
  но ADR-025 договорился об аргументе, в `payload` он виден сразу, а
  `delay_on_commit` всё равно требует брать `run_id` в момент вызова.
- django-celery-beat (расписание в базе с правкой в админке) — лишние
  таблицы; менять время проверок без программиста пока не нужно.
- django-celery-results, Flower — итог и наблюдение уже в `task_runs`,
  ADR-012.
- Встроенный `rate_limit` Celery для краулера — считает на тип задачи и
  воркер, а не на домен.
- `task_reject_on_worker_lost=True` — задача, которая роняет процесс
  (нехватка памяти), возвращалась бы в очередь по кругу.
- Алерт сразу в Telegram — часть E9-04; до неё письмо GlitchTip (ADR-026
  против ошибок логгером в Telegram — без группировки).
- Мягкая остановка Celery 5.5 (`worker_soft_shutdown_timeout`) — прерывает
  начатые задачи раньше; штатной хватает: начатые доделываются,
  отложенные возвращаются в очередь.

**Последствия.**
- Новая фоновая задача — `@shared_task(base=QueueTask, name=...)`,
  русское название — в `TASK_LABELS` (`apps/observability/admin.py`),
  строка — на странице «Фоновые задачи» пользовательской документации.
  Задача идемпотентна: прерванная остановкой воркера выполнится снова с
  начала. Аргументы — JSON: id, а не объект модели.
- Паузы и задачи — короче часа (visibility timeout), иначе Redis отдаст
  ждущее сообщение второй раз и задача выполнится дважды.
- Процесс воркера убит посреди задачи (нехватка памяти, жёсткий лимит) —
  строка остаётся «Выполняется», повторно задача не пойдёт. Для дашборда
  (E9-03) это «висит».
- Воркер и beat не перечитывают код: после правки задач —
  `make restart-queue`.
- Состояние beat локально — в `/tmp` контейнера: пересоздали контейнер —
  пропущенный запуск не догоняется. Прод (E10-01) — том для состояния
  beat, Redis с AOF и томом, число процессов воркера.
- Таймер воркера запускает повтор чуть позже заданной паузы (на живой
  проверке — до трёх секунд), но не раньше.
- Образ заводит пользователя с номерами хоста (`APP_UID`/`APP_GID`,
  аргументы сборки): без него воркер при старте считал процесс root-ом и
  писал тревожное предупреждение.

## ADR-040. SERP API: Serper, стоимость в центах с долями, пауза задачи
**Дата:** 30.09.2026 · **Статус:** принято

**Контекст.** E2-02 — клиент выдачи Google для проверки индексации (E2-03)
и gray scan (E2-06). В архитектуре провайдер — DataForSEO, альтернатива —
Serper. Запрос к выдаче стоит доли цента, а правило проекта — «деньги в
целых центах»: в `api_usage.cost_cents integer` запрос был бы нулём, и
дневной лимит не сработал бы никогда, или, с округлением вверх, одним
центом — лимит сработал бы на расходе в десятки раз меньше настоящего.
Критерий «при превышении лимита задачи встают» требует паузы задачи
до следующих суток, которой у `QueueTask` (ADR-039) не было.

**Решение.**
- **Провайдер — Serper** (`SERP_PROVIDER=serper`). DataForSEO отклонён
  заказчиком; к нему не возвращаться. У Serper нет дешёвой стандартной
  очереди — все запросы сразу, режимы live/standard из бэклога не нужны.
  Операторы `site:` не дорожают. Платим кредитами: до 10 результатов —
  один, глубже — два; сколько списано, Serper пишет в ответе (`credits`).
  Нет этого поля — ошибка: тратить деньги мимо учёта нельзя. Цена
  1000 кредитов зависит от купленного пакета ($1,00…$0,30) — настройка
  `SERPER_CENTS_PER_1000`, а не число в коде.
- **Стоимость — центы с долями:** `api_usage.cost_cents numeric(14,4)`
  (`schema.sql` 1.5). `numeric` — точная десятичная дробь, не float;
  в Python — `Decimal`. Правило «целые центы» остаётся для цен и
  размещений. `v_monthly_spend` не меняется: сумма просто становится
  `numeric`. `llm_calls.cost_cents` — так же, в E4-01 (вызов дешёвой
  модели тоже стоит доли цента).
- **Клиент** — `apps/integrations/serp/`: `search(query, *, depth=10,
  country="us") -> SerpPage`. Отступление от бэклога: вместо
  `list[SerpResult]` — страница с `results` и `total_estimate` («примерно
  N», если провайдер его даёт — для E2-06). Провайдеры — словарь
  `PROVIDERS`, интерфейс — `SerpProvider` (Protocol). Порядок: кеш →
  лимит → запрос → строка `api_usage` сразу, с `run_id` цепочки → кеш.
- **Кеш** — Django cache на Redis, база на единицу больше, чем у очереди
  (`cache.clear()` очищает базу целиком). Ключ — хеш `(запрос, глубина,
  страна)`, пробелы в запросе и регистр страны нормализуются; срок —
  `SERP_CACHE_HOURS`. Тесты — кеш в памяти процесса, пустой в каждом тесте.
- **Дневной лимит** — `SERP_DAILY_BUDGET_CENTS` против суммы `api_usage`
  провайдеров выдачи с начала суток в `TIME_ZONE`. Проверяется до
  запроса: последний запрос дня может выйти за лимит на свою цену (на
  каждый параллельный воркер). Исчерпан — `SerpBudgetExceeded` до
  полуночи и одно событие в Sentry за сутки (`cache.add` по дате), дальше
  — INFO. Ответ из кеша лимит не проверяет: он бесплатный.
- **Пауза задачи — `Postpone(until, reason)`** из `config/queue.py`.
  `QueueTask` не повторяет её (`dont_autoretry_for`), а откладывает ту же
  задачу (id, `run_id`, номер попытки) — попытка не тратится. Строка
  `task_runs` остаётся «Выполняется», в `payload.waiting` — до когда и
  почему; экран «Запуски задач» показывает это колонкой «пауза». За раз
  — не дольше `MAX_POSTPONE` (30 минут): Redis отдаёт снова сообщение, не
  подтверждённое за `visibility_timeout` (час), и задача, отложенная до
  утра, выполнилась бы по разу в час. Проснувшись раньше срока, задача
  проверяет условие снова. Без очереди (eager, тесты) пауза — ошибка.
- **Экран «Расход API»** в «Служебном» — только просмотр; суммы в
  долларах, над списком — расход на выдачу за сегодня против лимита.
  Ручная проверка — `manage.py serp_search`.

**Альтернативы.**
- Целые центы с округлением вверх — схема та же, но расход завышен
  в десять раз и больше, лимит и себестоимость статьи (E8-05) врут.
- Колонка в миллионных долях доллара (`cost_micros bigint`) — тоже
  точно, но другая единица, чем у остальных денег, и правка представления.
- Тип `money` Postgres — число знаков после запятой задаёт локаль базы,
  обычно два: $0,001 округлится до нуля.
- Пауза до полуночи одним `countdown` — повторная выдача сообщения
  Redis по `visibility_timeout`, см. выше.
- Кеш в таблице базы — видно в админке, но правка схемы ради данных,
  которые живут сутки.

**Последствия.**
- Новый платный API пишет свои строки в `api_usage` с `cost_cents`
  долями цента; его название — в `PROVIDER_LABELS`
  (`apps/observability/admin.py`).
- Задача, которой «рано продолжать», бросает `Postpone`, а не ошибку.
- Оценки «примерно N» у Serper нет (реальный ответ 30.09.2026:
  `searchParameters`, `organic`, `credits`) — Q20, блокирует E2-06.
- Serper отвечает кодом 403 и «Unauthorized.» на неверный ключ, 400 «Not
  enough credits» — на пустой баланс: задача падает, после третьей
  попытки — алерт.

## ADR-041. Единая база площадок: продавцы, цены по продавцам, из файла ничего не теряется
**Дата:** 30.09.2026 · **Статус:** принято; схема и «где дешевле» уточнены ADR-043

**Контекст.** Рутина сейчас: продавец-перекупщик присылает прайс в
своём формате (`import_examples/`: `1.xlsx`, `2.xlsx`, CSV Zain Mediax);
каждую площадку ищут руками в таблице линкбилдинга; иногда таблицу
обновляют выгрузкой каталога Collaborator (~40 000 строк); цену продавца
в долларах сравнивают с евро Collaborator и берут где дешевле;
комментарии «для истории» пишут в ячейку таблицы и хотят видеть при
каждом аудите. Размещения Clideo ведёт другой сотрудник — файлом с
историей или просто списком площадок. Пользователь хочет свою базу
площадок, как каталог Collaborator, которую пополняют файлы из разных
источников, автоматизация и аудит.

**Решение.**
- **Площадка одна на домен**, откуда бы ни пришла; источники её
  дополняют, а не создают копии.
- **Продавец — сущность**: имя (без учёта регистра), контакты, заметки.
  Collaborator — тоже продавец.
- **Цена — предложение продавца на дату** (снапшот): публикация
  (гостевой пост), вставка ссылки, написание, анонс, серая ниша; в
  валюте продавца. Цены из таблицы линкбилдинга — предложения
  Collaborator.
- **«Где дешевле» — публикация против публикации.** Гостевой пост у
  продавца — только публикация, статью пишем мы (подтвердил
  пользователь); сравнивается с «размещением» Collaborator. Анонс и
  написание показываются рядом, в сравнение не входят. Доллары для
  сравнения пересчитываются в евро по курсу ЕЦБ (раз в день, снапшотом);
  хранится исходная цена в исходной валюте, суммы валют не складываются.
- **Из файла ничего не теряется.** Каждая непустая колонка — в своё
  поле или в «прочие данные» строки (заголовок → значение), они видны на
  странице площадки. Серая цена хранится и служит сигналом «принимает
  серые тематики», как «Особые тематики» Collaborator.
- **Метрики продавца** хранятся с источником «продавец» и
  показываются, только если у площадки нет замеров Ahrefs или
  Collaborator, — с пометкой. Появился наш замер — показывается он.
- **Заметки — история**: дата, автор или файл-источник, продукт, если
  заметка про решение под него. Не удаляются. Видны в «Площадках», на
  странице площадки и в досье аудита (E4-02) — их учитывает и человек,
  и модель.
- **Загрузка файлов — экран в админке** (E1-08). Строка заголовков
  ищется сама, колонки угадываются по словарю синонимов, человек
  подтверждает или поправляет. Разметка запоминается у продавца: в
  следующий раз вопросы только о новых колонках. Сводка до записи,
  запись — задачей очереди, результат — рабочий список (ADR-033).
  Каталог Collaborator — та же загрузка со встроенной разметкой.
- **Размещения всех продуктов** (E1-09): у размещения — через какого
  продавца куплено и кто из сотрудников вёл. Сотрудники — пользователи
  системы без права входа, пока не начнут работать в ней сами; их
  размещения к тому времени уже за ними.
- **Таблица линкбилдинга** загружается как прежде (`import_workbook`),
  пока её ведут; её заметки идут в историю.

**Альтернативы.**
- Переименовывать заголовки в Excel руками — работа на каждый файл,
  опечатка молча теряет колонку.
- Общий словарь синонимов без подтверждения — у разных продавцов одно
  название значит разное («Traffic» органический или общий), ошибка
  тихая: площадка выглядит в разы сильнее.
- Разметка каждого формата в коде — продавцов десятки, форматы разовые,
  каждый новый ждал бы разработчика.
- Хранить только известные колонки — пропадает то, что пользователь
  считает важным (серая цена, DA, TF…).
- Сотрудники текстом — при их регистрации история не свяжется с
  учётной записью.

**Последствия.**
- Задачи E1-07 (модель и показ), E1-08 (загрузка файлов и каталога
  Collaborator), E1-09 (списки размещений); `schema.sql` — новая версия
  в E1-07.
- E4-02 — досье включает заметки, предложения продавцов и серую цену;
  E9-02 — блоки продавцов и заметок в карточке; E1-06 — цены по
  продавцам в выгрузке.
- «База Starmedia» грузится как прайс продавца (E1-08).
- Когда база станет местом работы, а не копией Excel, нужен бэкап
  (E10-01, E10-03): файлы можно загрузить заново, правки в админке —
  нет.

## ADR-042. Проверка индексации: два запроса, сроки в настройке, сводка оповещений
**Дата:** 01.10.2026 · **Статус:** принято

**Контекст.** E2-03 — проверка индексации статьи размещения по расписанию
и кнопкой. В бэклоге: «через `site:article_url`», сроки 3 дня / ежедневно /
раз в месяц, алерт через 30 дней в Telegram. При планировании и живой
проверке выяснилось:
- Telegram-бота нет до E9-04 (ADR-039: до него алерты — события GlitchTip),
  а бесплатный GlitchTip ограничен числом событий в месяц;
- числа сроков — пороги, а правило проекта — пороги из `domain_settings`;
- в базе 651 опубликованная статья, у 599 нет даты публикации: первый
  запуск проверит их все разом;
- `site:` в Google неточный: статья debutify.com по `site:` то
  находилась, то нет (у Serper за 40 минут ответ сменился, у человека в
  браузере — пусто), а обычный поиск по адресу её находил;
- Google дописывает к адресам страниц магазинов метку `?srsltid=…`
  (artistpush.me, Shopify): статья была в выдаче, но адрес не совпадал;
- чтобы снять статью с проверок, оставалось только сменить статус на
  «Отменено» — это исказило бы учёт оплаченных размещений.

**Решение.**
- **Два запроса.** Сначала `site:<адрес без схемы>`; нет статьи — второй
  запрос из самого адреса, как его ищет человек. Нашлась хоть одним — «в
  индексе», в `checks.result.found_by` — `site` или `url`. Второй запрос
  платный (0,1 ¢) и только для не найденных первым. Засчитывается только
  сам адрес статьи.
- **Сравнение адресов:** без схемы, `www.`, порта, `#…`, `/` в конце,
  домен без учёта регистра, путь — с учётом, `%`-кодирование раскрыто. У
  адреса статьи нет `?…` — параметры в выдаче не учитываются вовсе; есть —
  сравниваются, кроме меток отслеживания (`srsltid`, `utm_*`, `gclid`…).
- **Выдача всегда свежая** — `search(..., fresh=True)`: ответ не берётся из
  кеша, но пишется в него. Иначе ежедневная проверка в 06:00 попадала бы
  во вчерашний ответ, живой в кеше до 06:00:05.
- **Сроки — настройка `INDEXATION_SCHEDULE`** (общая, продукт может
  переопределить, ADR-035): `enabled`, `first_check_days` 3, `retry_days` 1,
  `recheck_days` 30, `alert_after_days` 30. Форма значения проверяется в
  админке. Заводится миграцией `content.0003` **выключенной**: первый
  прогон включает человек.
- **Срок — от полуночи** (`TIME_ZONE`): следующая проверка — полночь дня
  проверки плюс N дней. Сутки до секунды сдвигали бы ежедневную проверку
  в 06:00 на день. Нет даты публикации — проверяем при ближайшем запуске.
  Сменили адрес статьи — тоже.
- **Расписание:** `indexation_schedule_run` в 06:00 ставит в очередь
  проверку каждому, кому пора; `check_indexation` — одна статья, плановая
  проверка, которой уже не пора (повтор сообщения, проверили кнопкой),
  ничего не делает. Запросы к выдаче — не чаще 5 в секунду на всех
  (`Throttle("serp")`).
- **Флажок `placements.skip_checks` «Не проверять»** (`schema.sql` 1.6):
  размещение без плановых проверок — индексации и, с E2-05, живости.
  Кнопка работает и для него.
- **Оповещение:** серия неудач дольше `alert_after_days` — пометка
  `alert` в строке `checks`, одна на серию. Серия — с публикации (нет даты —
  с первой неудачи), после успеха — с первой неудачи после него.
  `indexation_alerts` в 06:30 собирает новые пометки (с прошлого удачного
  запуска) в **одно** событие GlitchTip в день; отпечаток с датой — каждый
  день новая проблема и новое письмо. В Telegram пометки отправит E9-04.
- **Кнопки без перезагрузки:** ↻ в колонке «в индексе», действие
  «Проверить индексацию» для отмеченных строк и кнопка в карточке ставят
  пачку проверок одним запросом и спрашивают её состояние одним запросом
  по строкам `task_runs`; ход и итог — всплывающим окном (зелёное — всё в
  индексе, жёлтое — не в индексе или пауза, красное — не удалось
  проверить). «В индексе» и время проверки в карточке — только чтение:
  их пишет проверка, результат человека — запись в журнале (E1-09).
- Поиск — до транзакции записи: строка `api_usage` не откатывается вместе
  с упавшей записью проверки.

**Обоснование.** Ложное «нет в индексе» дороже лишней доли цента: оно
ведёт к напрасному разбору с площадкой и ложному оповещению. Сводка раз в
день держит расход событий GlitchTip в пределах одного в сутки при любом
числе статей. Выключенное расписание не тратит кредиты до решения человека.

**Альтернативы.** Только `site:` (как в бэклоге) — ложные «нет» на живых
статьях (debutify.com). Событие на каждую статью — 50 событий в день
после первого месяца, лимит GlitchTip. Пакетные запросы Serper — те же
кредиты за каждый поиск, а ошибка одного валит пачку. Сроки в коде —
против правила о порогах. Статус «Отменено» вместо «Не проверять» —
искажает учёт.

**Последствия.** Расход на индексацию — ~0,1 ¢ на статью в индексе раз в
месяц и до 0,2 ¢ в день на каждую, которой нет. `make restart-queue`
пересоздаёт воркер и beat, а не перезапускает: `restart` оставлял
окружение с момента создания контейнера, и воркер ходил в Serper со
старым ключом (403).

## ADR-043. Рабочая цена площадки, предложения продавцов, доверенные метрики
**Дата:** 01.10.2026 · **Статус:** принято

**Контекст.** ADR-041 ввёл продавцов и «где дешевле», схему оставил плану
E1-07. Первый план показывал в «Площадках» лучшую цену у продавцов рядом
с ценой Collaborator. Пользователь посмотрел экран и уточнил работу:
- цену Collaborator на экране не видно: колонка «размещение + анонс» не
  говорит, чья это цена;
- в работе нужна одна цена, на которую ориентируемся, —
  зафиксированная, с источником. После новой загрузки видно, что
  изменилось, и человек решает: принять новую цену или оставить старую;
- написание и анонс берут не всегда — дорогие не берут. Сравнивать надо
  только цену размещения, остальное — справочно. Пример: у Collaborator
  200 € + 10 € за написание, у продавца 190 €, но статью пишем сами;
- у предложения есть услуга — публикация (guest post) или вставка
  ссылки (link insert) — и одна цена за неё;
- метрики продавцов не равны замерам Collaborator и Ahrefs: доверять
  надо выбранным источникам.

Порядок работы проверен на кликабельном прототипе
(`docs/prototypes/price-review.html`). Из лучших практик загрузки взяты:
просмотр до записи, разметка колонок с памятью у источника, очередь
изменений по выгоде, решения клавишами и отмена.

**Решение.**
- **Продавец** — `sellers`. Имя уникально без учёта регистра (индекс по
  `lower(name)`), контакты, заметки, валюта прайсов по умолчанию. Флажок
  `is_collaborator` — ровно у одного продавца: по нему загрузки находят
  Collaborator. Флажок `metrics_trusted` — см. ниже. Collaborator заводит
  миграция.
- **Предложение — строка `site_prices`.** Это площадка, продавец, услуга
  (`placement_type`, тот же тип, что у размещений), цена услуги
  (`placement_cents`), валюта и дата. Справочно: написание, анонс, серая
  цена (признак «принимает серые тематики», ADR-041), «прочие данные»
  файла (`extra`). Снимок: новая цена — новая строка, история не
  стирается. Две цены в прайсе — два предложения.
- **Рабочая цена — `sites.price_id`**, одно предложение, общее для всех
  продуктов.
  - От неё считаются «пишем мы», «плановые расходы» и сравнение с
    ориентиром 550 €. Правила `04-DOMAIN-RULES.md` §1.3 не меняются.
  - Первая цена площадки становится рабочей сама (публикация, если
    есть), дальше рабочую меняет только человек.
  - Каждая смена записывается заметкой в историю.
  - У вставки ссылки «пишем мы» нет — писать нечего.
- **Разбор.** `site_prices.reviewed_at` пусто, пока по предложению не
  решили.
  - Загрузка оставляет пустым только то, что требует решения: цена
    продавца изменилась, дешевле или дороже рабочей, другая услуга,
    площадку отклоняли. Остальное сразу разобрано.
  - «Сделать рабочей» разбирает все предложения этой услуги у площадки.
  - «Оставить как есть» разбирает выбранные предложения, а действие в
    «Площадках» — все у площадки.
- **Пометки в «Площадках»** считает `v_site_latest`. Сравнивается только
  цена размещения одной услуги, в евро.
  - «Новая цена»: последнее предложение того же продавца за ту же услугу
    — не рабочее. Подорожало — ▲ красная, подешевело — ▼ зелёная.
  - «Дешевле»: самое дешёвое текущее предложение другого продавца за ту
    же услугу, если оно дешевле рабочей.
  - Пока предложение не разобрано, пометка цветная, после — серая.
- **Евро — по курсу ЕЦБ**: `exchange_rates` (валюта, дата, курс за 1
  евро), задача очереди раз в день. Курса на сегодня нет — берётся
  последний. Пересчёт нужен только для сравнения и показа: исходная цена
  хранится и видна, суммы в разных валютах не складываются.
- **Доверенные метрики.** `site_metrics.seller_id` — замер со слов
  продавца.
  - Доверенные: без продавца (Ahrefs API, вручную, таблица
    линкбилдинга) и от продавца с флажком `metrics_trusted`. У
    Collaborator флажок включён.
  - Показывается последний доверенный замер. Нет такого — последний от
    продавца, с пометкой «прод.».
  - В графики (E9-02) идут только доверенные.
  - Значение `seller` в `metric_source` не заводим: «со слов продавца» —
    это заполненный `seller_id`.
- **Заметки — `site_notes`**: текст, продукт (если заметка про решение
  под продукт), автор-пользователь или источник-файл, дата.
  - Заметки не правятся и не удаляются.
  - `sites.notes` удалена. Её 140 текстов и 62 причины отказа из
    таблицы перенесены миграцией с источником «таблица линкбилдинга».
  - В историю пишутся сами: смена рабочей цены, причина отказа,
    поставленная в админке, комментарии таблицы при `import_workbook`.
- **Размещение**: `seller_id` — через кого куплено, `employee_id` — кто
  вёл. Сотрудник — пользователь Django без пароля.
- **Экран «Площадки».**
  - Колонки: «Цена» (рабочая: цена, ≈ €, услуга, продавец),
    «Предложения» (пометки, при наведении — все цены), «Написание» с 📝
    вместо «пишем мы», «💬» с числом заметок.
  - Фильтры: «предложения» (есть новые / есть дешевле / нет рабочей
    цены), «продавец», «заметки».
  - Действия: «Принять новые цены», «Зафиксировать продавца…»,
    «Оставить как есть».
  - Карточка площадки открывается окном справа без перезагрузки, тем же
    приёмом, что кнопки индексации (ADR-042). Вся админка без
    перезагрузок — E9-09 (HTMX, ADR-014). **Уточнение 03.10.2026
    (ADR-048):** окно карточки заменено общей панелью записи.
- **Пользователи в `schema.sql`** — уточнение ADR-029 от 01.10.2026.

**Альтернативы.**
- Лучшая цена у продавцов без фиксации (первый план). Непонятно, на что
  ориентироваться, и после загрузки нечего разбирать.
- Отдельная таблица предложений рядом с `site_prices` — две таблицы
  одной структуры, перенос 1978 строк.
- Цены услуг колонками в одной строке (публикация, вставка) —
  фиксировать пришлось бы пару «строка + колонка». Пользователь: «одна
  цена за конкретную услугу».
- Сравнение с написанием и анонсом — их берут не всегда, «дешевле» было
  бы ложным.
- Действие «Зафиксировать самое дешёвое» — молча выбирало бы «дешёвое
  на бумаге». Есть «Зафиксировать продавца…».
- Рабочая цена своя у каждого продукта — пока не нужна. Если появится —
  колонка в `product_sites`.
- Флажок «рабочая» у строки цены — равноценно. Выбрано поле площадки:
  решение о площадке лежит у неё.

**Последствия.**
- `schema.sql` 1.7:
  - таблицы `sellers`, `site_notes`, `exchange_rates`;
  - у `site_prices` — продавец, услуга, серая цена, прочие данные,
    `reviewed_at`;
  - у `sites` — `price_id` вместо `notes`;
  - у `site_metrics` — продавец; у `placements` — продавец и сотрудник;
  - новые версии представлений.
- `reference_total_cents` и `expected_spend_cents` у площадки без цены
  теперь пусты, а не 0 (закрыт долг из PROGRESS) и считаются в евро.
- E1-08 — экран загрузки и разбора по прототипу. E1-09 — продавец и
  сотрудник у размещений из файлов. E9-02 — графики изменений. E9-09 —
  админка без перезагрузок. E4-02 — досье берёт рабочую цену,
  предложения и заметки.
- ADR-041 уточнён: «где дешевле» — пометка относительно рабочей цены, а
  не сравнение с Collaborator.

## ADR-044. Загрузка файлов продавцов и каталога Collaborator; рабочая цена идёт за продавцом
**Дата:** 01.10.2026 · **Статус:** принято; уточняет ADR-043

**Контекст.** ADR-041 и ADR-043 решили, что прайсы продавцов и каталог
Collaborator грузятся экраном в админке, с памятью разметки у продавца,
сводкой до записи и разбором по прототипу. При планировании E1-08 по
настоящим файлам выяснилось:
- полная выгрузка каталога (`my_source/`, 01.10.2026) — 45 041 строка
  из английского интерфейса, а база и настройки (`PROJECT_TOPICS`,
  `SPECIAL_TOPICS`) — в русском написании Collaborator из таблицы;
- цены Collaborator в евро плывут с курсом гривны: из 1891 площадки,
  что есть и в таблице, и в выгрузке, у 387 цена та же до цента, у 1401
  выросла не больше чем на 3%, дальше почти пусто до 10%. Цены вроде
  €23,19, €46,38, €92,77 кратны 1000 грн;
- пользователь: каталог — регулярно, около трёх раз в месяц; цену при
  новой выгрузке «надо менять, мы же с ними работать будем», и у
  Collaborator, и у других продавцов; фиксировать — пока по площадке
  заявка в работе. «Both» в прайсе — публикация, она в приоритете;
- повторное размещение того же продукта на площадке не нужно: один
  продукт — одна площадка; другой продукт — можно.

**Решение.**
- **Загрузка — запись `uploads`**: что за файл (прайс или каталог),
  продавец, дата цен, файл в папке загрузок (`UPLOADS_DIR`, видит
  воркер) и его отпечаток, разметка, сводка до записи, итог записи,
  рабочий список. Путь: колонки → проверка (задача `upload_check`, база
  не меняется) → сводка → запись (задача `upload_write`, одна транзакция)
  → разбор. Тот же файл с той же датой у того же продавца — открывается
  прежняя загрузка, ничего не пишется.
- **Строка разбора — `upload_items`**: предложение из файла, рабочая цена
  до загрузки, вкладка (`review_group`) по положению на момент записи,
  ждало ли решения, стало ли рабочим само, новая ли площадка. Решено ли —
  по самому предложению (`reviewed_at`) и рабочей цене площадки: решение
  из «Площадок» или карточки разбор видит.
- **Разметка — `sellers.column_map`** (заголовок → поле), словарь
  синонимов только подсказывает. Непустая колонка без поля — в «прочие
  данные», «не загружать» — только явно. Колонка наших комментариев —
  поле «Наша заметка», в историю заметок.
- **Каталог — встроенная разметка английской выгрузки**; тематики,
  особые тематики, типы сайта и языки переводятся словарями в русское
  написание (сопоставлены по 1891 площадке без спорных пар), незнакомое —
  как есть и в отчёт. Колонки без поля — в прочие данные предложения
  Collaborator, видны в карточке.
- **Рабочая цена идёт за продавцом** (уточнение ADR-043, где рабочую
  меняет только человек). Новая цена того же продавца за ту же услугу
  становится рабочей сама, при любой разнице; та же цена — рабочая
  переходит на свежий снимок. Пока у площадки размещение «заявка
  отправлена», «пишется» или «на проверке», рабочая не двигается, новая
  ждёт решения. Такие переходы в заметки не пишутся: при каждой выгрузке
  каталога их ~1500, история — в снимках цен.
- **Другой продавец или другая услуга — решает человек.** Предложение
  продавца, которое уже разобрали, снова ждёт решения, только если цена
  изменилась больше порога `OFFER_RECHECK` (3%). Старые неразобранные
  цены того же продавца за ту же услугу при новой загрузке разбираются
  сами: их сменила новая.
- **«Both»** — одно предложение «публикация», пометка остаётся в прочих
  данных (Q21).
- **Импорт таблицы** (`import_workbook`) цены не меняет по-новому: её
  цены Collaborator старее каталога и не должны подменять свежие.
- **Один продукт — одна площадка**: повторно размещать тот же продукт на
  площадке не планируем; другой продукт — можно (`04-DOMAIN-RULES.md`
  §1.5).
- **`v_site_latest`: заметки одним подзапросом** на все площадки:
  подзапрос на строку давал полный просмотр `site_notes` на каждую из
  45 000 строк — около секунды из двух на «Площадках».

**Альтернативы.**
- Просить выгрузку каталога в русском интерфейсе — лишний шаг три раза в
  месяц, забыть легко; заголовки и значения всё равно другие, чем в
  таблице.
- Перевести базу и настройки на английский — переписать 1978 площадок и
  настройки, а таблица продолжает приходить по-русски.
- Порог «до 3% — колебание курса» и для рабочей цены — пользователь
  выбрал «цена у продавца теперь такая», без порога.
- Фиксировать цену у всех площадок с заявкой или размещением любого
  продукта — около 650 площадок (599 — размещения Clideo) и сотни
  вопросов с каждой выгрузкой; цена после публикации нужна другим
  продуктам.
- «Both» — два предложения по одной цене — отклонено: публикация в
  приоритете.
- Сводка до записи пробной записью с откатом — вдвое дольше на каталоге;
  план без записи даёт то же и строится той же функцией, что и запись.

**Последствия.**
- `schema.sql` 1.8: `uploads`, `upload_items`, перечисления
  `upload_kind`, `upload_status`, `review_group`, `sellers.column_map`,
  новый текст `v_site_latest`.
- Настройка `OFFER_RECHECK` (`content.0004`).
- Выгрузка Ahrefs «кто ссылается на продукт» и отсев по ней — E1-09.
- Каталог целиком — рабочий список на 45 000 площадок: «Площадки»
  1,8 с на рабочих данных (было 3,4 с), счётчик страниц — 0,6 с.
- Снимки цен и метрик каталога — по 45 000 строк на загрузку, около
  2 ГБ в год с прочими данными; `v_site_offers` сортирует все снимки цен
  — со временем медленнее (техдолг).

**Уточнение 02.10.2026 — после показа экранов на копии базы.**
Пользователь попробовал загрузку каталога на копии рабочей базы и
попросил отсекать ненужное при загрузке, а не разбирать 43 000 новых
площадок; затем — работу без перезагрузок, лоадеры, удаление и
блокировку в разборе.
- **Две кнопки у каталога вместо «Записать в базу»:** «Обновить в базе»
  (площадки, которые уже есть; без фильтра) и «Добавить новые» (только
  новые для базы, по фильтру). У обеих галочки «цены / метрики /
  описание» — метрики Collaborator не перекрывают замер Ahrefs, если
  галочку снять. Нажатий сколько угодно, каждое — строка
  `uploads.result["runs"]` (кнопка, галочки, фильтр, счётчики). После
  записи сводка пересчитывается по свежему состоянию. Прайс продавца —
  по-прежнему одна кнопка.
- **Фильтры «Добавить новые»** (только каталог): Languages, Country,
  DR, Monthly Traffic, Organic traffic, Keywords, Publishing price, Link
  type, Advertising. «Любое из» — несколько значений, совпадение без
  регистра; «от — до» — пустая граница не ограничивает, нет значения при
  заданном диапазоне — не проходит; пустой фильтр — все. Не подошедшие
  не пишутся и **не отклоняются**: в следующей выгрузке могут пройти.
  Одна функция `filters.matches` и для живого счётчика, и для записи.
  Облачка — значения фильтров прошлых записей каталога; поиск — по
  значениям файла с числом площадок; выбранное браузер помнит для
  загрузки. Domain zone — не нужно (пользователь).
- **«Удалить из базы» в разборе** — пометка `sites.is_deleted` (правило
  «ничего не удаляем физически»), только у площадки без истории
  (размещения, аудиты, решения не «Новая», заметки людей); с историей —
  только блокировка. Удалённая для следующей загрузки — новая: запись
  снимает пометку, а не создаёт дубль.
- **«Заблокировать»** — статус «Чёрный список» у всех активных продуктов;
  такая площадка выпадает из разбора, загрузки её пропускают целиком и
  считают в сводке. Чёрный список у одного продукта — не блокировка.
  Список заблокированных — фильтр статуса в «Площадках». Обе операции
  отменяются; заметки в историю пишутся.
- **Экраны загрузки без перезагрузки:** шаги, вкладки, порядок и
  страницы разбора подгружаются запросом с заменой содержимого и адреса
  (`history.pushState`); кнопки записи и пересчёта отвечают JSON
  (заголовок `X-Seo-Ajax`), страница опрашивает состояние и обновляет
  только изменившиеся блоки. Лоадеры: полоска сверху, прогресс отправки
  файла, крутилка в кнопке, мерцание блоков. Без скрипта всё работает
  переходами. Вся админка без перезагрузок — по-прежнему E9-09.
- «Пересчитать сводку» у загрузки, из которой уже записывали, оставляет
  её «Записан» — разбор не закрывается.
- Экраны проверяются Chromium без окна на копии базы (разрешение
  пользователя): первый же прогон нашёл, что `form.action` у формы с
  полем `name="action"` — это поле, а не адрес.

Альтернативы уточнения: не подошедшие под фильтр — в «Отклонена»
(пользователь: «могут подойти в будущем»); удаление физически (правило
проекта); флажок блокировки у площадки — равноценно статусу, но статус
уже есть и виден в «Площадках»; фильтр и для «Обновить в базе» (данные
по известным площадкам должны быть свежими).

## ADR-045. Выгрузки Ahrefs Batch Analysis; трафик по странам — отдельная таблица снимков
**Дата:** 02.10.2026 · **Статус:** принято; уточняет ADR-043 и ADR-044

**Контекст.** Каталог Collaborator пересказывает метрики Ahrefs с
задержкой, а трафика по странам в нём нет. В таблице линкбилдинга его
вели руками: домены вставляли в Ahrefs → Batch Analysis, результат
вписывали в колонки Top Geo, Top Geo Traff, US Traff. При планировании
E1-10 по настоящим выгрузкам (`my_source/`, 01–02.10.2026):
- выгрузка **All locations** — DR, общий трафик (Traffic), ключи и одна
  колонка «Organic / Top Countries» вида «(us, 21101)»: на экране Ahrefs
  это Top location и Location traffic. Выгрузка по стране — те же
  колонки, но Traffic и Total Keywords — этой страны, а колонки топ-стран
  нет; саму страну файл не называет. У eggradients.com трафик США в
  выгрузке по США — ровно трафик топ-региона в выгрузке All locations;
- за сутки трафик сменился у всех 50 доменов, у ranktracker.com — и
  топ-страна (Индия → Япония);
- пользователь: регион в «Площадках» показывать, только если под страну
  загружали выгрузку этой страны — «в общем списке топ-регион может быть
  Индия, и мы просто не увидим, какой там трафик у US»; для работы со
  страной нужны обе выгрузки: трафик страны и топ-регион. Выбор страны
  при загрузке — с быстрым поиском;
- US Traff из таблицы (1941 площадка от 26.09) — трафик США у каждой
  площадки, не топ-регион (проверено при E1-04: при топ-регионе не US
  своя цифра, совпадения — только 0 = 0).

**Решение.**
- **Тип загрузки «Ahrefs Batch Analysis»** (`upload_kind` =
  `ahrefs_batch`) на экране «Загрузки»: встроенная разметка, без
  продавца (`uploads.seller_id` пуст только у него — CHECK
  `uploads_seller_check`), страна выгрузки — `uploads.country`, пусто —
  все страны. Выбор сверяется с файлом по колонке топ-стран; не сошлось —
  загрузка «Ошибка» с подсказкой. Сводка до записи (в базе, нет в базе,
  замер этого дня уже есть, дубли, ошибки) и итог; разбора и рабочего
  списка нет — решать нечего, а новый список сменил бы список «Площадок»
  по умолчанию.
- **Все страны → снимок `site_metrics`**: DR, трафик, ключи, топ-регион
  и его трафик; **страна → снимок `site_country_metrics`** (площадка,
  страна, трафик, ключи, источник, дата): по любой стране, а не колонкой
  на страну. Остальные колонки строки — в `raw`. Замер наш (без
  продавца, доверенный), источник — новое значение `metric_source`
  `ahrefs_batch`: в истории видно, откуда цифра, и снимок дня не
  совпадает со снимком импорта таблицы. Снимок дня — по площадке (и
  стране), источнику и дате: другой файл того же дня обновляет его.
  Строки в режиме Ahrefs, отличном от Subdomains/Domain, — ошибки: это
  метрики страницы.
- **Регион — только из выгрузок страны.** Трафик топ-региона в
  `site_country_metrics` не пишется. Последний замер по стране —
  `v_site_country_latest`; список регионов в «Площадках» — страны, по
  которым там есть строки.
- **US Traff — в `site_country_metrics`** (страна `us`, источник и дата
  снимка таблицы), колонка `site_metrics.us_traffic` удалена — трафик
  США не хранится в двух местах. Импорт таблицы пишет US Traff туда же.
- **Топ-регион в `v_site_latest`** — из последнего замера, где он есть,
  в том же порядке доверия, что метрики: замер каталога без гео его не
  стирает. Новые колонки `top_geo_traffic`, `top_geo_at`.
- **«Площадки»:** колонка «топ регион» всегда; фильтр «Регион» (по
  умолчанию «Все») добавляет колонки «трафик XX», «ключи XX» и «от — до»
  по ним, строки не отбирает; смена региона сбрасывает его «от — до» и
  сортировку. Пусто — данных по стране нет, не ноль.
- **«Домены для Ahrefs»** у рабочего списка (экран списков, разбор и
  каталог загрузки, «Площадки» с выбранным списком): части по 500 —
  лимит Batch Analysis, свойство внешнего сервиса, поэтому константа, а
  не настройка; по DR от большего, без удалённых; файл части или zip.
- **Названия стран** — django-countries: по-русски на экране,
  по-английски для поиска (в Ahrefs страны по-английски), свои короткие
  названия и синонимы («США», «uk») и правка перевода пакета, где он в
  родительном падеже («Мьянмы» → «Мьянма»). **Флаги** — общая картинка
  пакета (`flags/sprite-hq.png`, один запрос на все страны): флаги-эмодзи
  Windows не рисует. Выбор страны (загрузка) и региона («Площадки») — поле
  с поиском и флагами поверх `<select>` (`seo/country-picker.js`); без
  скрипта работает сам `<select>`.

**Альтернативы.**
- Трафик страны в `raw` замера — фильтр «от — до» по JSON на 45 000
  строк медленный и неудобный; колонка `country` в `site_metrics` —
  «последний замер» в `v_site_latest` пришлось бы отбирать по пустой
  стране, а выгрузка страны с DR перекрывала бы общий трафик пустым.
- Трафик топ-региона считать трафиком этой страны в регионе — отклонено
  пользователем: колонка страны была бы заполнена вразнобой, только у
  площадок, где страна — топ.
- Псевдопродавец «Ahrefs» вместо пустого продавца у загрузки — появился
  бы в «Продавцах», фильтре «Продавец» и выборе рабочей цены.
- `csv_import` как источник — снимок выгрузки и снимок импорта таблицы
  за один день попадали бы в одну строку и перетирали друг друга.
- Свой список стран в коде — 250 названий вручную; django-countries без
  моделей и миграций.

**Последствия.**
- `schema.sql` 1.9: `site_country_metrics`, `v_site_country_latest`,
  `uploads.country`, `uploads.seller_id` без NOT NULL с CHECK, значения
  `ahrefs_batch` у `metric_source` и `upload_kind`, без
  `site_metrics.us_traffic`, новый текст `v_site_latest` и
  `v_product_site_latest`. Миграции `sites.0013` (значения перечислений —
  отдельно: новое значение нельзя использовать в той же транзакции),
  `sites.0014` (перенос 1941 строки US Traff, суммы сходятся),
  `keywords.0003` (только состояние поля).
- Подзапрос топ-региона в `v_site_latest` — около +0,1 с на 45 000
  площадок (выборка страницы 0,67 → 0,76 с, подсчёт 0,41 → 0,49 с);
  страница «Площадок» на 45 000 — около 1,25 с и с регионом.
- Страница «Площадок» — 11 запросов: список регионов — свой запрос.
- Ahrefs API (E2-07) пишет в те же таблицы: общие метрики — в
  `site_metrics`, по странам — в `site_country_metrics`, источник
  `ahrefs_api`.
- **Наша статика — с версией в адресе** (`config/assets.py`: тег
  `{% asset %}`, `Css(...)` и `Js(...)` в `Media` админки): `?v=<время
  изменения файла>`. Сервер отдаёт статику без заголовков кеширования, и
  после правки браузер пользователя взял новый скрипт со старыми стилями —
  экран разъехался. Новые ссылки на наши CSS и JS — только так. В проде
  имена с хешем может дать ManifestStaticFilesStorage (E10-01).

## ADR-046. Админка без перезагрузки страниц: свой общий скрипт, не HTMX `hx-boost`
**Дата:** 02.10.2026 · **Статус:** принято

**Контекст.** Пользователю понравилось, что карточка площадки и экраны
загрузки работают без перезагрузки (E1-07, E1-08), остальная админка
перерисовывала страницу на каждый фильтр, переход и сохранение: «убирай
вообще всю подгрузку с обновлением страниц, а то это бесит» (02.10.2026,
E1-10). Задача E9-09 — переходы, фильтры, сортировка, страницы списков и
формы без полной перезагрузки; инструмент — HTMX (ADR-014) или подход
экранов загрузки, выбор — здесь.

Трудная часть не в перехвате ссылок, а в штатных скриптах Django и темы:
они настраивают страницу один раз — при выполнении файла (действия над
отмеченными, инлайны), по `DOMContentLoaded` или `load` (календарь, выбор
из двух списков, сворачивание групп меню) или вешают обработчики на
`document` (автодополнение, связанные объекты, окно «+» темы). После замены
содержимого первых надо запустить снова, вторых — нельзя: обработчики
задвоятся. Плагины jQuery (select2) цепляются к `window.jQuery`, который
`jquery.init.js` прячет. Набор стилей и скриптов у экранов разный: у
главной нет jQuery, у формы размещения — 21 скрипт.

**Решение.**
- **Свой скрипт `config/static/seo/soft-nav.js`** на всех страницах админки
  (`base_site.html`), на основе подгрузки экранов загрузки (ADR-044).
  Ссылки и формы (GET и POST, с файлами и нажатой кнопкой) админки
  перехватываются на `window`: свои обработчики (карточка, индексация,
  загрузки) срабатывают раньше и, отменив нажатие, забирают его себе.
- **Порядок перехода:** запрос страницы; стили нового экрана — до показа
  (иначе мелькнёт неоформленная страница); замена заголовка, классов
  `<body>`, крошек и `<main>` (боковое меню остаётся, переносится только
  подсветка пункта; меню нет на одной из страниц — меняется весь `#main`)
  в плавной смене View Transitions; затем новые скрипты `<head>` по порядку
  (`async = false`) — они запускаются сами и видят новое содержимое;
  скрипты внутри содержимого; перезапуск штатного, что было загружено
  раньше; событие `seo:load`. Перед заменой — `seo:unload`.
- **Перезапуск штатного** (`restartAdmin`): `actions.js` и `inlines.js`
  выполняются заново; `filters.js` — своим кодом (он вешается на все
  `<details>`, и на «Оформление» в шапке); автодополнение, ссылки
  связанного объекта, календарь, выбор из двух списков, сворачивание меню
  — вызовом их функций; скрипты темы, которые на главной без jQuery ничего
  не сделали, — заново, когда jQuery появился. Только то, что было
  загружено раньше: загруженное этим переходом запустилось само. Пока
  грузятся новые скрипты, `window.jQuery` снова указывает на
  `django.jQuery` — как при обычной загрузке, где плагины грузятся до
  `jquery.init.js`.
- **История и прокрутка:** адрес всегда настоящий (`pushState`); «Назад»
  перечитывает экран с сервера — цифры свежие (решение пользователя) — и
  возвращает прокрутку, сохранённую в записи истории
  (`scrollRestoration = manual`, сохраняем, когда прокрутка остановилась).
  Другой экран — наверх; тот же экран с другими фильтрами или сортировкой
  — на месте; страницы списка, меню, крошки — наверх. POST с ошибками в
  форме — без новой записи в истории.
- **Обычный переход** там, где подгрузка не к месту: файл в ответ
  (`Content-Disposition`) скачивается; страница входа (сессия истекла),
  ошибка сервера на GET, ответ не страницей — переходом; ошибка сервера на
  POST — его страница целиком (повторять POST нельзя); выход (POST в
  шапке), ссылки с `download`, `target`, `data-no-soft`, `?_popup=1`;
  во всплывающем окне связанного объекта и на странице входа скрипт
  выключен.
- **Фильтры списков:** выпадающие (тема) и «от — до» (rangefilter)
  открывали адрес через `window.location`; их скрипты убраны из наших
  шаблонов, выбор ведёт `soft-nav.js`; регион (`country-picker.js`) — через
  `seoNav.visit`.
- **Окно «Решение по площадке»** (после показа, по просьбе пользователя:
  «неудобно переходить постоянно»): статус в «Площадках» открывает окно
  поверх списка (`<dialog>`, `seo/site-decision.js`) — статус и причина
  отказа (`ProductSiteAdmin.decision_view`, ответ только формой по
  заголовку `X-Seo-Partial`, после записи — JSON с подписью). Сохранили —
  окно закрылось, список перечитан на месте, сообщение внизу. Причина —
  в историю заметок, как из полной формы. Полная форма — «Открыть
  полностью» или Ctrl. **Уточнение 03.10.2026 (ADR-048):** окно заменено
  общей панелью записи справа, статус — кнопками, после записи меняется
  только строка.
- **Наши скрипты** навешивают обработчики по `seo:load`, снимают по
  `seo:unload`, переходят через `window.seoNav` (`visit`, `reload`,
  `render`, `progress`, `toast`). Экраны загрузки — на общей подгрузке (своя
  удалена), карточка площадки после изменений перечитывает экран на месте
  (`seoNav.reload()`), а не всю страницу. Полоска загрузки и сообщения —
  общие, `seo/soft-nav.css`.
- **Браузерные проверки в репозитории** (`make e2e`): Playwright и
  Chromium без окна, отдельная цель `e2e` в Dockerfile и сервис compose с
  профилем (`make up` его не собирает), тесты `tests/e2e/`, сервер —
  `live_server` pytest-django. Ошибка JavaScript на странице роняет
  проверку. `make test` их пропускает (маркер `e2e`).

**Обоснование.** Для экрана разницы нет; разница — в надёжности.
`hx-boost` берёт на себя только перехват ссылок и форм. Перезапуск
штатных скриптов пришлось бы писать и с ним, а без доработки он не ждёт
стилей нового экрана и по «Назад» по умолчанию восстанавливает сохранённую
копию страницы с уже запущенными виджетами (двойные календари). Подход
экранов загрузки уже проверен пользователем, порядок «стили — замена —
скрипты» держим сами.

**Альтернативы.**
- HTMX `hx-boost` — см. обоснование. HTMX остаётся инструментом для своих
  экранов с частичным обновлением (ADR-014 не меняется): там его атрибуты
  экономят код.
- Turbo (Hotwire) — ждёт от формы ответа 303 или 422, а админка Django
  отвечает на ошибку в форме кодом 200.
- Предзагрузка страниц браузером (Speculation Rules) с переходами View
  Transitions — страница всё равно перезагружается целиком, только быстрее;
  моргание в Opera (ADR-038) не уходит.
- Запомненная копия экрана для «Назад» — мгновенно, но показала бы цену
  до правки в карточке; пользователь выбрал перечитывать.

**Последствия.**
- Время перехода — время ответа сервера: на копии базы «Площадки»
  открываются подгрузкой за 0,55–0,75 с, как перезагрузка из кеша
  браузера (0,65–0,68 с); число запросов к базе то же (11 у «Площадок»).
  Ускорение — заранее посчитанная «площадка на сегодня», отдельная задача.
- Новый скрипт экрана: обработчики — по `seo:load` (и снимать по
  `seo:unload`, если вешали на `document`), переходы — `seoNav.visit`, а не
  `window.location`. Штатный скрипт Django или темы, который настраивает
  страницу при загрузке, — добавить в `restartAdmin` и в `make e2e`.
- Шаблоны `admin_interface/dropdown_filter.html` и
  `rangefilter/numeric_filter.html` — без скриптов; при обновлении пакетов
  сверить с оригиналом (ADR-038).
- Панель отладки обновляется при подгрузке (`UPDATE_ON_FETCH`): запросы
  к базе видны у каждого экрана.
- Уход со страницы с несохранённой формой не предупреждает — как и раньше.
- Однострочные поля (E9-08, ADR-038) — только для text без списка
  значений: статусы — перечисления Postgres, для Django это тоже
  TextField, и с E9-08 форма показывала их полем ввода («New нет среди
  допустимых значений»). Исправлено в E9-09 (`config/admin.py`).

## ADR-047. Статусы площадки: просмотрено, заявка отправлена, отбрасываю, отказала площадка; статус по размещениям
**Дата:** 02.10.2026 · **Статус:** принято

**Контекст.** Шести статусов площадки мало, и «Отклонена» смешивала два
смысла: в таблице линкбилдинга так помечали и отказ площадки, и наш отказ.
На рабочей базе все 62 площадки Convertio с «Отклонена» — наш отказ, в
причине у каждой «…отбрасываем». «Одобрена» включала и отправленные заявки
(маппинг §1.2а). Статус сам не менялся: даже «Размещались» ставил только
импорт таблицы. Пользователь 02.10.2026 (E9-09): «отклонена значит что
площадка сама отклонила; просмотрено, отбрасываю, заявка отправлена —
статусы нужны».

**Решение.**
- **Девять статусов** в порядке окна статуса: Новая `new` → Просмотрено
  `viewed` → Одобрена `approved` → Заявка отправлена `ordered` →
  Размещались `placed`; Отбрасываю `discarded`, Отказала площадка
  `declined`, Чёрный список `blacklisted`; На аудите `auditing`.
  «Заявка отправлена» — тот же код, что у размещения.
- **`rejected` убран**, отказ площадки — новый код `declined`. У старого
  кода смысл «любой отказ»: новый код не даёт ему тихо перейти в новое
  значение, забытое место в коде падает на проверке типов. Внешних
  читателей кода ещё нет: срез для ai-editor (E10-07) и выгрузки (E1-06)
  не сделаны. Все `rejected` миграция переводит в `discarded`, причины не
  трогает.
- **Тип `site_status` создаётся заново** в этом порядке (`sites.0015`):
  значение, добавленное в старый тип, не переставить, а «На аудите» стоял
  вторым. Порядок значений в Postgres — порядок `SiteStatus` (сверка
  тестом), по нему сортирует колонка «статус» в «Площадках». Колонку
  читают `v_product_site_latest` и `v_site_funnel` — миграция их
  пересоздаёт тем же текстом, всё в одной транзакции.
- **Статус по размещениям** (`apps/sites/statuses.py`). Лесенка «Новая →
  Просмотрено → Одобрена → Заявка отправлена → Размещались», система
  двигает статус по ней только вперёд. Размещение «Заявка отправлена»,
  «Пишется», «На проверке» ставит площадке «Заявка отправлена»,
  «Опубликовано» — «Размещались». Новый факт — размещение создано или его
  статус сменился — сильнее прежнего «Отбрасываю», «Отказала площадка» и
  «На аудите» (выбор пользователя 02.10.2026: «попробуем, если что
  поменяем»); «Чёрный список» система не трогает никогда. Решение без
  факта — «Одобрена» по запланированному размещению, отказ из таблицы или
  аудита — встаёт только на «Новая» и «Просмотрено». Человек в окне
  статуса ставит любой.
- **Где срабатывает:** `Placement.save()` сравнивает статус, площадку и
  продукт со строкой в базе до записи и вызывает `statuses.advance()` —
  один UPDATE с условием на текущий статус, вместе с записью размещения
  (`atomic`). Правка без смены статуса — комментарий, проверка индексации
  — статус площадки не трогает. Так срабатывают админка, импорт и
  будущие списки E1-09; `QuerySet.update()` статуса размещения обходит
  правило — им статус размещения не менять.
- **Импорт таблицы** — то же правило: заявка — «Заявка отправлена»,
  публикация — «Размещались», запланированное — «Одобрена», «…отбрасываем»
  — «Отбрасываю». Новый факт — только если этот импорт создал размещение
  или продвинул его статус; та же заявка при повторном импорте отказ,
  поставленный после неё, не перекрывает — расхождение в отчёт.
- **Догоняющий проход** в той же миграции: площадка у продукта с заявкой в
  работе — «Заявка отправлена», с публикацией — «Размещались», только по
  лесенке. Прежний отказ не трогается: неизвестно, был он до размещения
  или после. На рабочей базе — 27 «Одобрена» стали «Заявка отправлена».
- **Разбор загрузки:** вкладка «Отклоняли» — «Отбрасываю», «Отказала
  площадка» и «Чёрный список», рядом с причиной — статус.
- **Аудит (E4)** отказ ставит как «Отбрасываю» (`04-DOMAIN-RULES.md` §1.7).

**Обоснование.** Статус площадки отвечает на вопрос «где мы с ней сейчас»,
и заявка с публикацией — самые надёжные ответы: их фиксирует размещение.
Двигать только вперёд — чтобы новая заявка на площадке, где уже
размещались, не откатывала её в «Заявка отправлена». Новый факт сильнее
старого отказа, иначе площадка с живой заявкой висела бы как отброшенная;
повторённый старый факт — нет, иначе каждый регулярный импорт (ADR-033)
откатывал бы отказ, поставленный после заявки.

**Альтернативы.**
- Оставить код `rejected` под «Отказала площадка» — меньше правок, но
  смысл кода меняется молча, и забытые места продолжили бы считать его
  нашим отказом.
- Дописать значения в старый тип (`ADD VALUE … BEFORE/AFTER`) — порядок
  окна и сортировки разошёлся бы с порядком в базе, а сверка тестом
  требует одного порядка.
- Триггер Postgres на `placements` — ловил бы и `QuerySet.update()`, но
  правило жило бы в двух языках (импорт тоже его применяет), а логика —
  вне Python, где её ищет разработчик.
- Отказ, аудит и чёрный список не трогать вовсе — статус с живой заявкой
  остался бы «Отбрасываю»; пользователь выбрал «новый факт сильнее».

**Последствия.**
- Размещение «Отклонено» статус площадки не меняет: у размещения это
  «площадка или мы отказались», отказ площадки ставит человек.
- Цвета девяти статусов для дашборда — к E9-03 (ADR-038).
- Повторный импорт таблицы, где у площадки ещё стоит заявка, а в системе
  — «Отказала площадка», каждый раз даёт строку в разделе расхождений.

## ADR-048. Записи панелью справа поверх списка: одна панель, форма с сервера, строка — на месте
**Дата:** 03.10.2026 · **Статус:** принято

**Контекст.** После E9-09 переходы идут без перезагрузки, но запись
открывалась отдельной страницей: чтобы сменить статус размещения, пользователь
уходил из «Размещений» на полную форму. Пользователь 02.10.2026 (показ
E1-12): «выдвигающееся окно с правого края, примерно до списка доменов»,
кнопки и поля — «по best practice UX», похожие окна сделать такими же — «как
можно меньше переходов». Образец — карточка площадки (E1-07). Своих окон было
два: карточка справа, с затемнением, и «Решение по площадке» — окно по центру
(`<dialog>`, E9-09).

**Решение.**
- **Одна панель на всё** — `config/static/seo/panel.js` на всех страницах
  админки (`base_site.html`); `site-card.js` и `site-decision.js` удалены.
  Панель без затемнения, список под ней живой: щелчок по другой записи
  открывает её, ↑/↓ — соседнюю запись той же колонки, щелчок по списку или
  Esc — закрыть.
- **Ширина — по содержимому**, с небольшими отступами (решение
  пользователя 03.10.2026 после показа: «ровно на ту, чтобы контент
  помещался»). Ширину задают поля, кнопки и таблицы; текст — пояснения,
  заметки, прочие данные — переносится по ней и сам её не раздвигает
  (`contain: inline-size`, `seo/panel.css`). Не уже 480 px и не дальше
  первой колонки строки (домен, название) — она видна всегда; экран уже
  900 px — во всю ширину. Большие текстовые поля в панели — 30em вместо
  48em, форма размещения — по одному полю в строке. Первый раз панель
  показывается, когда содержимое на месте, — без рывка ширины.
- **Что открывается панелью.** Ссылки с `data-panel` (адрес — значение
  атрибута или `href`): карточка и решение в «Площадках», домен в разборе
  загрузки, ссылки внутри панели. В списках админок с `panel = True`
  (`config.admin.ModelAdmin`, класс `seo-panel-list` у `<body>`) — ссылки
  строк на запись этого списка и «Добавить». Включено у размещений,
  каталога площадок, продавцов, ключей, рабочих списков, продуктов и
  настроек; у снимков — нет: новый замер там — «Сохранить как новый
  объект». Ctrl, Shift, средняя кнопка — полная страница.
- **Форма с сервера — та же страница.** Панель просит адрес записи с
  заголовком `X-Seo-Partial`; админка с `panel = True` рисует ту же форму,
  но вместо заголовка страницы — шапка панели (запись, «Открыть полностью»,
  ✕), вместо кнопок внизу — закреплённые «Сохранить» и «Отмена»
  (`seo_panel` в `admin/change_form.html`); «История» и удаление — на полной
  странице. Стили, скрипты и штатные виджеты (автодополнение, «Добавить
  ещё», окно «+») поднимает `seoNav.mount` (`soft-nav.js`): порядок тот же,
  что у перехода, но перезапуск штатного — только внутри панели, `actions.js`
  списка под ней не трогается.
- **Записали — JSON, ошибка — форма с кодом 200.** В режиме панели
  `response_change` и `response_add` отвечают `{saved, pk, message, notes}`;
  сообщения, положенные кодом записи, уходят в ответ, а не на следующий
  экран. Ошибка — та же форма с подсказками, код 200, как у штатной админки:
  ответ 400 браузер пишет в консоль ошибкой. Адрес отправки формы — от адреса
  записи: у формы Django он бывает относительным (`?_changelist_filters=…`),
  и от адреса списка запись ушла бы на список.
- **Строка — на месте, а не весь экран.** После записи панель перечитывает
  адрес списка и меняет ячейки одной строки — той, где ссылка, которой
  запись открыли. Ячейку с галочкой не трогает: `actions.js` держит галочки,
  найденные при загрузке страницы, и отмеченное человеком не теряется.
  Запись больше не подходит под фильтры — строка остаётся блёклой с
  подсказкой (решение пользователя 03.10.2026). Новая запись («Добавить») и
  список с полями в строках (`list_editable`) — экран перечитывается целиком.
- **Несохранённые правки.** Главная форма при показе запоминается и
  сравнивается с нынешней. Esc, ✕, щелчок мимо панели, ↑/↓, ссылка из
  панели при правках — вопрос строкой внизу панели: «Сохранить · Не
  сохранять · Остаться»; «Сохранить» записывает и делает то, что хотели.
  Щелчок мимо панели ловится до всех обработчиков страницы и после ответа
  повторяется. «Отмена» закрывает без вопроса; F5 и закрытие вкладки —
  вопрос браузера.
- **Форма под удобство** (`config/forms.py`): `ChoiceButtons` — выбор
  кнопками по порядку (это радиокнопки: клавиши и отправка штатные);
  `DayField` — день для поля-момента: новый день — начало дня по времени
  проекта, как у импорта, день не меняли — момент со временем остаётся;
  поле даты браузера и «Сегодня» по часам сервера; `MoneyField` — сумма в
  валюте («120,50»), в базе — центы. Размещение: статус кнопками, группы
  «Заявка», «Публикация», ссылки статьи, «Проверки», «Комментарий»,
  «Служебное»; в панели площадка и продукт — в заголовке, на полной странице
  — поля. Кнопка «Заявка отправлена» или «Опубликовано» ставит сегодняшний
  день в пустую дату (решение пользователя 03.10.2026); подставленный день
  подсвечен и уходит, если выбрали другой статус. Решение по площадке —
  статусы кнопками в три ряда: путь площадки, отказы, аудит; так же и в
  полной форме решения.
- **Карточка, решение, факты, размещение** связаны ссылками внутри панели:
  «сменить» у статуса продукта в карточке, «Карточка площадки» в решении и в
  размещении, «Факты о площадке» в карточке.

**Обоснование.** Форма в панели — та же, что на полной странице: всё, что
правится в админке, работает в панели без своего шаблона на каждую модель;
права, проверки формы, журнал изменений и `Placement.save()` со статусом
площадки (ADR-047) идут штатным путём. Замена одной строки вместо всего
экрана: «Площадки» перечитываются 0,55–0,75 с (ADR-046) — список за это время
не моргает, следующую запись можно открыть сразу, галочки не сбрасываются.

**Альтернативы.**
- Свой кусок формы без страницы на каждую модель — меньше данных, но форма
  разошлась бы с полной страницей; по скорости разницы не видно.
- Перечитывать весь экран после записи, как окно решения E9-09, — проще,
  но сбрасывает галочки и перерисовывает весь список; строка, ушедшая из
  фильтра, исчезала бы без следа.
- Панель с затемнением, как прежняя карточка, — список под ней не нажать: к
  соседней записи только через закрытие.
- Панель от первой колонки списка до края экрана (первый вариант E9-11) —
  на широком экране половина панели пустая; пользователь на показе
  попросил ширину по содержимому.
- Убирать строку, ушедшую из фильтра, сразу — пользователь выбрал оставлять
  её блёклой.
- HTMX для панели — трудная часть та же, что у переходов: стили, скрипты,
  перезапуск штатного (ADR-046); её уже делает `seoNav.mount`.
- Календарь Django для дат размещения — его окошко живёт в `<body>` и
  считает место от страницы, а не от панели; время и предупреждение о
  часовом поясе в этих датах не нужны.

**Последствия.**
- Новая админка с правкой записей — `panel = True`, если форме хватает
  одной кнопки «Сохранить»; заголовок панели — `panel_title()`.
- Своя ссылка на запись в колонке списка — `data-panel`; в списке с панелью
  ссылка на `…/<номер>/change/` этого же списка работает и так.
- Скрипт для содержимого панели вешает обработчики делегированием на
  `document` (как `indexation.js`, `widgets.js`): `seo:load` при показе
  панели не приходит.
- Кнопка проверки индексации в панели — в группе «Проверки»
  (`data-indexation-button`); на полной странице — прежняя форма над
  записью, она работает и без скрипта.
- Дата заявки и публикации из формы — начало дня по времени проекта; время,
  если оно было, не меняется, пока не сменили день.
- Окно карточки (ADR-043) и окно решения (ADR-046) заменены панелью.

## ADR-049. История смены статусов: строку пишет триггер, «кто и откуда» — отметка кода
**Дата:** 03.10.2026 · **Статус:** принято

**Контекст.** Пользователь 03.10.2026 (E9-11): «можно потом хронологию смены
статусов посмотреть на карточке». Статус площадки у продукта и статус
размещения хранились только текущими: когда размещение стало «Пишется», кто
и когда отбросил площадку — нигде. Меняют статус много путей: панель и
полная форма админки, строки статусов в фактах площадки, решение по
площадке, система по размещению (`statuses.advance()`, ADR-047 — это
`QuerySet.update()` без `save()`), импорт таблицы, блокировка в разборе
загрузки и её отмена (тоже `update()`), будущие миграции-переводы.
История копится только с запуска.

**Решение.**
- **Две таблицы** (`schema.sql` 1.11): `site_status_changes` — по строке
  `product_sites`, `placement_status_changes` — по размещению. В строке —
  был, стал, когда, откуда (`status_source`), кто (`auth_user`), `run_id`; у
  площадки ещё размещение, по которому статус сменила система. Статусы —
  те же типы `site_status` и `placement_status`, поэтому таблицы две, а не
  одна с текстом. Строки не правятся и не удаляются.
- **Строку пишет триггер** `AFTER INSERT / UPDATE OF status` на
  `product_sites` и `placements`, только если статус правда сменился
  (`OLD.status IS DISTINCT FROM NEW.status`). Правка без смены статуса и
  тот же статус ещё раз строки не дают — это условие триггера, а не
  дисциплина кода. Новое размещение — строка «Создано» (`from_status`
  пусто); строки «Новая» для каждой пары продукт × площадка — не смена.
- **Кто и откуда — отметка кода** в переменных транзакции:
  `set_config('seo.change_*', …, true)`, значение живёт до конца
  транзакции, триггер читает его `current_setting(…, true)`. Модуль
  `config/changes.py`: `bind_change(source, actor_id)` — точка входа
  говорит, откуда работа (`ContextVar`, как `run_id`); `stamped()` переносит
  отметку в транзакцию на время одной записи и потом возвращает прежнюю,
  чтобы отметка не прилипла к следующей записи той же транзакции.
  `stamped()` вызывают `ProductSite.save()`, `Placement.save()`,
  `statuses.advance()` (сам ставит «по размещению» и номер размещения) и
  отмена блокировки.
- **Точки входа:** `ChangeContextMiddleware` — запрос админки: вошедший
  пользователь, «панель» при `X-Seo-Partial`, иначе «форма»; импорт
  таблицы — «импорт таблицы», разбор загрузки — «загрузка» от того, кто
  нажал. Миграция, которая переводит статусы, первой строкой RunSQL
  выполняет `config.changes.MIGRATION_STAMP_SQL` — «миграция».
- **Не отметил — всё равно строка**, «откуда» пусто, на экране «не
  отмечено». Так смена в обход экранов (консоль, будущий код) видна, а не
  пропадает.
- **Показ:** в карточке площадки — «история (N)» у статуса каждого продукта,
  раскрывается списком, новые сверху (выбор пользователя 03.10.2026); в
  панели и форме размещения — список сразу под кнопками статуса. Смена «по
  размещению» в карточке — ссылка на размещение в той же панели (ADR-048).
- **Задним числом не заполняем** (решение пользователя 03.10.2026): даты
  заявки и публикации и так видны в размещении.

**Обоснование.** Критерий задачи — «каждая смена — строка». Обход `save()`
уже есть в двух местах и легко появится снова; триггер ловит любую смену
по построению, а тест сверки схемы (ADR-029) держит его текст равным
`schema.sql`. «Кто» и «откуда» база сама знать не может — это знает только
код, поэтому отметка, а не правило.

**Альтернативы.**
- Только Python — запись истории в `save()` и в каждом `update()` — проще
  читать, но забытый путь тихо теряет строку; пользователь выбрал триггер.
  ADR-047 отклонил триггер для *правила* движения статуса (правило жило бы
  в двух языках); здесь в триггере правила нет, только запись факта.
- Пакеты истории Django (`django-simple-history`, `django-reversion`) —
  копия всей строки на каждое сохранение, тоже только через `save()`.
- Одна таблица для обоих статусов — колонки статусов пришлось бы держать
  текстом без проверки типа.
- Отметка сразу в переменных сессии (`set_config(…, false)`) — соединения
  Django живут дольше запроса, отметка прилипла бы к чужой работе.

**Последствия.**
- Тест сверки схемы сравнивает и триггеры (`pg_get_triggerdef`).
- Продукт, у которого меняли статус, удалить нельзя, даже если строки снова
  «Новая» (`Product.has_history`).
- Новое место, которое меняет статус, — внутри `bind_change` своей точки
  входа; `update()` статуса — внутри `stamped()`, иначе в истории «не
  отмечено».
- Время в истории — по времени проекта, как во всей админке.
