# 08. Журнал решений (ADR)

Каждая запись: контекст, решение, альтернативы, последствия.
Новые решения дописывать сюда, а не держать в голове или в переписке.
Через полгода именно этот файл ответит на вопрос «почему мы сделали так».

Формат статуса: `принято` / `пересмотрено` / `отменено`.

## ADR-001. Источник правды — Postgres, а не Excel
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** 568 строк, 33 колонки, два человека, параллельные версии
файла, 530 строк без статуса.

**Решение.** Единственный источник правды — база. Excel остаётся форматом
экспорта для отчётов.

**Альтернативы.** Google Sheets с скриптами — отвергнуто: логика в
таблице не тестируется и не версионируется; надстройки над Excel —
отвергнуто по той же причине.

**Последствия.** Любой модуль пишет в базу, а не в файл. Требуется
импорт и экспорт. Excel перестаёт быть рабочим инструментом.

## ADR-002. Python + Django вместо PHP + Laravel
**Дата:** 17.09.2026 · **Статус:** принято (пересмотр предыдущей рекомендации)

**Контекст.** Разработчик имеет опыт легаси-PHP 5.6/7 без фреймворков,
немного Go, Python не знает. Первоначально рекомендовался PHP как
«знакомый».

**Решение.** Python 3.12 + Django.

**Обоснование.**
- Фреймворк придётся учить в любом случае — аргумент «бери знакомое»
  обнуляется примерно на 60%, переносится только синтаксис и общие
  инстинкты.
- Вторая половина системы (E8, проверка уникальности через эмбеддинги,
  статистика по вариантам промпта) — питоновская территория.
- Официальный SDK Anthropic для Python — первого класса; PHP SDK в бете.
- Карьерная ценность: SEO-автоматизация + LLM-пайплайны — питоновская
  экосистема.
- Явный питоновский код проще ревьюить, чем магию Laravel, что важно при
  разработке с ИИ-помощником.

**Цена решения.** Плюс 2–3 недели до первого рабочего модуля.

**Альтернативы.** PHP+Laravel — было бы правильным выбором при наличии
боевого опыта Laravel. Go — слишком много ручной работы, нет админки.
FastAPI — отвергнуто: ничего не даёт из коробки, слишком много развилок
для человека, изучающего язык.

## ADR-003. ORM для объектов, сырой SQL для отчётов
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** Известная критика ORM («выстрел в ногу») справедлива в Go,
где ORM слабые и пишутся нагруженные сервисы.

**Решение.** Django ORM для жизненного цикла объектов (создать площадку,
обновить статус, записать проверку, отрисовать карточку). Сырой SQL и
представления — для отчётов, агрегаций и дашбордов.

**Обоснование.** Объём данных мизерный (тысячи строк), бюджет задержек
съедают внешние API (секунды и минуты), а админка генерируется из моделей
ORM — отказ от ORM убивает главную причину выбора Django.

**Обязательные меры против классических граблей.** Логирование SQL в
разработке, django-debug-toolbar со счётчиком запросов, явные
`select_related`/`prefetch_related`, просмотр `sqlmigrate` перед
применением миграций, индексы вручную.

## ADR-004. Своя LLM не используется
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Только внешние API.

**Обоснование.** Локальная модель слабее по качеству оценки текста,
требует GPU, стоимость которого сопоставима с годом оплаты API, вся
поддержка на одном человеке. Единственный аргумент за локальную модель —
приватность — неприменим: анализируются публичные сайты.

## ADR-005. Никакого fine-tune, «обучение» через библиотеку
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** Запрос звучал как «повышать вес при положительном вердикте».

**Решение.** Веса модели не меняются. Веса живут на уровне библиотеки
примеров, анкорных конструкций и вариантов промпта.

**Обоснование.** Параметры модели меняются только градиентным спуском на
большом датасете; одна принятая статья их не двигает. Fine-tune Claude
доступен фактически только для старой модели Claude 3 Haiku через Amazon
Bedrock в одном регионе — отдавать ей генерацию статей хуже, чем брать
топовую модель с хорошим промптом. Правила ТЗ меняются часто, и правка
строки в базе несравнимо дешевле переобучения.

**Уточнение 23.09.2026.** Claude 3 Haiku, для которой дообучение было
доступно в Bedrock, дошла до конца жизненного цикла 10.09.2026 (карточка
модели в документации AWS). Публично известного пути дообучения Claude
на эту дату нет. Решение не меняется, аргумент стал сильнее.

**Пересмотр.** Вернуться к вопросу при 100+ принятых статей с разметкой —
и только если к тому моменту появится доступный путь дообучения.

## ADR-006. Роутинг моделей по задачам через конфиг
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Слой абстракции над провайдером с первого вызова; модель для
каждой задачи задаётся конфигом, не кодом.

**Обоснование.** Дешёвая модель для классификации и извлечения фактов,
сильная — для аудита, генерации и критика. Смена модели или добавление
второго вендора не должны затрагивать код модулей.

## ADR-007. Продукт — сущность первого класса
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** В старой таблице Clideo присутствует как колонка «Пример
статьи на Clideo».

**Решение.** Таблица `products`; Convertio и Clideo равноправны.
Старая ссылка на Clideo — это обычное размещение другого продукта.

**Последствия.** Проверка живости старых ссылок выполняется тем же
чекером. Система готова к третьему продукту без переделки схемы.

**Уточнение 23.09.2026.** В первой версии было записано, что удаление
ссылки на любой продукт — стоп-фактор для остальных. Это расходилось с
промптом аудитора: удалённая ссылка на Clideo — «не формальный жёсткий
стоп-фактор, но весомый негативный сигнал». Исправлено: стоп —
только удаление ссылки на основной продукт (Convertio), Clideo — сильный
минус в гибкой зоне. В самом промпте есть противоречие между двумя
разделами, трактовка вынесена в Q12.

## ADR-009. Деньги в центах, итоговая цена вычисляется
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Целые числа в центах + код валюты. Итоговая цена не
хранится: плановая считается до размещения, фактическая — после.

**Обоснование.** Float для денег даёт накопительную ошибку. В текущей
таблице поле «Итог цена» местами некорректно, что подтверждает
нежизнеспособность хранимого агрегата.

## ADR-010. Монолит на одном VPS
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Docker Compose, один сервер, без Kubernetes и микросервисов.

**Обоснование.** Два пользователя, сотни задач в сутки. Сложность

## ADR-011. Три раздельных слоя наблюдаемости
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Технические логи (stdout, JSON, 3 недели) ≠ доменный аудит
(таблицы в Postgres, вечно) ≠ ошибки (Sentry).

**Обоснование.** Смешение этих слоёв — главная причина, по которой
системы наблюдаемости ставят и не используют. В интерфейс выводится
только доменный слой.

---

## ADR-012. Без Prometheus, Grafana и Jaeger на старте
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Не ставим.

**Обоснование.** Prometheus решает задачу временных рядов при высоком
RPS на многих инстансах — не наш случай. Jaeger решает трассировку через
множество сервисов — у нас монолит. Полезная идея из Jaeger (сквозной
идентификатор) реализуется колонкой `run_id`.

**Пересмотр.** Если понадобятся графики — Grafana умеет ходить в Postgres
напрямую, слой метрик не нужен.

---

## ADR-013. Sentry берём сразу
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Единственный внешний сервис наблюдаемости с первого дня.

**Обоснование.** Разница между «что-то упало ночью» и «вот точное место
и входные данные» — часы времени на каждом инциденте.

**Уточнение (26.09.2026).** До выкладки на прод события принимает
GlitchTip — совместимый с Sentry сервис, sentry.io с машины разработчика
недоступен. См. ADR-026.

## ADR-014. Django Admin как интерфейс версии 1
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Первый интерфейс — админка. SPA не делаем.

**Обоснование.** Требование «потрогать на второй день» выполняется

## ADR-015. Критик — отдельный вызов с чистым контекстом
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Проверка статьи выполняется отдельным LLM-вызовом, который
не видит историю генерации.

**Обоснование.** Модель, только что написавшая текст, — плохой судья

## ADR-016. Детерминированные проверки делает код, не LLM
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Позиции ссылок, rel, количество ссылок, структура, объём,
индексируемость — кодом. LLM оставляем тест на извлечение и оценку
естественности.

**Обоснование.** Код не галлюцинирует, не замыливается, стоит ноль.
Отдавать LLM то, что решается парсером, — самая частая ошибка в таких
проектах.

## ADR-017. Уникальность контента — критичное требование
**Дата:** 17.09.2026 · **Статус:** принято

**Контекст.** 50 статей в месяц из одного пула фактов.

**Решение.** Ротация фактов, ротация структур, проверка косинусной
близости, вариативность анкорных конструкций — всё обязательно, с первой
версии генератора, а не «допилим потом».

**Обоснование.** Это единственный риск проекта, способный навредить
основному бизнесу, а не просто потратить время.

## ADR-018. Человек остаётся в цикле
**Дата:** 17.09.2026 · **Статус:** принято

**Решение.** Финальное «да/нет» по площадке и «принято» по статье —
за человеком. Автопостинг не делаем.

**Обоснование.** Одна статья с выдуманным фактом на дорогой площадке

## ADR-019. Пороги и списки — отдельно от правил проверки
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Пороги аудита (зоны DR, трафика) и контентные настройки
были записаны в таблицу `rules`. Проверка схемы на живом Postgres
показала, что вставка падает: у правила обязательны критичность и тип
проверки, а у порога их нет.

**Решение.** Таблица `domain_settings` (ключ → JSONB) для порогов,
списков и настроек. `rules` — только проверки статьи с критичностью.

**Альтернативы.** Сделать `severity` необязательным — отвергнуто:
смешение двух разных сущностей в одной таблице, и валидаторам пришлось
бы отличать правило от порога по пустому полю.

## ADR-020. Предфильтр по полям выгрузки до любых API и LLM
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Пул кандидатов на 23.09 — 1494 площадки. Аудит каждой
через краулер, SERP и LLM стоит денег и времени.

**Решение.** Массовый аудит начинается с детерминированного шага по
полям Collaborator: основной язык английский, нет пометки «реклама»,
dofollow. Затем очередь сортируется по тематикам проекта и метрикам —
сортируется, а не отсекается.

**Обоснование.** Эти условия — жёсткие правила промпта аудитора, их
проверка ничего не стоит. На пуле они убирают 646 площадок из 1494 до
первого платного вызова. Тематику сайта в фильтр не ставим: промпт
говорит, что тематика статьи важнее тематики сайта.

## ADR-021. Пользовательская документация — docs-as-code
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Нужна документация по функциям системы, которая
пополняется с каждой завершённой задачей и открывается в разделе
«Документация» интерфейса.

**Решение.** Markdown-файлы с YAML-заголовком в папке `user-docs/` того
же репозитория. Структура по Diátaxis (обучение, инструкции, справочник,
объяснения), журнал изменений по Keep a Changelog, навигация в
`mkdocs.yml`. Интерфейс рендерит те же файлы. Подробно — `15-USER-DOCS.md`.

**Обоснование.**
- Документация меняется в том же коммите, что и код: её пишет тот же
  агент, который сделал задачу, и она проходит то же ревью.
- Markdown с заголовком читают все распространённые движки: MkDocs,
  Docusaurus, VitePress и Python-библиотеки для рендера внутри Django.
  Смена движка не требует переписывать тексты.
- История правок бесплатно — это git.

**Движок.** MkDocs 1.6 + Material for MkDocs 9.7, версия MkDocs
ограничена `<2`: вышедший в 2026 году MkDocs 2.0 несовместим с Material.
Запасной путь — Zensical от авторов Material: на версии 0.0.64 собирает
наш `mkdocs.yml` без изменений (проверено 23.09.2026). Переход — когда
Zensical выйдет в 1.0.

**Альтернативы.** Вики в Notion или Confluence — отвергнуто: живёт
отдельно от кода и неизбежно отстаёт. Страницы в базе с редактором в
админке — отвергнуто: нет ревью, нет истории вместе с кодом, агенту
неудобно писать.

## ADR-022. Эмбеддинги — Voyage AI
**Дата:** 23.09.2026 · **Статус:** принято

**Контекст.** Проверка уникальности статей (E6-06) и поиск дублей фактов
(E5-03) требуют векторов текста. Независимое ревью пакета заметило, что
в конфиге был только ключ Anthropic, а своей модели эмбеддингов у
Anthropic нет — задача была нереализуема.

**Решение.** Voyage AI через API, модель `voyage-4-lite`. Для других
языков — `voyage-4`, он мультиязычный. Вызовы учитываются в `api_usage`.

**Обоснование.** Документация Anthropic по эмбеддингам прямо называет
Voyage AI. Поток — десятки статей в месяц, расход копеечный.

**Альтернативы.** Локальная модель (sentence-transformers или
открытая `voyage-4-nano`) — бесплатно, но тянет в образ PyTorch и
гигабайты зависимостей на VPS с 4 ГБ памяти. Имеет смысл, если внешний
провайдер станет проблемой; интерфейс эмбеддингов делается общим, чтобы
замена была правкой конфига.

## ADR-023. Пакеты — uv, проверки — в контейнере
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** `02-ARCHITECTURE.md` оставлял выбор «uv или poetry, на
вкус». На машине разработчика системный Python 3.10, проекту нужен 3.12.

**Решение.** Менеджер пакетов — uv, lock-файл `uv.lock`, версия Python —
`.python-version` и `requires-python = ">=3.12,<3.13"`. Тесты, линтер и
типы запускаются в контейнере `app` через `make test` и `make check`.
В контейнере окружение пакетов лежит в `/opt/venv`; `.venv` на хосте
нужен только PyCharm для подсказок.

**Обоснование.**
- uv сам ставит нужную версию Python — не надо собирать 3.12 рядом с
  системным. Один инструмент вместо pyenv + poetry, быстрый lock.
- Проверки в контейнере идут в том же окружении и с теми же переменными
  из `.env`, что и приложение: тест не пройдёт локально и не упадёт на
  сервере из-за разницы версий.

**Альтернативы.** Poetry — работает, но Python ставить отдельно и
медленнее разрешает зависимости. Проверки на хосте через `uv run` —
быстрее на запуск, но настройки Django требуют переменных окружения,
и пришлось бы дублировать их вне `.env`.

## ADR-024. Приложения в `apps/`, настройки по `DJANGO_ENV`
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** E0-02 требует деления приложений по доменам и разделения
настроек local/prod. `02-ARCHITECTURE.md` при этом говорит, что окружения
отличаются только переменными окружения.

**Решение.**
- Шесть доменных приложений лежат в пакете `apps/`: `apps.sites`,
  `apps.placements`, `apps.keywords`, `apps.content`,
  `apps.observability`, `apps.integrations`. Метка приложения (label) —
  последняя часть имени: `sites`, `placements` и т.д.
- Настройки — пакет `config/settings/`: `base.py` — общее, `local.py` и
  `prod.py` импортируют всё из base и дописывают своё. Модуль выбирает
  `DJANGO_ENV` (`local` | `prod`) через `config.env.settings_module()` в
  `manage.py`, `wsgi.py`, `asgi.py`. Значения по умолчанию нет.
- `prod.py` — минимум, который нельзя забыть: `DEBUG = False` независимо
  от `DJANGO_DEBUG`, secure-куки сессии и CSRF. HTTPS, HSTS, статика —
  E10-01, когда будет понятно устройство VPS.
- mypy и pytest работают с `config.settings.local`.

**Обоснование.**
- `apps/` держит корень чистым: там уже `config`, `docs`, `user-docs`,
  `source`, `tools`, `tests`.
- Выбор модуля переменной окружения сохраняет правило из архитектуры:
  между машинами отличается только `.env`, развилок по окружению в коде
  настроек нет.
- Без значения по умолчанию прод не может тихо стартовать с локальными
  настройками.

**Альтернативы.** Приложения в корне — короче импорты, но корень
смешивает код и документацию. Один `settings.py` с `if` по `DJANGO_ENV` —
меньше файлов, но условия расползаются по всему модулю. Отдельный
модуль настроек для тестов — пока не нужен: отличий от local нет.

**Последствия.** Метка `sites` совпадает с меткой `django.contrib.sites`.
Мы его не подключаем; если понадобится пакет, который его требует
(например, allauth), нашему приложению придётся задать другую метку до
появления миграций, после — это болезненная переделка.

## ADR-025. Логи, `run_id` и Sentry — в `config/`, stdlib `logging`
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** E0-03 вводит технические логи, `run_id` и Sentry до того,
как появились очередь (E2-01) и первые цепочки. Код нужен всем
приложениям сразу.

**Решение.**
- Код лежит в `config/`, рядом с `env.py`: `run_id.py`, `logs.py`,
  `sentry.py`. Это инфраструктура, а не домен: если положить её в
  `apps/observability`, каждое приложение импортировало бы другой
  доменный модуль. `apps/observability` — таблицы блока 6 модели данных
  и команда `observability_check`.
- Логи — stdlib `logging`, JSON — `python-json-logger`. Формат выбирает
  модуль настроек: `base.py` — JSON, `local.py` — читаемая строка.
  Фильтры `run_id` и маскировки висят на обработчике, чтобы через них
  проходили записи всех логгеров.
- Маскировка секретов — по значению (переменные окружения с секретными
  именами, от 8 символов) и по имени ключа в словарях (`api_key`,
  `password`, `token`…). Та же функция обрабатывает события Sentry в
  `before_send`.
- `run_id` внутри процесса — `ContextVar`, привязывается
  `with bind_run_id(run_id):`. Между процессами передаётся явно.
  **Для E2-01:** базовый класс задачи Celery принимает `run_id`
  аргументом (строкой — аргументы идут через JSON) и выполняет задачу
  внутри `bind_run_id`; задача, запускающая следующую, передаёт
  `current_run_id()` дальше.
- Sentry: `environment = DJANGO_ENV`, без PII и без трейсинга
  производительности, тег `run_id` на каждом событии. Пустой
  `SENTRY_DSN` — выключен. Тесты выключают Sentry принудительно
  (`init(dsn="")`: при `None` SDK берёт `SENTRY_DSN` из окружения сам).

**Альтернативы.** structlog — удобнее контекст и цепочки процессоров,
но второй способ логировать рядом с `logging`, который всё равно нужен
Django и библиотекам; для наших объёмов избыточен. Свой JSON-форматтер
без зависимости — короче, но разбор `extra` и исключений пришлось бы
писать и сопровождать самим. JSON и локально — единообразно, но логи
читаются глазами хуже; JSON-формат покрыт тестами.

**Последствия.** Секрет короче 8 символов, попавший в текст сообщения,
не маскируется по значению — только по имени ключа. Локальный пароль
базы короткий, поэтому это осознанный компромисс; прод-секреты длинные.

## ADR-026. GlitchTip до прода, sentry.io — в проде
**Дата:** 26.09.2026 · **Статус:** принято

**Контекст.** При проверке E0-03 sentry.io не открылся с машины
разработчика ни напрямую (соединение рвётся на TLS-рукопожатии), ни
через VPN-сервер (выход NEW-VPS). Открывается только через встроенный
VPN Firefox, через который WSL и Docker не ходят. Проверить доставку
ошибок локально нельзя.

**Решение.**
- До выкладки на прод ошибки принимает облачный GlitchTip
  (app.glitchtip.com, бесплатный тариф). Он принимает события от того же
  `sentry-sdk`: код не меняется, переменная остаётся `SENTRY_DSN`.
- При выкладке на прод (E10-02) — sentry.io: на прод-сервере задаётся
  DSN проекта Sentry и выполняется `manage.py observability_check
  --raise`. Если sentry.io с сервера недоступен, остаёмся на GlitchTip
  (Q15).

**Обоснование.** Смена сервиса — замена DSN в `.env`, в обе стороны.
Проверка на реальной отправке сейчас ценнее, чем удобство Sentry,
которое понадобится только в проде.

**Альтернативы.** Отложить проверку доставки до деплоя — до фазы 2
ошибки не отслеживались бы нигде. Sentry на своём сервере — Kafka,
ClickHouse, от 16 ГБ памяти, на VPS не влезает. Bugsink — лёгкий, но
рассчитан на свой сервер. Hawk.so — свой SDK, переписывать интеграцию.
Ошибки логгером сразу в Telegram — без группировки, одна ошибка в цикле
даёт сотню сообщений.

**Последствия.** История ошибок из GlitchTip в Sentry не переносится —
не нужна: ошибки важны, пока их чинят. Правила алертов и участников
проекта при переходе заводим заново. Лимит бесплатного тарифа — баг в
цикле может его исчерпать, тогда новые события до конца месяца не
принимаются; на работу приложения это не влияет.
