# 05. Контент-система (E5–E8)

Самая ценная и самая рискованная часть проекта. Заменяет копирайтеров на
потоке ~50 статей в месяц.

---

## 1. Пул знаний (E5)

### 1.1. Зачем пул, а не ресёрч под каждую статью

Три причины, третья главная:

1. **Дешевле и быстрее** — не платим за повторный поиск одних и тех же
   фактов.
2. **Не галлюцинирует** — модель берёт проверенное утверждение, а не
   придумывает цифру.
3. **Консистентность между статьями.** Если в одной статье «300+ форматов»,
   в другой «200», в третьей «более 250» — это следы штамповки и возможная
   фактическая ошибка. Единый пул гарантирует одинаковые и верные цифры
   во всех размещениях.

### 1.2. Слои пула

| Слой | Содержимое | Жизненный цикл |
|---|---|---|
| `product` | что умеет Convertio: форматы, лимиты, OCR, облачная обработка, что бесплатно | перепроверка раз в квартал |
| `domain` | WAV vs MP3, битрейт, когда нужен FLAC, H.264 vs H.265, почему GIF тяжелее MP4 | вечнозелёное, годами |
| `stat` | статистика с источником и датой | срок годности обязателен |
| `comparison` | заготовки сравнительных таблиц и структур | обновление по мере надобности |

Отдельно, не как факты:
- **анкорные конструкции** (`anchor_patterns`) — образцы предложений-носителей,
  прошедших тест на извлечение;
- **стоп-лист** — чего писать нельзя: не обещать бесплатность там, где её
  нет, не сравнивать в лоб с конкурентами, не выдумывать интеграции.
  Идёт в промпт критика, а не генератора.

### 1.3. Обязательные метаданные факта

Утверждение, развёрнутая формулировка, источник (URL + название),
дата проверки, срок годности, теги категории, статус, счётчик
использования. Плюс отдельная таблица `fact_usages`: в каких статьях
и на каких площадках факт уже засветился.

### 1.4. Наполнение пула

Не вручную с нуля. Этап ресёрча возвращает **кандидатов** в факты —
утверждение плюс источник, — а человек подтверждает или отклоняет одной
кнопкой. Десять секунд на факт вместо получаса гугления. Пул растёт сам
по ходу работы над статьями.

Побочный эффект: слой `stat` закрывает требование «1–2 ссылки на
авторитетные внешние источники» — ссылка уже привязана к факту, генератору
не нужно ничего искать.

### 1.5. Свежесть

Раз в месяц задача выбирает факты с истекающим `expires_at`, переводит их
в `pending_review` и отправляет очередь в Telegram. Без этого через год
в статьях будут цифры трёхлетней давности, и никто об этом не узнает.

## 2. Пайплайн генерации (E6)

```
Задание → Ресёрч → План статьи → Черновик → Валидаторы (код)
   → Критик (LLM) → [провал: правка, до 3 раз] → Человек → Библиотека
```

### 2.1. Задание (brief)

Формируется автоматически из данных системы:
- площадка: тематика, стиль, язык, примеры её статей;
- анкоры и целевые URL (из E3);
- количество слотов;
- требования площадки-донора;
- заданная человеком идея или угол подачи (опционально).

### 2.2. Ресёрч

Гибрид: пул закрывает 70–80% (всё повторяющееся), точечный ресёрч даёт
локальную специфику под конкретную площадку. Если статья идёт на блог про
свадебное видео — нужны примеры из этого контекста, а не общие.

Именно локальная специфика делает статью похожей на написанную под этот
сайт, а не подставленную.

Требование площадок: ТЗ прямо запрещает генерацию одним промптом и требует
проверенных фактов. Ресёрч — не опция.

### 2.3. План статьи

Отдельный шаг перед написанием: структура, подзаголовки, где какой факт,
где анкор. Проверяется на уникальность структуры относительно последних
статей ещё до генерации текста — дешевле поймать однотипность здесь.

### 2.4. Черновик

Генерация по плану, с подстановкой:
- релевантных правил из `rules`;
- top-N примеров из `examples` по тегам и весу;
- анкорных конструкций под нужный тип анкора;
- отобранных фактов с их источниками.

### 2.5. Ограничение цикла

Максимум 3 итерации правок, и только по проваленным пунктам —
не «перепиши целиком». После трёх неудач статья уходит в ручную очередь
с пометкой: скорее всего кривое задание, а не плохая генерация.

---

## 3. Валидаторы (E7, код)

Детерминированные проверки, без LLM. Быстрые, не галлюцинируют и почти
ничего не стоят: единственная платная — уникальность, ей нужен вызов
модели эмбеддингов (ADR-022).

| Проверка | Как считается |
|---|---|
| Позиция первой ссылки | смещение в символах с пробелами от начала текста |
| Позиция второй ссылки | то же |
| Количество ссылок на продукт | подсчёт по домену |
| Атрибуты rel | разбор HTML |
| Совпадение анкора с заданием | точное сравнение строк |
| Целевой URL | точное сравнение |
| Количество внутренних ссылок | домен площадки |
| Наличие внешних авторитетных ссылок | белый список доменов |
| Структура | наличие H2/H3, списков, таблиц, оглавления, изображений |
| Объём | число слов и абзацев |
| Индексируемость | meta robots, robots.txt |
| Уникальность | косинусная близость к предыдущим статьям |

Все пороги — из таблиц `rules` и `domain_settings`, не из кода. Заметность
ссылки в v1 проверяет человек: без отрисовки страницы стили не вычислить
(`04-DOMAIN-RULES.md` §3.2).

## 4. Критик (E7, LLM)

### 4.1. Правила

- **Отдельный вызов с чистым контекстом.** Не «проверь свой текст».
  Модель, которая только что написала текст, — плохой судья своему тексту.
- Критик видит только статью, задание и рубрику. Он не видит, как текст
  создавался, какие примеры подставлялись и сколько было итераций.
- Ответ строго в JSON по схеме, не свободным текстом.

### 4.2. Что оценивает

Только то, что нельзя проверить кодом:

1. **Тест на извлечение для каждой ссылки** — главный пункт, разбирается
   подробно, с пересказом предложения и вердиктом.
2. Естественность текста, признаки сырой генерации.
3. Соответствие тематике площадки.
4. Заметность ссылки в контексте абзаца.
5. Фактические противоречия внутри статьи.

### 4.3. Схема ответа

```json
{
  "verdict": "pass | revise | reject",
  "links": [
    {
      "anchor": "...",
      "extraction_test": true,
      "reason": "...",
      "suggested_fix": "..."
    }
  ],
  "issues": [
    {"rule_code": "RAW_AI_TEXT", "severity": "medium", "detail": "..."}
  ],
  "notes": "..."
}
```

## 5. Уникальность и ротация — критичное требование

При 50 статьях в месяц из одного пула главный риск — однотипность.
Это единственный сценарий, который может навредить основному бизнесу,
а не просто потратить время.

Меры, все обязательные:

1. **Ротация фактов.** Не брать факты, использованные в последних N
   статьях. Запрос по `fact_usages`.
2. **Ротация структур.** Держать несколько схем построения статьи и
   чередовать.
3. **Проверка на близость.** Эмбеддинг нового черновика против всех
   предыдущих, максимальная косинусная близость в `similarity_max`.
   Выше порога — на переработку. Порог подбирается эмпирически (Q6).
4. **Вариативность анкорных конструкций.** Не один шаблон на все статьи.
5. **Разные углы подачи** — инструкция, сравнение, разбор проблемы,
   кейс, чеклист.

## 6. Обратная связь и «обучение» (E8)

### 6.1. Что это НЕ

Не обучение модели. Не fine-tune. Веса модели не меняются и не могут
меняться от одной принятой статьи. См. ADR-005.

### 6.2. Где реально живут веса

**Уровень 1 — примеры и конструкции.** У каждой записи в `examples` и
`anchor_patterns` есть `times_used` и `times_accepted`. Вес =
сглаженная доля принятых:

```
score = (times_accepted + α) / (times_used + α + β)
```

α и β — параметры сглаживания, чтобы новый пример с одним удачным
использованием не выбивался на первое место. При сборке промпта берутся
top-N по весу среди релевантных по тегам.

Отклонённые примеры хранятся, но идут **в промпт критика** как чеклист
типовых косяков, а не в промпт генератора.

**Уровень 2 — варианты промпта.** Несколько формулировок системного
промпта, каждая с накопленной долей принятых статей. Выбор следующей —
по многорукому бандиту (Thompson sampling или UCB). Это настоящая
статистика, считается на коленке, ML-кода не требует.

Важно: сравнивать варианты честно можно только при достаточной выборке.
На 5 статьях разница между 60% и 80% — шум. Показывать доверительный
интервал, а не голое число.

### 6.3. Золотой набор

10–20 заданий с известным эталоном. Прогоняется при **каждом** изменении
промпта, правила или набора примеров. Результат — в `eval_runs`.

Без этого «улучшение» недоказуемо: через месяц кто-то «чуть-чуть поправит
промпт» и сломает то, что работало, а заметят это через десять статей.

### 6.4. Реалистичные ожидания

Первые 20–30 принятых статей дадут заметный скачок — библиотека
наполнится типовыми конструкциями. Дальше рост замедлится и упрётся в
потолок качества модели и качества правил. Это нормально и всё равно
окупается.

Метрики, по которым судим:
- доля черновиков, прошедших валидаторы с первой попытки;
- доля статей, принятых человеком без правок;
- среднее число итераций до принятия;
- себестоимость одной принятой статьи.

### 6.5. Когда думать о fine-tune

Не раньше 100+ принятых статей с разметкой. И скорее всего не
понадобится: библиотека примеров решает ту же задачу и правится за минуту,
а правила меняются каждый месяц.

---

## 7. Человек в цикле — не убирать

Полная автоматизация без проверки человеком не планируется. Одна статья
с выдуманным фактом на дорогой площадке дороже, чем все сэкономленные
часы. Цель — довести черновик до состояния «15 минут вычитки», а не
«отправить не глядя».

---

## 8. Промежуточное решение на период разработки

Пока система строится, текущую очередь статей разгребать вручную через
чат: ТЗ как промпт, чеклист как рубрика, факты собираются по ходу.
Медленнее будущей системы, но кратно быстрее копирайтеров.

Побочный эффект: каждая такая статья и вердикт по ней — готовый материал
для библиотеки примеров. Пул наполняется до появления системы.
