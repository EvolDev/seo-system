## Формат описания задачи

Каждая задача содержит одинаковый набор блоков:

- **Шапка** — размер (S до дня, M 2–4 дня, L неделя+), зависимости, фаза.
- **Зачем** — какую боль снимает. Если не сформулировано, задача под
  вопросом.
- **Что делаем** — содержание работы.
- **Детали реализации** — то, что иначе всплывёт в процессе и вызовет
  переделку.
- **Критерии приёмки** — проверяемые, не «работает хорошо».
- **Подводные камни** — известные грабли.
- **Смотри также** — ссылки на разделы других документов.

## Definition of Done — для каждой задачи

Задача закрыта, когда выполнено всё:

1. Критерии приёмки из описания задачи проверены.
2. Тесты проходят, `ruff` и `mypy` без ошибок.
3. **Документация:** страницы из раздела «Влияние на документацию» в ТЗ
   написаны или обновлены, запись в `user-docs/changelog.md` в разделе
   «[Не выпущено]» с ID задачи, `python tools/check_user_docs.py` без
   ошибок. Если в ТЗ стоит «влияния нет» — этот пункт пропускается.
4. `PROGRESS.md` обновлён; новые решения — в `08-DECISIONS.md`.

Чек-лист целиком — `docs/templates/task-close.md`.

Оценки даны для одного разработчика, работающего не полный день, с
изучением Python по ходу. Сдвиг на 30–40% нормален.

## E0. Подготовка окружения

### E0-01 · Локальное окружение
**Размер:** S · **Зависимости:** — · **Фаза:** 0

**Что делаем.** Python 3.12, менеджер пакетов с lock-файлом, Django,
Postgres и Redis в Docker Compose, ruff + mypy + pytest в конфиге.

**Детали.** mypy включить в строгом режиме с самого начала: аннотации
типов компенсируют отсутствие опыта в языке и ловят ровно те ошибки,
которые PHP-разработчик привык ловить в IDE. Ослаблять строгость позже
проще, чем вводить её на готовой кодовой базе.

**Критерии приёмки.**
- `docker compose up` поднимает пустое приложение;
- `pytest` проходит на пустом наборе тестов;
- линтер и проверка типов запускаются одной командой;
- версия Python зафиксирована, зависимости в lock-файле;
- реальные команды запуска, тестов и проверок вписаны в `CLAUDE.md`,
  раздел «Команды» — без них `/close-task` не сможет прогнать проверки.

**Смотри также:** `13-CONFIG.md` §1, ADR-002, `16-AGENT-SETUP.md`.

### E0-02 · Репозиторий и структура проекта
**Размер:** S · **Зависимости:** E0-01 · **Фаза:** 0

**Что делаем.** Git, `.env.example`, README с инструкцией запуска,
разделение конфигов local/prod, структура Django-приложений по доменным
областям.

**Детали.** Приложения делим по смыслу, а не по слоям: `sites`,
`placements`, `keywords`, `content`, `observability`, `integrations`.
Деление по слоям (всё в одном приложении) на такой системе разваливается
через пару месяцев.

Папка `docs/` из этого пакета кладётся в тот же репозиторий: документы
живут в гите и правятся вместе с кодом.

`.gitignore`, `CLAUDE.md` и `.claude/` уже есть в пакете — дополнять, а
не создавать заново. Раздел «Где что лежит» в `CLAUDE.md` обновить под
получившуюся структуру приложений.

**Критерии приёмки.**
- новый человек поднимает проект по README без вопросов;
- ни одного секрета в репозитории;
- `docs/` в репозитории, история правок ведётся.

### E0-03 · Sentry и структурированные логи
**Размер:** S · **Зависимости:** E0-01 · **Фаза:** 0

**Зачем.** Разница между «что-то упало ночью» и «вот точное место и
входные данные» — часы времени на каждом инциденте.

**Что делаем.** Подключение Sentry, JSON-логгер, генерация и проброс
`run_id`, фильтр секретов на уровне логгера.

**Детали.** `run_id` создаётся в точке входа цепочки (запуск аудита,
запуск генерации) и передаётся дальше через аргументы задач Celery.
Добавлять его ретроактивно, когда цепочки уже написаны, — долго и
муторно, поэтому делаем сразу.

**Критерии приёмки.**
- искусственное исключение долетает до Sentry с контекстом;
- ключи API в логах замаскированы (проверить намеренным логированием
  конфига);
- в логах виден `run_id`, по нему можно собрать всю цепочку.

**Смотри также:** `02-ARCHITECTURE.md` §Наблюдаемость, ADR-011, ADR-013.

### E0-04 · Каркас пользовательской документации
**Размер:** S · **Зависимости:** E0-02 · **Фаза:** 0

**Зачем.** Документация должна расти с первой задачи, а не «когда будет
время». Если каркаса нет с начала, первые двадцать функций останутся
неописанными навсегда.

**Что делаем.** Переносим в репозиторий то, что уже подготовлено в
пакете: `user-docs/`, `mkdocs.yml`, `tools/check_user_docs.py`,
`requirements-docs.txt`, шаблоны в `docs/templates/`. Подключаем
проверку в pre-commit, чтобы коммит с битой документацией не проходил.

**Детали.**
- `mkdocs serve` для локального просмотра, `mkdocs build --strict` —
  та же проверка, что будет при сборке образа.
- Проверщик сверяет ID задач со сводной таблицей этого файла, поэтому
  новые задачи сначала добавляются сюда, потом упоминаются в документации.

**Критерии приёмки.**
- `python tools/check_user_docs.py` — ноль ошибок;
- `mkdocs build --strict` собирает сайт без предупреждений;
- коммит с битой ссылкой в `user-docs/` отклоняется pre-commit.

**Смотри также:** `15-USER-DOCS.md`, ADR-021.

**Колонка «Модель»** — на какой модели Claude Code вести задачу.
`Opus` — Opus 5.5, по умолчанию. `Fable` — Fable 5.1, более сильная
модель: для задач, где ошибка дорогая и тесты её не поймают сами:
- схема и данные, от которых зависит всё дальше (E1-01, E1-02, E1-04);
- фундамент очередей: идемпотентность, `run_id`, лимиты (E2-01);
- алгоритмы с неочевидными правилами (E3-01, E8-03);
- всё, где качество определяет промпт или цепочка вызовов LLM (E4-01,
  E4-04, E5-04, E6-02…E6-04, E7-02, E7-03).

Это гипотеза, а не замер. Первая сверка — после E1-01: сколько правок
понадобилось после плана и после первого прогона тестов. По итогам
разметку пересматриваем. Переключение — `/model` между задачами, после
`/clear`. `/close-task` называет модель для следующей задачи,
`/start-task` предупреждает, если сессия идёт не на той.
