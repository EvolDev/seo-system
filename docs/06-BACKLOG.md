## Формат описания задачи

Каждая задача содержит одинаковый набор блоков:

- **Шапка** — размер (S до дня, M 2–4 дня, L неделя+), зависимости, фаза.
- **Зачем** — какую боль снимает. Если не сформулировано, задача под
  вопросом.
- **Что делаем** — содержание работы.
- **Детали реализации** — то, что иначе всплывёт в процессе и вызовет
  переделку.
- **Критерии приёмки** — проверяемые, не «работает хорошо».
- **Подводные камни** — известные грабли.
- **Смотри также** — ссылки на разделы других документов.

## Definition of Done — для каждой задачи

Задача закрыта, когда выполнено всё:

1. Критерии приёмки из описания задачи проверены.
2. Тесты проходят, `ruff` и `mypy` без ошибок.
3. **Документация:** страницы из раздела «Влияние на документацию» в ТЗ
   написаны или обновлены, запись в `user-docs/changelog.md` в разделе
   «[Не выпущено]» с ID задачи, `make docs-check` без ошибок. Если в
   ТЗ стоит «влияния нет» — этот пункт пропускается.
4. `PROGRESS.md` обновлён; новые решения — в `08-DECISIONS.md`.

Чек-лист целиком — `docs/templates/task-close.md`.

Оценки даны для одного разработчика, работающего не полный день, с
изучением Python по ходу. Сдвиг на 30–40% нормален.

**Колонка «Модель»** — на какой модели Claude Code вести задачу.
`Opus` — Opus 5.5, по умолчанию. `Fable` — Fable 5.1, более сильная
модель: для задач, где ошибка дорогая и тесты её не поймают сами:
- алгоритмы с неочевидными правилами (E3-01, E8-03);
- всё, где качество определяет промпт или цепочка вызовов LLM (E4-01,
  E4-04, E5-04, E6-02…E6-04, E7-02, E7-03).

Fable на тарифе Pro работает только на платных usage credits (в том
числе в облачных сессиях). Без них задачу с `Fable` ведём на Opus 5.5 с
усилием на ступень выше — `xhigh` вместо `high`.

**Колонка «Усилие»** — уровень `/effort` для модели из колонки «Модель»:
насколько глубоко модель рассуждает перед ответом. Чем выше, тем
тщательнее и медленнее, и тем быстрее расходуется лимит.
- `medium` — механика: интерфейс и CRUD поверх готовой логики, экспорт,
  бот, мелкая инфраструктура;
- `high` — ошибка стоит денег или данных: схема и представления,
  клиенты платных API, чекеры, прод и бэкапы, всё с моделью `Fable`;
- `xhigh` — код решает за человека и ошибка незаметна: стоп-факторы
  (E4-03), детерминированные валидаторы статьи (E7-01), пропажа ссылки,
  которая ставит стоп (E2-05);
- `max` и `ultracode` (`xhigh` плюс workflows — Claude сам запускает
  много субагентов) по умолчанию не назначаются: расход лимита
  кратно выше. Включаются на одну задачу по согласованию.

**Ревизия 04.10.2026 (после 24 сессий).** Задачи на `high` закрывались
без переделок решений; ошибки находились на стыках частей системы — их
ловят браузерные проверки и показ на копии, а не глубина рассуждений.
Поэтому два правила: задача при планировании выросла на размер — усилие
на ступень выше сразу; планирование — на ступень выше уровня из таблицы
(тонкие ошибки — в данных и в плане), код — по таблице. Переключение —
`/model` и `/effort` между задачами, после `/clear`. `/close-task` называет
модель и усилие для следующей задачи, `/start-task` предупреждает, если
сессия идёт не на той модели, и напоминает уровень усилия.
