# 02. Архитектура

## Стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык | Python 3.12+ | ADR-002 |
| Веб-фреймворк | Django 5.x | ORM + миграции + админка одним куском |
| Интерфейс v1 | Django Admin | E9 почти бесплатно, «потрогать» на второй день |
| Документация | MkDocs 1.6 + Material, `mkdocs<2` | Markdown в репозитории, ADR-021, `15-USER-DOCS.md` |
| Эмбеддинги | Voyage AI | своей модели у Anthropic нет, ADR-022 |
| Интерфейс v2 | Django + HTMX | когда админки перестанет хватать; не SPA |
| Очереди | Celery + Redis | зрелая интеграция с Django, ретраи, расписание |
| БД | PostgreSQL 16 | JSONB, оконные функции, на вырост pgvector |
| Ошибки | Sentry | единственный внешний сервис, окупающийся сразу |
| Контейнеризация | Docker Compose | один VPS, без оркестрации |
| Качество кода | ruff, mypy, pytest | компенсация отсутствия опыта в языке |
| Пакеты | uv или poetry | на вкус, главное — lock-файл |

Go остаётся в резерве ровно для одной задачи: краулер, если упрёмся в
скорость обхода. Отдельный сервис, дёргаемый из очереди. Не на старте.

## Слои системы

```
ИСТОЧНИКИ          Ahrefs API │ SERP API │ Краулер │ Collaborator │ LLM API
                        ↓          ↓         ↓           ↓           ↓
ЯДРО                        PostgreSQL — единственная точка правды
                        ↓          ↓         ↓           ↓
МОДУЛИ            Чекеры │ Подбор анкоров │ Аудит │ Контент-пайплайн
                        ↓          ↓         ↓           ↓
ВЫХОДЫ                  Django Admin │ Дашборд │ Telegram │ Экспорт
```

Ключевое правило: модули общаются только через базу и очередь. Никаких
прямых вызовов между модулями. Это позволяет разрабатывать и перезапускать
их независимо.

## Абстракция над LLM-провайдером

Обязательна с первого вызова. Один интерфейс, задача описывается по имени,
а модель и провайдер задаются конфигом.

```
LLMClient.run(task="site_audit", payload={...}, run_id=...) -> LLMResult
```

Роутинг моделей по задачам (конфиг, не код):

| Задача | Класс модели | Почему |
|---|---|---|
| Классификация тематики сайта | быстрая/дешёвая | тысячи вызовов, задача простая |
| Извлечение фактов со страницы | быстрая/дешёвая | большой объём, ошибки заметны |
| Аудит качества площадки | сильная | нужно суждение |
| Генерация статьи | сильная | это конечный продукт |
| Критик по рубрике | сильная, чистый контекст | от неё зависит, отправим ли брак |

Требования к слою:
- каждый вызов логируется в `llm_calls` (промпт-версия, токены, стоимость,
  длительность, `run_id`);
- структурированный ответ через JSON-схему, а не парсинг свободного текста;
- ретраи с экспоненциальной задержкой, отдельно — на невалидный JSON;
- таймауты и лимит стоимости на одну цепочку;
- смена модели = правка конфига, ноль изменений в коде модулей.

## Очереди и расписание

Типы задач и их характеристики:

| Задача | Периодичность | Приоритет | Идемпотентность |
|---|---|---|---|
| Проверка индексации размещения | раз в сутки до успеха, далее реже | высокий | да |
| Проверка живости ссылок | 7 дней, затем 14, затем 30 — `04-DOMAIN-RULES.md` §4 | средний | да |
| Gray scan площадки | при аудите + раз в квартал | низкий | да |
| Обновление метрик Ahrefs | раз в месяц для активных | низкий | да |
| Обновление позиций ключей | раз в неделю | средний | да |
| Генерация статьи | по требованию | высокий | нет, версионируется |
| Критик и валидаторы | следом за генерацией | высокий | да |
| Перепроверка протухших фактов | раз в месяц | низкий | да |

Правила:
- все задачи идемпотентны, кроме генерации: повторный запуск не портит данные;
- каждая задача пишет запись в `task_runs` — начало, конец, результат, ошибка;
- ретраи: 3 попытки с задержкой, затем задача помечается упавшей и попадает
  в дневную сводку;
- внешние API вызываются с ограничением скорости на уровне очереди, а не
  в коде задачи.

## Наблюдаемость

Три слоя, которые нельзя смешивать (ADR-011):

**1. Технические логи** — структурированные JSON в stdout, с `run_id`.
Для отладки конкретного вызова. Ротация 3 недели. Отдельная страница для
их просмотра не нужна — хватает grep.

**2. Доменный аудит** — таблицы `llm_calls`, `task_runs`, `api_usage`,
`checks`, `site_audits`, `validation_results`. Это не логи, а данные
системы; на них строятся решения и весь E8. Хранятся вечно, выводятся
в интерфейс.

**3. Ошибки** — Sentry, с алертом в Telegram.

**Prometheus, Grafana, Jaeger на старте не ставим.** Обоснование — ADR-012.
Если позже понадобятся графики, Grafana умеет ходить в Postgres напрямую,
без слоя метрик.

### Что показываем на дашборде

- очередь за сутки: выполнено / упало / висит;
- расходы за месяц по API с трендом;
- воронка статей: черновиков → прошло валидаторы с 1-й попытки → принято;
- просроченные проверки: площадки и ссылки, давно не проверявшиеся.

### Правила алертов

В Telegram летит только то, на что человек пойдёт и что-то сделает:
- ссылка на продукт пропала с площадки;
- расход API превысил дневной порог вдвое;
- задача упала 3 раза подряд;
- статья не прошла валидаторы после 3 циклов правок.

Успешные операции не алертят никогда. Усталость от алертов опаснее их
отсутствия.

## Внешние интеграции

### Ahrefs
API v3 — единственный официально поддерживаемый путь для программного
доступа; MCP-сервер Ahrefs запрещено дёргать из собственных скриптов.
Доступ к REST по открытым данным — с плана Advanced и выше, при этом в
справке Ahrefs встречается формулировка про Enterprise: **проверить по
своему аккаунту** (см. `09-OPEN-QUESTIONS.md`, Q2).
Тарификация в юнитах: строки × поля, минимум 50 юнитов на оплачиваемый
запрос. Массовый обход планировать, а не вызывать в цикле.

Фолбэк, если API недоступен: ручной ввод метрик через форму + импорт CSV
экспорта из интерфейса Ahrefs. Архитектурно метрики приходят в одну таблицу
независимо от способа ввода, поле `source` указывает происхождение.

### SERP (индексация и серость)
Google официального API выдачи не даёт, самостоятельный парсинг ведёт к
блокировкам. Провайдер: DataForSEO (стандартная очередь ~$0.60 за 1000
выдач, пополняемый баланс от $50) либо Serper как альтернатива.

Важные нюансы:
- Google убрал параметр `num=100` в сентябре 2025, глубокая выдача стоит
  дороже; для `site:` проверок глубина обычно не нужна;
- долю серости приходится считать по оценке Google «примерно N» — у
  сайта тысячи страниц, пролистать их нельзя. Оценка неточна, поэтому
  малые числа досчитываются точно, а значения у порогов проверяет
  человек (`04-DOMAIN-RULES.md` §1.4).

### Collaborator
Наличие API не подтверждено (Q1). До выяснения — ручной ввод статусов
через админку. Парсинг личного кабинета не делаем: хрупко и рискованно
по правилам сервиса.

### LLM
Официальные SDK Anthropic существуют для Python, TypeScript, Java, Go,
Ruby, C# и PHP (PHP в бете). Используем Python SDK через собственную
абстракцию.

### Эмбеддинги
Своей модели эмбеддингов у Anthropic нет, документация рекомендует
Voyage AI. Нужны для проверки уникальности статей (E6-06) и поиска
дублей фактов (E5-03). Модель — `voyage-4-lite`: дешёвая, а для сравнения
похожести своих же статей точности хватает. Когда появятся статьи на
других языках — `voyage-4`, он мультиязычный. Решение — ADR-022.

## Безопасность и данные

- секреты только в переменных окружения, в репозитории — `.env.example`;
- фильтр ключей на уровне логгера, чтобы токены не попадали в логи;
- ежесуточный бэкап Postgres на внешнее хранилище, проверка восстановления
  раз в квартал (бэкап, который не восстанавливали, не существует);
- никаких персональных данных в системе — работаем с публичными сайтами.

## Окружения и деплой

Два окружения: `local` (разработка) и `prod` (VPS). Между ними отличаются
только переменные окружения.

- `docker-compose.yml` — app, worker, beat, postgres, redis;
- миграции применяются скриптом деплоя, руками схему не трогаем никогда;
- деплой: `git pull` → сборка → миграции → перезапуск;
- откат: предыдущий образ + откат миграции, если она обратима.

Требования к VPS минимальные: 2 vCPU, 4 ГБ RAM, 40 ГБ диска с запасом.

## Принципы, которые не нарушаем

1. **База — единственная точка правды.** Excel становится форматом
   экспорта, а не хранения.
2. **Снапшоты вместо перезаписи.** Метрика, цена, позиция — всегда новая
   строка с датой.
3. **ORM для жизненного цикла объектов, сырой SQL для отчётов** (ADR-003).
4. **Идемпотентность фоновых задач.**
5. **run_id протягивается через всю цепочку** с первой задачи. Добавлять
   ретроактивно больно.
6. **Ничего не удаляем физически** — мягкое удаление флагом или статус
   отмены. В админке удаление доменных объектов отключено: каскады в
   схеме остаются как защита целостности, но наружу не выставляются.
   История решений ценнее чистоты таблиц.
