# 15. Пользовательская документация

Документация **продукта** — что умеет система и как ей пользоваться.
Она растёт вместе с системой: каждая завершённая задача добавляет или
обновляет страницы. Читается в разделе «Документация» интерфейса.

Не путать с проектной документацией в `docs/` — та описывает, **как
строить** систему, и адресована разработчику и агенту. Пользовательская
лежит в `user-docs/` и описывает, **как работать** с тем, что построено.

Решение и альтернативы — ADR-021.

---

## 1. Принципы

1. **Docs-as-code.** Страницы — Markdown-файлы в том же репозитории, что
   и код. Функция и её описание попадают в один коммит.
2. **Один формат — любой движок.** Markdown с YAML-заголовком читают
   MkDocs, Docusaurus, VitePress и Python-рендеры внутри Django. Сменить
   движок можно, не переписывая тексты.
3. **Описываем только то, что работает.** Функция не выкачена — её
   страница помечена черновиком или не существует.
4. **Документацию пишет тот, кто сделал задачу.** Агент в конце задачи
   видит код, тесты и ТЗ — лучшего момента не будет. Человек проверяет.
5. **Проверка автоматическая.** Скрипт `tools/check_user_docs.py` ловит
   битые ссылки, пропущенные поля, ссылки на несуществующие задачи и
   страницы вне навигации. Без зелёной проверки задача не закрыта.

---

## 2. Структура — Diátaxis

Стандарт де-факто для технической документации: четыре вида страниц под
четыре разные потребности читателя. Смешивать их внутри одной страницы
нельзя — это главная причина, почему документацию «невозможно читать».

| Раздел | Папка | Отвечает на вопрос | Пример |
|---|---|---|---|
| Начало работы | `getting-started/` | «Я здесь впервые, с чего начать?» | Первый день: от импорта до первой проверки |
| Инструкции | `how-to/` | «Как сделать конкретную вещь?» | Как проверить индексацию статьи |
| Справочник | `reference/` | «Что означает это поле или статус?» | Статусы площадок и размещений |
| Как это устроено | `explanation/` | «Почему система решила именно так?» | Как система оценивает площадку |

Плюс две служебные страницы в корне:
- `index.md` — главная раздела;
- `changelog.md` — журнал изменений.

Каждая папка раздела содержит `index.md` — вводную страницу раздела.

## 3. Формат страницы

### 3.1. Имя файла

`kebab-case` латиницей, по действию или объекту: `check-indexation.md`,
`site-statuses.md`. Имя файла становится адресом страницы
(`/docs/how-to/check-indexation/`), поэтому после публикации его не
меняют — иначе сломаются ссылки из интерфейса.

### 3.2. Заголовок страницы (front matter)

```yaml
---
title: Проверка индексации статьи
description: Как система проверяет, попала ли статья в индекс Google, и что делать, если нет.
section: how-to
status: current
tasks: [E2-03]
updated: 2026-10-05
since: 2026.10.05
screens: [placement_card]
tags: [проверки, индексация]
---
```

| Поле | Обязательно | Значения | Зачем |
|---|---|---|---|
| `title` | да | строка | заголовок в навигации и на странице |
| `description` | да | одно предложение | поиск, карточки, подсказки |
| `section` | да | `getting-started`, `how-to`, `reference`, `explanation`, `root` | должно совпадать с папкой |
| `status` | да | `draft`, `current`, `deprecated` | черновик виден с плашкой, устаревшее — с предупреждением |
| `tasks` | да | список ID из бэклога, может быть `[]` | связь страницы с задачами — по ней видно, какие страницы задела задача |
| `updated` | да | `ГГГГ-ММ-ДД` | дата последней содержательной правки |
| `since` | для `current` | версия деплоя `ГГГГ.ММ.ДД` | с какой версии функция доступна |
| `screens` | нет | идентификаторы экранов | контекстная справка: кнопка «?» на экране ведёт сюда |
| `tags` | нет | список | поиск и группировка |

Material for MkDocs понимает `title`, `description` и `tags` без
настроек; остальные поля движки молча игнорируют, а читают наш проверщик
и раздел «Документация» в интерфейсе.

### 3.4. Идентификаторы экранов для `screens`

Кнопка «?» на экране ищет страницы по этим идентификаторам. Новый экран —
новая строка здесь, в том же коммите.

| Идентификатор | Экран | Задача |
|---|---|---|
| `site_list` | список площадок | E9-01 |
| `placement_card` | карточка размещения | E9-01 |
| `site_card` | карточка площадки | E9-02 |
| `decision_queue` | очередь ручных решений | E9-05 |
| `audit_queue` | очередь массового аудита | E4-05 |
| `article_editor` | редактор статьи | E9-06 |
| `dashboard` | дашборд | E9-03 |

### 3.3. Текст

- **Повелительное наклонение** в инструкциях: «Откройте карточку
  площадки», а не «Пользователь открывает карточку».
- **Одна инструкция — одна задача.** Два разных действия — две страницы.
- **Сначала результат, потом шаги.** Первый абзац отвечает на вопрос
  «что я получу».
- **Названия элементов интерфейса — жирным и дословно**, как на экране:
  **Проверить индексацию**.
- **Без внутренней кухни.** Таблицы базы, имена функций, очереди Celery —
  в проектную документацию. Пользователю важно «проверка занимает до пяти
  минут», а не «задача уходит в стандартную очередь DataForSEO».
- **Числа из настроек — только на одной странице.** Пороги живут в
  таблицах `rules` и `domain_settings` и меняются без деплоя; если
  повторять их по всей документации, при первой же правке страницы
  начнут врать. Поэтому все такие числа собраны на
  `reference/thresholds.md`, а остальные страницы пишут качественно («за
  верхней границей зоны серость — по сути отказ») и ссылаются туда.
  Правка настроек = правка этой страницы в том же коммите.
- Предупреждения — блоком `!!! warning`, советы — `!!! tip`.

Шаблоны всех четырёх видов страниц — `docs/templates/`.

## 4. Журнал изменений

Формат **Keep a Changelog**: сверху раздел «[Не выпущено]» (в оригинале
стандарта — `[Unreleased]`, у нас по-русски, как весь интерфейс), ниже —
выкаченные версии, новые сверху. Внутри версии — группы:

- **Добавлено** — новые функции;
- **Изменено** — изменения в поведении существующих;
- **Исправлено** — баги;
- **Удалено** — убранные функции.

Правила записи:
- одна строка — одно изменение, с точки зрения пользователя;
- в конце строки — ID задачи и ссылка на страницу, если она есть:
  `Проверка индексации опубликованных статей по расписанию (E2-03,
  [инструкция](how-to/check-indexation.md)).`;
- внутренние изменения, которых пользователь не заметит (рефакторинг,
  миграции без видимого эффекта), в журнал **не пишутся**.

**Версии — по дате деплоя** (`2026.10.05`). Для внутреннего инструмента
с непрерывной выкаткой это проще семантических версий и сразу отвечает
на вопрос «когда это появилось». При деплое раздел «[Не выпущено]»
переименовывается в версию с датой, и над ним создаётся новый пустой.

## 5. Процесс — как документация растёт с каждой задачей

### 5.1. В ТЗ задачи

Шаблон ТЗ (`docs/templates/spec.md`) содержит обязательный раздел
«Влияние на документацию» с одним из трёх ответов:

- **нет** — задача не меняет того, что видит пользователь (схема,
  инфраструктура, рефакторинг);
- **обновить** — список существующих страниц;
- **создать** — список новых страниц с разделом и названием.

Решение принимается **до** кода, а не после: так документация не
становится тем, что «потом допишем».

### 5.2. При закрытии задачи

Чек-лист `docs/templates/task-close.md`, пункты про документацию:

1. Страницы из раздела «Влияние на документацию» написаны или обновлены.
2. У каждой затронутой страницы в `tasks` есть ID задачи, `updated` —
   сегодняшняя дата, `status` соответствует реальности.
3. В `changelog.md` в разделе «[Не выпущено]» — строка с ID задачи.
4. Новые страницы добавлены в `nav` в `mkdocs.yml`.
5. `python tools/check_user_docs.py` — без ошибок.

### 5.3. Жизненный цикл страницы

```
draft ──(функция выкачена)──▶ current ──(функция убрана/заменена)──▶ deprecated
```

`draft` допустим для объяснений, написанных заранее, — например, как
система оценивает площадку. Правила согласованы, кода ещё нет. После
выкатки E4 страница становится `current`.

`deprecated` страницу не удаляют сразу: в интерфейсе она видна с
предупреждением и ссылкой на замену ещё одну версию.

### 5.4. Связь с памятью проекта

Закрытие задачи обновляет три слоя памяти, и у каждого свой читатель:

| Что | Для кого | Файл |
|---|---|---|
| Состояние проекта | агент и разработчик в следующей сессии | `PROGRESS.md` |
| Принятые решения | будущий «почему так» | `docs/08-DECISIONS.md` |
| Что умеет система | пользователи в интерфейсе | `user-docs/` + `changelog.md` |

## 6. Как документация попадает в интерфейс

### 6.1. v1 — MkDocs как готовый движок (E9-07)

Самый дешёвый путь с поиском, навигацией и темой из коробки, без своего
рендера:

1. `mkdocs.yml` в корне репозитория описывает навигацию и расширения.
2. При сборке Docker-образа: `mkdocs build --strict` → статические файлы
   в `site/`. Флаг `--strict` роняет сборку на битой ссылке — сломанная
   документация не доедет до продакшена. **Только после неё** —
   `tools/check_user_docs.py --screens-out site/screens.json`: сборка
   очищает `site/` и стёрла бы карту экранов, если бы шла второй.
3. Django отдаёт `site/` по адресу `/docs/` **через view с
   `login_required`**. Не через WhiteNoise: он отдаёт статику всем без
   авторизации, а документация внутренняя.
4. В меню админки — пункт «Документация».
5. Контекстная справка: `site/screens.json` — карта «экран → страница»
   из поля `screens`. Кнопка «?» на экране открывает нужную страницу.
6. «Что нового» на дашборде: верхний раздел `changelog.md`.

Локальный просмотр для разработки: `mkdocs serve`, страницы
пересобираются при сохранении.

**Про версии движка — важно.** В феврале 2026 вышел MkDocs 2.0: он
переписан с нуля, без плагинов, с другим форматом конфига и несовместим с
Material for MkDocs. Поэтому:

- в `requirements-docs.txt` жёстко `mkdocs<2`; Material с версии 9.7.5
  сам ограничивает MkDocs тем же;
- команда Material рекомендует свой новый движок **Zensical** как замену
  MkDocs 1.x. Проверено 23.09.2026 на версии 0.0.64: наш `mkdocs.yml` и
  все страницы собираются без единой правки, строгий режим так же падает
  на битой ссылке. Лицензия MIT;
- пока Zensical не дошёл до 1.0, остаёмся на MkDocs 1.6 + Material 9.7.
  Переход — замена одной команды сборки: тексты, заголовки страниц и
  навигация не меняются.

Проверено в песочнице: `mkdocs build --strict` и `zensical build -s`
падают на битой ссылке, `tools/check_user_docs.py` тоже.

### 6.2. v2 — свой рендер внутри интерфейса, если понадобится

Если документация должна выглядеть частью интерфейса, а не отдельным
сайтом: Django читает те же файлы, парсит заголовок (`python-frontmatter`),
рендерит Markdown (`markdown` + `pymdown-extensions` с теми же
расширениями, что в `mkdocs.yml`, — тогда вывод совпадает), навигацию
берёт из `mkdocs.yml`, поиск — полнотекстовый в Postgres по
`to_tsvector('russian', …)`.

Тексты при этом не меняются — ради этого и выбран общий формат.
