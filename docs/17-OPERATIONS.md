# 17. Эксплуатация прода: пульт, выкладка, бэкапы, восстановление, вход с кодом

Инструкция для администратора (ADR-081). Пользователям — справка
`user-docs/reference/backups.md`. Настройка нового сервера — шаг 4 плана в
`PROGRESS.md` (пополнит этот документ).

**Адрес системы** — `https://<адрес>/<SITE_PATH>/` (ADR-081): админка — в корне
секретного пути, справка — `/<путь>/docs/`. На любой другой адрес — главную,
`/admin`, `/wp-admin` — Caddy обрывает соединение без ответа (как 444 в nginx),
сервер не выдаёт даже, что на нём за система. Путь знают только свои: в закладки,
публично не выкладывать. Сменить — `SITE_PATH` в `.env`, «Службы → Перезапустить
всё»; людям — новые закладки, войти заново.

---

## 1. Пульт

Всё по серверу — из меню в терминале `deploy/seo`: стрелки, Enter, Esc — назад.

| Где | Команда | Что в меню |
|---|---|---|
| Сервер | `seo` (ссылка на `deploy/seo`, метка `.seo-server`) | состояние, обновить, откатить, службы, журналы, бэкапы, восстановление, ручные команды, обслуживание |
| Локальная версия | `make ops` | копия локальной базы, меню сервера по SSH, тестовая копия прода |
| Тестовая копия прода | `SEO_REHEARSAL_ENV=<путь> deploy/seo rehearsal` | то же, что на сервере |

Каждое действие пишет журнал в `deploy/logs/` (в git не идёт), выкладки — строкой
в `deploy/logs/history`. Опасные пункты (откат базы, восстановление,
перезагрузка) просят вписать слово; обычные — «Да / Нет».

Любое действие — и без меню: `deploy/seo server --run <действие> [--yes]`
(список — в начале `deploy/seo`), время для восстановления — `SEO_WHEN="2026-11-20
14:05"`. Так пульт проверяется на тестовой копии.

**Меню сервера по SSH** из локальной версии читает `deploy/ops.local.conf`
(в git не идёт):

```bash
SEO_SSH=seo@203.0.113.10
SEO_SERVER_DIR=/srv/seo-system
```

**Копия локальной базы** — `pg_dump` в `backups/<дата>-local.dump`: базу только
читает, работать можно. Пункт «Удалить старые копии» оставляет десять последних.
Вернуть копию в рабочую базу пульт не умеет нарочно — только вместе с
разработчиком.

## 2. Выкладка и откат (E10-02)

**Обновить до новой версии** берёт `main` из git:

1. снимок базы в `backups/<дата>-before-<версия>.dump` (пять последних);
2. код — перемоткой (`git merge --ff-only`); не перематывается — отказ;
3. сборка образа приложения с меткой версии (`seo-system-prod:<коммит>`) и
   образа базы (`seo-system-postgres:latest` — меняется только с
   `deploy/postgres/`, выкладка версии базу не перезапускает);
4. миграции: список и `sqlmigrate` каждой — в журнал выкладки, затем `migrate`;
5. перезапуск приложения, воркера, beat;
6. проверка: контейнер приложения здоров и `/<путь>/healthz` через Caddy
   отвечает «ok» — до 3 минут.

Сборка или миграции не прошли — код возвращается, работает прежняя версия. Сайт
после перезапуска не открылся — пульт сам возвращает прежний образ и код;
миграции новой версии остаются в базе (обычно прежней не мешают), журнал
говорит, какие.

**Откатить на прошлую версию** — к версии до последней выкладки: снимок базы,
миграции, которых в прошлой версии не было, — назад кодом текущей версии (он
знает, как их отменить), затем прошлый код и образ. Необратимая миграция —
откат останавливается, работает текущая версия.

Необратимые миграции (удаление колонок) — в два шага с паузой в выкладку: сначала
код перестаёт пользоваться колонкой, следующей выкладкой — удаление.

На тестовой копии 09.11.2026: обновление с миграцией — 28 и 94 с; обновление,
которое меняет сам пульт, — без сбоев (пульт читается целиком до начала работы);
версия, у которой падают миграции, — отказ за 17 с; версия, у которой не
открывается сайт, — сама вернулась прежняя за 5 мин; откат с отменой миграции —
24 с.

## 3. Бэкапы

Как устроено: база сама отправляет каждое изменение в архив Backblaze B2
(WAL-G, `archive_command`), контейнер `backup` делает остальное по расписанию
(`deploy/backup/crontab`) и пишет каждую копию и проверку строкой
`backup_runs` — «Служебное → Бэкапы». Приложение раз в час проверяет, что всё
свежее (`system_health`), беда — событие GlitchTip и письмо.

| Что | Когда | Куда |
|---|---|---|
| Архив изменений базы (WAL) | не позже минуты после изменения | B2, `wal-g/` |
| Полный снимок базы | 03:00 каждый день | B2, `wal-g/` |
| Ночной дамп базы и файлы загрузок | 03:30 каждый день | B2 и, если включено, R2, `files/` |
| Проверка восстановления | воскресенье 04:30 | временные базы в контейнере |

Проверка восстановления B2 — база из архива на минуту перед проверкой и
ночной дамп во временную базу, оба сверяются по числу строк каждой таблицы,
архив файлов загрузок читается целиком. R2 — то же для его ночного дампа.

Время — по `TIME_ZONE`. При первом запуске сервера снимок, ночная копия и
проверка делаются сразу. Вручную — пульт, «Бэкапы»: копия сейчас (например,
перед большой загрузкой), полный снимок сейчас, проверка восстановления сейчас,
последние бэкапы.

### Ключи — в менеджер паролей

Без двух ключей шифрования копии не прочитать никому, в том числе нам.
Потерять ключ — потерять все копии.

| Ключ | Как получить |
|---|---|
| `BACKUP_WALG_KEY` | `openssl rand -hex 32` — 64 знака |
| `BACKUP_FILES_PASSWORD` | `openssl rand -base64 32` |

В менеджер паролей кладётся весь `.env` сервера целиком: ключи шифрования,
ключи доступа к хранилищам, пароль базы, ключи API. С ним сервер поднимается
у любого провайдера (раздел 4).

### Хранилища — один раз

Обе корзины — частные, хранение 30 дней, удаление с сервера невозможно.
Точные названия пунктов меню у провайдеров сверяем на месте при настройке.

**Backblaze B2** — архив, полные снимки, ночная копия:

- корзина в регионе EU, Private, с **Object Lock**: режим Governance, срок
  по умолчанию 30 дней — файлы нельзя удалить или подменить 30 дней;
- правило жизненного цикла: удалять файлы через 35 дней после загрузки;
- ключ приложения — только для этой корзины, чтение и запись; удалить старые
  копии он не сможет из-за Object Lock;
- в `.env`: `B2_ENDPOINT=https://s3.<регион>.backblazeb2.com`,
  `B2_REGION=<регион>`, `B2_BUCKET`, `B2_KEY_ID`, `B2_APPLICATION_KEY`.

**Cloudflare R2** — вторая ночная копия у другой компании. На старте её нет
(решение 12.11.2026, ADR-081): `BACKUP_R2_ENABLED=false`, копия и проверка —
только в B2, проверка здоровья R2 не ждёт. Включить позже — корзина по списку
ниже, ключи и `BACKUP_R2_ENABLED=true` в `.env`, затем пульт «Службы →
Перезапустить всё» или `docker compose -f compose.prod.yaml up -d backup`: при
запуске контейнер `backup` видит, что в R2 ещё нет копии и проверки, и делает
их сразу (на тестовой копии — за минуту), в «Служебное → Бэкапы» появляются
строки R2.

- корзина с юрисдикцией EU;
- правило жизненного цикла: удалять объекты через 35 дней;
- блокировка корзины (bucket lock): 30 дней;
- токен API: Object Read & Write только для этой корзины;
- в `.env`: `R2_ENDPOINT=https://<номер аккаунта>.eu.r2.cloudflarestorage.com`,
  `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`.

Включение на сервере — в `.env`: `PG_ARCHIVE_MODE=on`, `BACKUP_MONITOR=true`,
переменные хранилищ и ключи (`.env.example`, «Бэкапы»). Через несколько минут
после запуска в «Служебное → Бэкапы» — полный снимок, дамп и файлы в оба
хранилища и две проверки, все «✓ Готово».

## 4. Восстановление

Пульт, «Восстановление». Скрипты (`deploy/backup/`) пишут только в пустую папку
`/restore` или `/scratch/…` и никогда — в папку живой базы.

**Копия базы на минуту** — посмотреть и достать удалённое или испорченное, не
трогая работу остальных. Копия поднимается рядом с живой базой (временный сервер
в контейнере `backup`, без сети); пульт предложит открыть её консоль и убрать
после. Нужные строки переносятся в живую базу запросом. Перед копией пульт
досылает в архив изменения до текущей минуты — иначе последних минут в нём ещё
нет. На тестовой копии — 25 с.

**Откатить всю базу на минуту** — работа всех после этой минуты пропадёт из базы
(останется в архиве и в снимке перед откатом). Порядок: снимок базы, изменения —
в архив, остановка, копия тома базы как есть (`<проект>_pgdata_before_<дата>`),
база из архива на эту минуту, запуск. Не вышло — прежний том возвращается сам.
Копию тома после проверки удалить: «Обслуживание». На тестовой копии — 45 с,
удалённая заметка вернулась.

**Восстановление после аварии — новый сервер.** Только на пустом томе базы
(пульт проверяет):

1. Новый сервер у любого провайдера, Docker, папка проекта из git, `.env` — из
   менеджера паролей.
2. Пульт: «Восстановление → Восстановление после аварии»: сборка образов, база из
   архива B2 (до последнего изменения или на минуту) и файлы загрузок из ночной
   копии (R2, если включён, иначе B2) — в пустые тома, запуск, проверка `/healthz`.
   Шаг не удался — пульт останавливается и систему не запускает.
3. Запись DNS домена — на адрес нового сервера.

Старый сервер, если оживёт, не включать: оба писали бы в один архив. На
тестовой копии с пустыми томами — 51 064 площадки, 734 размещения, 90 файлов,
всё совпало.

Без пульта — то же командами (`C="docker compose -f compose.prod.yaml"`, тома
`seo_pgdata`, `seo_uploads`):

```bash
$C build
$C run --rm --no-deps -v seo_pgdata:/restore \
    --entrypoint /usr/local/lib/seo-backup/restore.sh backup /restore ["2026-11-20 14:05"]
$C run --rm --no-deps -v seo_uploads:/restore \
    --entrypoint /usr/local/lib/seo-backup/restore-files.sh backup /restore
$C up -d
```

## 5. Пришло оповещение

| Сообщение | Что значит | Что делать |
|---|---|---|
| «Изменения базы не уходят в архив B2» | B2 недоступен или ключ не работает | файлы журнала ждут на диске; проверить ключ и доступ к B2; пульт — «Журналы служб → База» |
| «…: последняя попытка … не удалась — …» | упал снимок, дамп, файлы или проверка | причина — в сообщении и «Журналы служб → Бэкапы»; повторить: «Бэкапы» |
| «…: последний удачный — …» | копия давно не делалась | «Состояние системы»: работает ли backup |
| «Диск сервера занят на N %» | место кончается | «Обслуживание → Удалить старые образы»; затем тариф больше |

## 6. Вход с кодом

На сервере после пароля — шесть цифр из Google Authenticator или запасной код
(`config/otp.py`, ADR-081). Включён в проде сам (`LOGIN_OTP_REQUIRED`, по
умолчанию `true` в `config/settings/prod.py`), в локальной версии выключен.
Первый вход человека — привязка телефона: QR-код, проверочный код, десять
запасных кодов один раз. Подтверждение живёт в сессии — 14 дней от последнего
захода.

- **Человек потерял телефон** — «Настройки → Пользователи», его карточка,
  «Сбросить Authenticator», «Сохранить». При следующем заходе он привяжет новый
  телефон; его открытые сессии сразу просят код заново. Кто привязал телефон —
  колонка «Телефон для кода» в списке.
- **Администратор потерял телефон и запасные коды**, а другого администратора
  нет — одноразовый код с сервера: пульт, «Ручные команды → Команда manage.py»,
  `addstatictoken <логин>` (печатает код). Войти с ним, в своей карточке —
  «Сбросить Authenticator», привязать новый телефон.
- **Неверные коды подряд** тормозят: следующая попытка через 1, 2, 4, 8… секунд,
  страница говорит, сколько ждать. Сбрасывает удачный код или сброс
  администратором.
- **Выключить вход с кодом у всех** — только в крайнем случае:
  `LOGIN_OTP_REQUIRED=false` в `.env`, «Службы → Перезапустить приложение».
  Телефоны и коды остаются, включение возвращает всё как было.

## 7. Тестовая копия прода в локальной версии

Хранилища подменяет эмулятор S3 (`deploy/compose.rehearsal.yaml`), ключи
настоящих хранилищ не нужны. Рабочая база локальной версии только читается
(`pg_dump`). Все проверки выкладки, бэкапов и восстановления — только здесь, на
временных базах и одноразовых серверах.

```bash
export SEO_REHEARSAL_ENV=<путь>/rehearsal.env
C="docker compose -p seo-rehearsal -f compose.prod.yaml -f deploy/compose.rehearsal.yaml \
    --env-file $SEO_REHEARSAL_ENV"
docker build -t seo-system-postgres:latest -f deploy/postgres/Dockerfile deploy
$C up -d --no-build
deploy/seo rehearsal        # пульт на тестовой копии
$C down -v                  # убрать копию вместе с томами
```
