# E9. Интерфейс

**Цель эпика.** Дать людям экран, с которого работают, вместо
33 колонок Excel. Начинаем с админки Django — она даёт рабочий
интерфейс на второй день (ADR-014).

**Зависит от:** E1 · **Блокирует:** E3-04, E5-03, E8-01

**Принцип:** никакого SPA. Когда админки перестанет хватать —
Django + HTMX, не React. Для инструмента на двоих этого хватит надолго.

## E9-01 · Django Admin как база
**Размер:** S · **Зависимости:** E1-01 · **Фаза:** 1

**Зачем.** Первое «потрогать руками». Часть первого вертикального
среза.

**Что делаем.** Регистрация моделей, списки с фильтрами и сортировками,
поиск.

**Детали реализации.**
- Фильтры, которые нужны сразу: статус, DR (диапазоны), трафик
  (диапазоны), язык, «пишем мы» (`we_write` из `v_product_site_latest`),
  наличие размещений. Статус и «пишем мы» — для выбранного продукта
  (ADR-030).
- В списке площадок показывать последние значения метрик через
  аннотацию из представления, а не подзапросом на каждую строку —
  иначе получится N+1 на полутора тысячах строк.
- Поиск по домену с нормализацией ввода: человек вставит URL целиком.
- `list_select_related` и `prefetch_related` настроить сразу.
- Список площадок продукта строится поверх `v_product_site_latest` —
  там уже статус под продукт, последние метрики, цены и признак
  «пишем мы».
- Рабочие списки (ADR-033, с E1-04): фильтр по списку и фильтр «уже
  работали / новые для нас» по выбранному продукту — статус не «Новая»,
  был аудит или его размещение. Статья другого продукта (Clideo) «уже
  работали» не делает — показывать её ссылкой. Какой список открыт по
  умолчанию — решить здесь.
- Удаление доменных объектов в админке отключено
  (`has_delete_permission`): ничего не удаляем физически, отмена —
  статусами.

**Критерии приёмки.**
- все площадки видны и фильтруются — после импорта это около 2000;
- страница списка выполняет не больше 10 запросов (проверить
  django-debug-toolbar);
- поиск находит площадку по вставленному полному URL.

**Подводные камни.** Админка по умолчанию делает N+1 на связанных
полях. При двух тысячах строк это заметно сразу — и это хороший учебный
момент по ADR-003.

**Смотри также:** ADR-003, ADR-014, `07-ROADMAP.md` §Фаза 1.

## E9-02 · Карточка площадки
**Размер:** M · **Зависимости:** E9-01, E1-05 · **Фаза:** 3

**Зачем.** Главный экран системы. Для принятия решения не должно
требоваться ничего, кроме него.

**Что делаем.** Единый экран: метрики с историей, цены, серость,
история аудитов, размещения, ссылки и их живость, кандидаты в анкоры,
кнопки действий.

**Детали реализации.**
- Метрики — с графиком динамики, а не только последним значением.
  Тренд трафика входит в правила оценки. В графиках — только доверенные
  источники (ADR-043): Ahrefs и продавцы с флажком «метрикам доверяем».
- Значок графика рядом с DR, трафиком и рабочей ценой в «Площадках» и в
  карточке: окошко с графиком изменений, при наведении — значение, дата,
  источник; под графиком — «таблицей». Как выглядит — прототип
  `docs/prototypes/price-review.html`. Цвета — проверенные валидатором
  dataviz (ADR-038).
- Серость — доля с разбивкой по категориям и примерами URL.
- История аудитов: все вердикты, а не последний. Видно, менялось ли
  мнение.
- Блок размещений — по всем продуктам, включая Clideo, с продавцом и
  сотрудником (E1-09).
- Блоки «Предложения продавцов» (рабочая цена, цены с историей, пометки
  «дешевле» и «новая цена») и «Заметки» (история, добавить) — ADR-041,
  ADR-043; окно карточки делает E1-07, здесь — полный экран.
- Кнопки: запустить аудит, подобрать анкоры, проверить индексацию,
  проверить ссылки, добавить в очередь размещений.
- Долгие действия уходят в очередь и показывают статус, а не вешают
  страницу.

**Критерии приёмки.**
- решение по площадке принимается без открытия других экранов;
- график динамики трафика отображается;
- запуск аудита с карточки работает и показывает прогресс;
- кнопка «?» ведёт на страницу документации с `screens: [site_card]`.

**Смотри также:** `04-DOMAIN-RULES.md` §1, `E4-SITE-AUDIT.md`, ADR-043.

## E9-03 · Дашборд
**Размер:** M · **Зависимости:** E1-03, E2-08 · **Фаза:** 5

**Что делаем.** Четыре блока: очередь за сутки, расходы за месяц,
воронка статей, просроченные проверки.

**Детали реализации.**
- Данные из представлений, не из ORM-агрегаций (ADR-003).
- Расходы с разбивкой по провайдерам и трендом.
- Воронка статей: черновиков → прошло валидаторы с первой попытки →
  принято.
- Просроченные проверки с приоритетом и ссылками на сущности.
- Сюда же выводятся метрики качества из E8-05.
- Очередь за сутки — по `task_runs`: строка — запуск задачи, а не попытка
  (ADR-039). «Висит» — «Выполняется» дольше часа: процесс воркера убит
  посреди задачи. Пульс очереди (`heartbeat`, раз в час) в счётчики
  «выполнено» не включать — он для проверки, что очередь жива.
- Если на дашборде статусы площадок (воронка `v_site_funnel`) — цвета
  девяти статусов (ADR-047) подобрать валидатором dataviz под все
  расцветки, как цвета графиков (ADR-038): путь в работу — одной гаммой
  по нарастанию, отказы и чёрный список — отдельно.

**Критерии приёмки.**
- дашборд отвечает на вопрос «что сегодня не так» за десять секунд;
- страница грузится меньше секунды на реальных данных.

**Смотри также:** `02-ARCHITECTURE.md` §Что показываем на дашборде;
ADR-038 — цвета графиков под расцветки админки (проверены, «Ahrefs —
тёмную» проверить здесь), главная админки уже с карточками «Работы».

## E9-04 · Telegram-бот
**Размер:** S · **Зависимости:** E2-01 · **Фаза:** 2

**Зачем.** Алерты должны приходить туда, где их прочитают, а не на
страницу, которую надо открыть.

**Что делаем.** Алерты по правилам из `02-ARCHITECTURE.md` плюс
утренняя сводка.

**Детали реализации.**
- **Правило одно:** летит только то, на что человек пойдёт и что-то
  сделает. Пропала ссылка — да. Расход превысил порог вдвое — да.
  Задача упала трижды — да. «Проверка выполнена успешно» — никогда.
- «Задача упала трижды» — строки «Ошибка» в `task_runs`: их ставит
  базовый класс задачи после третьей неудачи (ADR-039). До E9-04 об
  этом приходит письмо GlitchTip.
- «Статья не в индексе дольше срока» — строки `checks` проверки
  индексации с пометкой `result.alert` (E2-03, ADR-042), одним сообщением
  за день. До E9-04 их собирает сводка `indexation_alerts` в событие
  GlitchTip — её заменить или оставить как запасной путь.
- Усталость от алертов убивает наблюдаемость надёжнее, чем её
  отсутствие. Если в канал сыплется всё подряд, через две недели его
  перестают читать, и настоящая авария проходит мимо.
- Сводка — счётчики, а не простыня.
- Группировка: 12 пропавших ссылок — одно сообщение, не двенадцать.

**Критерии приёмки.**
- приходят только алерты из списка;
- за неделю работы в канале не больше 10–15 сообщений;
- каждое сообщение содержит ссылку на соответствующий экран.

**Смотри также:** `02-ARCHITECTURE.md` §Правила алертов.

## E9-05 · Очередь ручных решений
**Размер:** M · **Зависимости:** E9-02 · **Фаза:** 3

**Зачем.** Единая точка входа в рабочий день. Всё, что ждёт человека,
в одном списке.

**Что делаем.** Список: пограничные аудиты, статьи на вычитку,
кандидаты в факты, открытые вопросы по слотам, статьи после трёх
неудачных итераций.

**Детали реализации.**
- Сортировка по приоритету и сроку: статья, которую ждёт площадка,
  важнее кандидата в факты.
- Каждый элемент решается в один-два клика, без перехода в другие
  разделы, где это возможно.
- Счётчик в шапке: сколько всего ждёт.

**Критерии приёмки.**
- рабочий день начинается с этого экрана;
- элемент можно решить, не покидая список, где это применимо.

## E9-06 · Редактор статьи
**Размер:** M · **Зависимости:** E7-03 · **Фаза:** 4b

**Зачем.** Вычитка 50 статей в месяц — 12–17 часов. Удобство редактора
напрямую влияет на эту цифру.

**Что делаем.** Просмотр черновика с подсветкой ссылок, позиций и
результатов валидаторов, правка руками перед отправкой.

**Детали реализации.**
- Подсветка: где ссылки, на каком символе, какие проверки провалены.
- Рядом с каждым провалом — цитата места и предложение критика, что
  исправить.
- Правка человека сохраняется как новая версия и становится сигналом
  для E8: статья была почти хорошей.
- Кнопки вердикта (E8-01) здесь же.
- Сравнение версий: что изменилось между итерациями.

**Критерии приёмки.**
- человек правит статью, не выходя в другой редактор;
- видно, какие проверки провалены и где именно;
- правка сохраняется как версия, вердикт фиксируется.

**Смотри также:** `E7-VALIDATORS.md` E7-03, `E8-FEEDBACK.md` E8-01, Q8.

## E9-07 · Раздел «Документация» в интерфейсе
**Размер:** S · **Зависимости:** E9-01, E0-04 · **Фаза:** 2

**Зачем.** Документация пишется с каждой задачей, но пользы от неё ноль,
если за ней надо лезть в репозиторий. Раздел в меню делает её частью
рабочего инструмента.

**Что делаем.** Сборка MkDocs в Docker-образе, отдача собранного сайта
по адресу `/docs/` только авторизованным пользователям, пункт меню,
контекстная справка, блок «Что нового».

**Детали реализации.**
- Порядок в сборке образа важен: сначала `mkdocs build --strict`, потом
  `tools/check_user_docs.py --screens-out site/screens.json`. Наоборот
  нельзя — сборка очищает `site/` и сотрёт карту экранов. Битая ссылка
  роняет сборку, поэтому сломанная документация не доезжает до
  продакшена.
- Отдача через Django-view с `login_required`, **не через WhiteNoise**:
  WhiteNoise отдаёт статику всем подряд, а документация внутренняя.
- Карта «экран → страница» из поля `screens` лежит в
  `site/screens.json`. Кнопка «?» на экране берёт адрес оттуда; если
  страницы для экрана нет — кнопки нет. Идентификаторы экранов — список
  в `15-USER-DOCS.md` §3.4.
- Блок «Что нового» на дашборде — последний выпущенный раздел
  `changelog.md`.
- Свой рендер внутри шаблонов админки — не сейчас. Если понадобится,
  путь описан в `15-USER-DOCS.md` §6.2, тексты переписывать не придётся.

**Критерии приёмки.**
- без входа в систему `/docs/` недоступен;
- пункт «Документация» есть в меню, поиск по-русски находит страницы;
- кнопка «?» на списке площадок ведёт на страницу с
  `screens: [site_list]` (карточка площадки — критерий E9-02);
- «Что нового» показывает последнюю версию из журнала.

**Смотри также:** `15-USER-DOCS.md` §6, ADR-021.

## E9-08 · Причесать админку: удобство, переходы, выбор темы
**Размер:** L (было M, см. «Отклонения» в PROGRESS) · **Зависимости:** E9-01 · **Фаза:** 1

**Зачем.** После E9-01 админка работает, но пользоваться ей неудобно
(замечания пользователя, 28.09.2026, скриншот `screens/img_15.png`).
Всё сливается, названия почти одинаковые: «Площадки», «Площадки в
списке», «Площадки продукта», «Площадки продуктов». Экран моргает при
каждом переходе, переключатель темы не работает. Если с экраном
неудобно работать каждый день, Excel не уйдёт. Эту задачу делаем до
того, как на админке строить что-то дальше.

**Что делаем.**
1. **Ориентиры.** Сначала посмотреть, как сделаны админки и
   внутренние инструменты в других проектах: меню, группировка,
   списки, фильтры, плотность. Выписать, что берём. Решения — от
   удобства человека, а не от того, как устроены приложения Django.
2. **Выбор темы.** Установить не меньше четырёх тем или шаблонов
   админки, чтобы было из чего выбирать: unfold уже стоит, остальные —
   например, django-jazzmin, django-admin-interface, django-simpleui,
   Grappelli, django-baton. Показать пользователю одни и те же экраны
   (главная, «Площадки продукта» с фильтрами, страница продукта) в
   каждой теме. Выбирает пользователь. Совместимость с Django 5.2 и
   mypy strict проверить до показа. Выбор оформить уточнением ADR-037
   или новым ADR.
3. **Плавные переходы без моргания.** Варианты: View Transitions API
   (CSS `@view-transition`, переходы между страницами без JS),
   HTMX `hx-boost`, возможности выбранной темы. Не SPA (ADR-014).
4. **Переключатель темы.** Найти, почему не работает. На скриншоте
   «Переключатель темы» — пункт панели debug-toolbar, он меняет тему
   самой панели. Проверить и переключатель светлой и тёмной темы
   админки.
5. **Меню и названия.** Сгруппировать пункты по работе человека
   («Площадки», «Размещения», «Ключи», «Настройки»), а не по
   приложениям. Служебные таблицы (снапшоты метрик и цен, «площадки в
   списке», «площадки продуктов») убрать из первого уровня или
   переименовать так, чтобы названия не совпадали. Главная страница —
   не список всех таблиц.
6. **Читаемость.** Контраст, отступы, ширина колонок, выделение
   активного пункта меню. Панель debug-toolbar по умолчанию свёрнута и
   не закрывает страницу. Русский перевод подписей темы (у unfold его
   нет: **Filters**, **Apply Filters**).

**Критерии приёмки.**
- пользователь выбрал тему из четырёх и более вариантов, показанных на
  одинаковых экранах;
- переход между страницами админки не моргает;
- переключатель темы работает;
- в меню нет двух пунктов с похожими названиями, служебные таблицы не
  на первом уровне;
- пользователь посмотрел рабочие экраны и подтвердил, что ими удобно
  пользоваться;
- критерии E9-01 держатся: не больше 10 запросов на странице списка,
  поиск по вставленному адресу.

**Смотри также:** ADR-014, ADR-037, E9-01, `screens/img_15.png`.

## E9-09 · Админка без перезагрузки страниц
**Размер:** M · **Зависимости:** E9-08, E1-08 · **Фаза:** 3

**Зачем.** Пользователю понравилось, что карточка площадки и кнопки
разбора цен работают без перезагрузки страницы (прототип E1-07/E1-08,
01.10.2026): «динамическая подгрузка страниц мне очень нравится, жалко
у нас её нет». Остальная админка перезагружает страницу на каждый
фильтр, переход и сохранение. 02.10.2026, при E1-10: «убирай из
интерфейсов вообще всю подобную подгрузку с обновлением страниц, а то это
бесит, лучше динамическую делать везде» — пользователь выбрал взять задачу
сразу после E1-10, раньше фазы 3; фильтры «Площадок» — в ней же.

**Что делаем.** Переходы, фильтры, сортировка и пагинация списков,
сохранение форм — без полной перезагрузки. Инструмент — HTMX (ADR-014:
«когда админки перестанет хватать — Django + HTMX, не React»), а не SPA.
При планировании выбран свой общий скрипт на основе подгрузки экранов
загрузки (ADR-046).

**Детали реализации.**
- Начать с `hx-boost` на ссылках и формах админки и проверить, что
  переживают скрипты админки: виджеты дат, автодополнение, инлайны
  («Добавить ещё»), действия над отмеченными строками, фильтры
  диапазонов, расцветки (ADR-038), кнопки индексации и карточка
  площадки. Что не переживает — исключить из `hx-boost` или
  переинициализировать.
- Кнопка «Назад» в браузере и адрес страницы работают как раньше.
- Сравнить с View Transitions (ADR-038): одно из двух или вместе.
- Выбор оформить ADR.

**Критерии приёмки.**
- переход между экранами и применение фильтра в «Площадках» — без
  полной перезагрузки, «Назад» возвращает на прежнее место;
- формы, инлайны, действия и автодополнение работают как раньше;
- число запросов на странице списка не растёт от числа строк (E9-01).
  Уточнено 02.10.2026 с пользователем: «не больше 10» с E1-10 уже
  неверно — «Площадки» делают 11 (список регионов); подгрузка запросов
  не добавляет. Ускорение — E1-11.

**Сделано** (02.10.2026, ADR-046): свой скрипт `seo/soft-nav.js`, а не
HTMX; экраны загрузки и карточка — на нём; браузерные проверки
`make e2e`. После показа — окно «Решение по площадке» по щелчку на
статус в «Площадках» и починка статуса в формах (с E9-08 — поле ввода).

**Смотри также:** ADR-014, ADR-038, ADR-042, ADR-043, ADR-046, E9-08, E1-11.

## E9-10 · Сохранённые наборы фильтров
**Размер:** M · **Зависимости:** E9-09 · **Фаза:** 1

**Зачем.** Пользователь 02.10.2026 (E9-09): нужна «система сохранения
фильтров для правого меню», чтобы, вернувшись на страницу или после
закрытия вкладки, сразу выбрать фильтры, которыми пользовались:
«селектор фильтров, кнопка добавить фильтр, кнопка удалить фильтр».

**Что делаем** (предложено, уточнить при планировании).
- Над колонкой «Фильтр» — блок «Мои фильтры»: выбор набора применяет его
  сразу (подгрузкой, ADR-046); первым пунктом — «Как в прошлый раз».
- «Добавить» — сохранить текущие фильтры, поиск, регион и сортировку
  под названием; «Удалить» — убрать выбранный набор, с «Отменить».
- Наборы не удаляются физически — пометкой (правило проекта).

**Открытые вопросы** (не ответил пользователь при E9-09):
- наборы у каждого свои или общие на двоих; предложение — свои, в базе
  (видны с любого компьютера), «Как в прошлый раз» — в браузере;
- только «Площадки» или все списки с фильтрами; предложение — все.

**Критерии приёмки.**
- набор сохраняется, применяется одним выбором, удаляется и
  восстанавливается «Отменить»;
- «Как в прошлый раз» возвращает фильтры после закрытия вкладки;
- `make e2e` — проверка на «Площадках».

**Сделано** (03.10.2026, ADR-050): наборы свои у каждого, в базе
(`saved_filters`, приложение `apps/workspace`); «Как в прошлый раз» — в
браузере; блок «Мои фильтры» первым в колонке фильтров всех списков;
название занято — вопрос «Заменить» в блоке; удаление пометкой, «Отменить»
в сообщении.

**Смотри также:** ADR-046, ADR-050, E9-01, E9-09.

## E9-11 · Записи — панелью справа поверх списка
**Размер:** L · **Зависимости:** E9-09, E1-12 · **Фаза:** 1

**Зачем.** Пользователь 02.10.2026 (показ E1-12): чтобы сменить статус
размещения, пришлось уходить из списка «Размещения» на полную страницу
формы — «можно ли сделать, чтобы меня не переводило на эту страницу, а
прямо на странице списка выдвигающееся окно с правого края, примерно до
списка доменов»; кнопки и поля в нём — «удобно, по best practice UX»;
«если есть похожие окна где-то, их тоже надо сделать такими же — как
можно меньше переходов». Образец — карточка площадки в «Площадках»
(`seo/site-card.js`, E1-07): «у нас есть похожая панель, такой же подход
для подобных панелей, когда работаем с доменами точечно».

**Что делаем** (предложено пользователю 02.10.2026, детали — при
планировании).
- Общая панель справа на подходе карточки площадки: щелчок по записи в
  списке — панель выезжает поверх списка, колонка доменов слева видна,
  список не перезагружается. Щелчок по другой записи — панель
  показывает её; ↑/↓ — соседняя запись списка.
- «Сохранить» — панель закрывается, строка списка обновляется на месте;
  Esc или щелчок по списку — закрыть, несохранённые правки — вопрос.
  Ctrl+щелчок — полная страница, как сейчас.
- Форма в панели — под удобство: площадка и продукт в заголовке, а не
  полями; статус — кнопками по порядку; поля по группам (заявка,
  публикация, проверки, комментарий); даты — без времени и предупреждения
  о часовом поясе, с «Сегодня»; «Заплачено» — в евро, а не в центах;
  «Сохранить» и «Отмена» закреплены внизу. Кнопки — классами `.seo-btn`
  (ADR-038).
- Где: размещение из «Размещений» (и статус размещения в списке — щелчком,
  как в «Площадках»); окно «Решение по площадке» и карточка площадки — в
  ту же панель; записи остальных списков — каталог площадок, продавцы,
  ключи, рабочие списки, продукты, настройки.

**Критерии приёмки.**
- статус размещения меняется из списка «Размещения» без перехода, строка
  обновляется на месте;
- все перечисленные списки открывают запись панелью, Ctrl — полной
  страницей;
- `make e2e`: панель на каждом из списков, сохранение с ошибкой формы —
  ошибка в панели, без перехода.

**Сделано** (03.10.2026, ADR-048): одна панель `seo/panel.js` для всех
перечисленных списков и «Добавить» (согласовано), форма с сервера по
`X-Seo-Partial`, запись — JSON, строка меняется на месте, ушедшая из
фильтра — блёклая; карточка и решение — в той же панели, статусы кнопками;
форма размещения — статус кнопками, кнопка статуса ставит сегодняшнюю дату,
даты днём, «Заплачено» в валюте. После показа — ширина панели по
содержимому, а не до колонки доменов. История смены статусов — E1-13.

**Смотри также:** ADR-043 (карточка окном), ADR-046, ADR-047, ADR-048,
E9-09, E1-12, E1-13.
