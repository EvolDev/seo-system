# E9. Интерфейс

**Цель эпика.** Дать людям экран, с которого работают, вместо
33 колонок Excel. Начинаем с админки Django — она даёт рабочий
интерфейс на второй день (ADR-014).

**Зависит от:** E1 · **Блокирует:** E3-04, E5-03, E8-01

**Принцип:** никакого SPA. Когда админки перестанет хватать —
Django + HTMX, не React. Для инструмента на двоих этого хватит надолго.

---

## E9-01 · Django Admin как база
**Размер:** S · **Зависимости:** E1-01 · **Фаза:** 1

**Зачем.** Первое «потрогать руками». Часть первого вертикального
среза.

**Что делаем.** Регистрация моделей, списки с фильтрами и сортировками,
поиск.

**Детали реализации.**
- Фильтры, которые нужны сразу: статус, DR (диапазоны), трафик
  (диапазоны), язык, «пишем мы» (`we_write` из `v_site_latest`),
  наличие размещений.
- В списке площадок показывать последние значения метрик через
  аннотацию из представления, а не подзапросом на каждую строку —
  иначе получится N+1 на полутора тысячах строк.
- Поиск по домену с нормализацией ввода: человек вставит URL целиком.
- `list_select_related` и `prefetch_related` настроить сразу.
- Список площадок строится поверх `v_site_latest` — там уже последние
  метрики, цены и признак «пишем мы».
- Удаление доменных объектов в админке отключено
  (`has_delete_permission`): ничего не удаляем физически, отмена —
  статусами.

**Критерии приёмки.**
- все площадки видны и фильтруются — после импорта это около 2000;
- страница списка выполняет не больше 10 запросов (проверить
  django-debug-toolbar);
- поиск находит площадку по вставленному полному URL.

**Подводные камни.** Админка по умолчанию делает N+1 на связанных
полях. При двух тысячах строк это заметно сразу — и это хороший учебный
момент по ADR-003.

**Смотри также:** ADR-003, ADR-014, `07-ROADMAP.md` §Фаза 1.

## E9-02 · Карточка площадки
**Размер:** M · **Зависимости:** E9-01, E1-05 · **Фаза:** 3

**Зачем.** Главный экран системы. Для принятия решения не должно
требоваться ничего, кроме него.

**Что делаем.** Единый экран: метрики с историей, цены, серость,
история аудитов, размещения, ссылки и их живость, кандидаты в анкоры,
кнопки действий.

**Детали реализации.**
- Метрики — с графиком динамики, а не только последним значением.
  Тренд трафика входит в правила оценки.
- Серость — доля с разбивкой по категориям и примерами URL.
- История аудитов: все вердикты, а не последний. Видно, менялось ли
  мнение.
- Блок размещений — по всем продуктам, включая Clideo.
- Кнопки: запустить аудит, подобрать анкоры, проверить индексацию,
  проверить ссылки, добавить в очередь размещений.
- Долгие действия уходят в очередь и показывают статус, а не вешают
  страницу.

**Критерии приёмки.**
- решение по площадке принимается без открытия других экранов;
- график динамики трафика отображается;
- запуск аудита с карточки работает и показывает прогресс;
- кнопка «?» ведёт на страницу документации с `screens: [site_card]`.

**Смотри также:** `04-DOMAIN-RULES.md` §1, `E4-SITE-AUDIT.md`.

## E9-03 · Дашборд
**Размер:** M · **Зависимости:** E1-03, E2-08 · **Фаза:** 5

**Что делаем.** Четыре блока: очередь за сутки, расходы за месяц,
воронка статей, просроченные проверки.

**Детали реализации.**
- Данные из представлений, не из ORM-агрегаций (ADR-003).
- Расходы с разбивкой по провайдерам и трендом.
- Воронка статей: черновиков → прошло валидаторы с первой попытки →
  принято.
- Просроченные проверки с приоритетом и ссылками на сущности.
- Сюда же выводятся метрики качества из E8-05.

**Критерии приёмки.**
- дашборд отвечает на вопрос «что сегодня не так» за десять секунд;
- страница грузится меньше секунды на реальных данных.

**Смотри также:** `02-ARCHITECTURE.md` §Что показываем на дашборде.

## E9-04 · Telegram-бот
**Размер:** S · **Зависимости:** E2-01 · **Фаза:** 2

**Зачем.** Алерты должны приходить туда, где их прочитают, а не на
страницу, которую надо открыть.

**Что делаем.** Алерты по правилам из `02-ARCHITECTURE.md` плюс
утренняя сводка.

**Детали реализации.**
- **Правило одно:** летит только то, на что человек пойдёт и что-то
  сделает. Пропала ссылка — да. Расход превысил порог вдвое — да.
  Задача упала трижды — да. «Проверка выполнена успешно» — никогда.
- Усталость от алертов убивает наблюдаемость надёжнее, чем её
  отсутствие. Если в канал сыплется всё подряд, через две недели его
  перестают читать, и настоящая авария проходит мимо.
- Сводка — счётчики, а не простыня.
- Группировка: 12 пропавших ссылок — одно сообщение, не двенадцать.

**Критерии приёмки.**
- приходят только алерты из списка;
- за неделю работы в канале не больше 10–15 сообщений;
- каждое сообщение содержит ссылку на соответствующий экран.

**Смотри также:** `02-ARCHITECTURE.md` §Правила алертов.

## E9-05 · Очередь ручных решений
**Размер:** M · **Зависимости:** E9-02 · **Фаза:** 3

**Зачем.** Единая точка входа в рабочий день. Всё, что ждёт человека,
в одном списке.

**Что делаем.** Список: пограничные аудиты, статьи на вычитку,
кандидаты в факты, открытые вопросы по слотам, статьи после трёх
неудачных итераций.

**Детали реализации.**
- Сортировка по приоритету и сроку: статья, которую ждёт площадка,
  важнее кандидата в факты.
- Каждый элемент решается в один-два клика, без перехода в другие
  разделы, где это возможно.
- Счётчик в шапке: сколько всего ждёт.

**Критерии приёмки.**
- рабочий день начинается с этого экрана;
- элемент можно решить, не покидая список, где это применимо.

## E9-06 · Редактор статьи
**Размер:** M · **Зависимости:** E7-03 · **Фаза:** 4b

**Зачем.** Вычитка 50 статей в месяц — 12–17 часов. Удобство редактора
напрямую влияет на эту цифру.

**Что делаем.** Просмотр черновика с подсветкой ссылок, позиций и
результатов валидаторов, правка руками перед отправкой.

**Детали реализации.**
- Подсветка: где ссылки, на каком символе, какие проверки провалены.
- Рядом с каждым провалом — цитата места и предложение критика, что
  исправить.
- Правка человека сохраняется как новая версия и становится сигналом
  для E8: статья была почти хорошей.
- Кнопки вердикта (E8-01) здесь же.
- Сравнение версий: что изменилось между итерациями.

**Критерии приёмки.**
- человек правит статью, не выходя в другой редактор;
- видно, какие проверки провалены и где именно;
- правка сохраняется как версия, вердикт фиксируется.

**Смотри также:** `E7-VALIDATORS.md` E7-03, `E8-FEEDBACK.md` E8-01, Q8.

## E9-07 · Раздел «Документация» в интерфейсе
**Размер:** S · **Зависимости:** E9-01, E0-04 · **Фаза:** 2

**Зачем.** Документация пишется с каждой задачей, но пользы от неё ноль,
если за ней надо лезть в репозиторий. Раздел в меню делает её частью
рабочего инструмента.

**Что делаем.** Сборка MkDocs в Docker-образе, отдача собранного сайта
по адресу `/docs/` только авторизованным пользователям, пункт меню,
контекстная справка, блок «Что нового».

**Детали реализации.**
- Порядок в сборке образа важен: сначала `mkdocs build --strict`, потом
  `tools/check_user_docs.py --screens-out site/screens.json`. Наоборот
  нельзя — сборка очищает `site/` и сотрёт карту экранов. Битая ссылка
  роняет сборку, поэтому сломанная документация не доезжает до
  продакшена.
- Отдача через Django-view с `login_required`, **не через WhiteNoise**:
  WhiteNoise отдаёт статику всем подряд, а документация внутренняя.
- Карта «экран → страница» из поля `screens` лежит в
  `site/screens.json`. Кнопка «?» на экране берёт адрес оттуда; если
  страницы для экрана нет — кнопки нет. Идентификаторы экранов — список
  в `15-USER-DOCS.md` §3.4.
- Блок «Что нового» на дашборде — последний выпущенный раздел
  `changelog.md`.
- Свой рендер внутри шаблонов админки — не сейчас. Если понадобится,
  путь описан в `15-USER-DOCS.md` §6.2, тексты переписывать не придётся.

**Критерии приёмки.**
- без входа в систему `/docs/` недоступен;
- пункт «Документация» есть в меню, поиск по-русски находит страницы;
- кнопка «?» на списке площадок ведёт на страницу с
  `screens: [site_list]` (карточка площадки — критерий E9-02);
- «Что нового» показывает последнюю версию из журнала.

**Смотри также:** `15-USER-DOCS.md` §6, ADR-021.
