# E7. Валидаторы и критик

**Цель эпика.** Автоматическая проверка статьи по всем пунктам ТЗ.
Код проверяет то, что можно посчитать; LLM — только то, что требует
суждения.

**Зависит от:** E2-04, E5-02, E4-01 · **Блокирует:** E8

**Ключевой принцип (ADR-016):** отдавать модели то, что решается
парсером, — самая частая ошибка в таких проектах. Из 17 пунктов ТЗ
модели остаётся по сути один: тест на извлечение.

**Отдельная ценность:** E7-01 и E7-04 полезны до всякой генерации —
ими проверяются статьи от площадок и копирайтеров. Поэтому они в
фазе 4a, раньше генератора.

---

## E7-01 · Детерминированные валидаторы
**Размер:** L · **Зависимости:** E2-04, E5-02 · **Фаза:** 4a

**Зачем.** Снимает ручную проверку статей по чеклисту — прямо сейчас
это делается глазами по 17 пунктам на каждую статью.

**Что делаем.** Все проверки из `05-CONTENT-SYSTEM.md` §3, пороги из
таблицы `rules`.

**Детали реализации.**

Полный перечень с указанием, что именно считается:

| Проверка | Как считается |
|---|---|
| `LINK_POSITION_FIRST` | смещение в символах с пробелами от начала **тела** статьи |
| `LINK_POSITION_SECOND` | то же для второй ссылки |
| `PRODUCT_LINKS_COUNT` | подсчёт ссылок по домену продукта |
| `LINK_NOFOLLOW`, `LINK_REL_SPAM` | разбор атрибутов `rel` |
| `WRONG_TARGET` | точное сравнение URL с заданием |
| `ANCHOR_MISMATCH` | сравнение текста анкора с заданием без учёта регистра |
| `TOO_MANY_INTERNAL` | ссылки на домен площадки |
| `NO_AUTHORITY_LINKS` | пересечение с белым списком доменов |
| `WEAK_STRUCTURE` | количество H2/H3, списков, таблиц |
| `NO_TOC` | наличие блока оглавления |
| `ARTICLE_LENGTH` | число слов |
| `NOINDEX` | meta robots + robots.txt |
| `AD_LABEL` | поиск маркеров из параметров правила |

- Определение «тела статьи» — то же, что в E2-04. Одно место в коде,
  не два.
- Каждый результат пишется в `validation_results` с указанием места в
  тексте, а не просто `false`.
- Пороги **только** из `rules`, ни одного числа в коде.
- Валидаторы работают и на черновике (markdown), и на опубликованной
  странице (HTML). Общий интерфейс, разные парсеры на входе.

**Критерии приёмки.**
- на 10 реальных статьях результат совпадает с ручной проверкой;
- каждый провал содержит указание места в тексте;
- изменение порога в базе меняет поведение без перезапуска;
- проверка одной статьи занимает меньше секунды.

**Подводные камни.** Позиция ссылки в символах — главный источник
расхождений. Считать по тексту без тегов, с пробелами, от начала тела
статьи. Зафиксировать в тестах на конкретном примере.

**Смотри также:** `05-CONTENT-SYSTEM.md` §3, `13-CONFIG.md` §2,
`04-DOMAIN-RULES.md` §3.

## E7-02 · Критик
**Размер:** M · **Зависимости:** E4-01, E5-02 · **Фаза:** 4b

**Зачем.** Тест на извлечение — то, ради чего вообще платятся деньги за
размещение. Плохо интегрированная ссылка не работает.

**Что делаем.** Отдельный LLM-вызов по промпту P6, чистый контекст,
JSON по схеме.

**Детали реализации.**
- Критик **не видит** историю генерации, использованные примеры и номер
  итерации (ADR-015). Только статью, задание и рубрику.
- В идеале — другая модель, не та, что писала.
- Оценивает **только** то, что не проверил код: интеграцию анкора,
  естественность, тематическое соответствие, заметность ссылки в
  контексте, внутренние противоречия.
- Отрицательные примеры из `examples` идут именно сюда — как чеклист
  типовых косяков.
- Для каждой ссылки обязан вернуть: пересказ предложения своими
  словами, вердикт по тесту, и при провале — конкретную формулировку
  что исправить.

**Критерии приёмки — контрольная точка.**
- на 10 статьях с заведомо плохой интеграцией ловит проблему минимум
  в 9;
- на 10 хороших — не больше одного ложного срабатывания;
- ответ всегда валидный JSON по схеме;
- не выдаёт вердиктов по пунктам, которые проверяет код.

**Подводные камни.** Соблазн дать критику весь чеклист целиком «чтобы
уж наверняка». Тогда он начнёт спорить с валидаторами и выдавать
ложные срабатывания по позициям ссылок, которые уже посчитаны точно.

**Смотри также:** `11-PROMPTS.md` §P6, ADR-015, ADR-016.

## E7-03 · Цикл правок
**Размер:** M · **Зависимости:** E6-04, E7-01, E7-02 · **Фаза:** 4b

**Что делаем.** До 3 итераций, правки только по проваленным пунктам,
после третьей — в ручную очередь.

**Детали реализации.**
- В модель уходит исходный текст плюс список проваленных пунктов, и
  указание править **только их**. Переписывание целиком ломает уже
  прошедшие проверки — это главная причина, почему цикл надо
  ограничивать содержательно, а не только по числу итераций.
- Каждая итерация — новая версия в `article_versions`. Ничего не
  затирается.
- После каждой правки — полный прогон валидаторов заново: правка могла
  сломать то, что работало.
- После третьей неудачи статья получает статус `needs_human` и уходит в
  очередь ручных решений с пометкой: скорее всего дефект задания, а не
  генерации.

**Критерии приёмки.**
- цикл завершается предсказуемо, не зацикливается;
- все версии сохранены и доступны для сравнения;
- статья после трёх итераций попадает в ручную очередь с понятной
  причиной;
- повторный прогон валидаторов после правки выполняется.

**Смотри также:** `05-CONTENT-SYSTEM.md` §2.5, `11-PROMPTS.md`
§Промпт правок.

## E7-04 · Проверка опубликованной статьи
**Размер:** M · **Зависимости:** E7-01, E2-04 · **Фаза:** 4a

**Зачем.** Финальная приёмка размещения. Сейчас делается вручную по
17 пунктам, и именно здесь глаз замыливается сильнее всего.

**Что делаем.** Прогон валидаторов по живому URL плюс проверки, которые
возможны только на опубликованной странице.

**Ограничение фазы 4a.** Критик (E7-02) появится только в 4b. До него
`BAD_INTEGRATION`, `RAW_AI_TEXT` и `OFF_TOPIC` в отчёте помечены «не
проверено — вычитка человеком», а вердикт «готово к финалу» без них не
выдаётся. Главный пункт — тест на извлечение — до 4b делает человек.
Механическая часть проверки перестаёт быть ручной уже в 4a.

**Детали реализации.**
- Дополнительно к E7-01: индексация, анонс на главной, глубина в кликах
  от главной, финальные атрибуты ссылок (площадка могла поменять `rel`
  после публикации).
- Глубина в кликах: обход от главной с ограничением в 2 уровня, поиск
  URL статьи.
- Статья площадки заводится как `articles` с `origin = platform` и
  версией 1 — без этого результатам проверок некуда записаться:
  `validation_results` ссылается на версию статьи.
- Результат выдаётся **по трём корзинам критичности**, а не общим
  списком, с ценой размещения в контексте: площадка до ~150 EUR не
  обязана быть идеальной, площадка близко к 550 должна отрабатывать по
  максимуму.
- Итоговый вердикт: готово к финалу / нужны правки / критично нарушено.
  «Готово к финалу» — только когда проверена интеграция анкора: критиком
  или человеком.

**Критерии приёмки.**
- по URL опубликованной статьи выдаётся отчёт по трём корзинам;
- цена размещения присутствует в отчёте как контекст;
- критичное нарушение не смягчается из-за низкой цены;
- без проверки интеграции анкора вердикт «готово к финалу» не выдаётся;
- на 5 реальных опубликованных статьях отчёт совпадает с ручным
  разбором.

**Смотри также:** `04-DOMAIN-RULES.md` §3, `05-CONTENT-SYSTEM.md`
§3; формат ответа — часть 2 промпта аудитора в
`source/audit-system-prompt.md`.
