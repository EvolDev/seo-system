# E2. Чекеры

**Цель эпика.** Снять с людей все механические проверки: индексацию,
живость ссылок, серость, обновление метрик. Система сама помнит, что
и когда перепроверить.

**Зависит от:** E1 · **Блокирует:** E4 (досье), E7-04

---

## E2-01 · Инфраструктура очередей
**Размер:** M · **Зависимости:** E0-01, E1-03 · **Фаза:** 1

**Зачем.** Все проверки — фоновые. Без очереди они либо блокируют
интерфейс, либо не выполняются вовсе.

**Что делаем.** Celery + Redis + beat, базовый класс задачи с записью
в `task_runs`, ретраи, ограничение скорости на внешние API.

**Детали реализации.**
- Базовый класс задачи пишет `task_runs` автоматически: старт, финиш,
  длительность, ошибка, `run_id`. Каждая задача не должна помнить об
  этом сама.
- `run_id` — по договорённости ADR-025: задача принимает его аргументом,
  базовый класс выполняет её внутри `bind_run_id`, следующей задаче
  передаётся `current_run_id()`. Механизм готов в E0-03.
- Ограничение скорости — на уровне очереди, а не внутри задачи. Для
  краулера — не чаще одного запроса в секунду на домен.
- Ретраи: 3 попытки с экспоненциальной задержкой. После третьей —
  пометка `failed` и попадание в дневную сводку.
- Идемпотентность: повторный запуск задачи не портит данные. Для
  проверок это естественно, для генерации — нет, там версионирование.

**Критерии приёмки.**
- тестовая задача выполняется по расписанию;
- падение задачи пишется в `task_runs` с текстом ошибки;
- три неудачи подряд дают алерт;
- при остановке воркера задачи не теряются.

**Подводные камни.** `CELERY_TASK_ALWAYS_EAGER=true` в тестах, иначе
тесты будут зависеть от запущенного воркера.

**Смотри также:** `02-ARCHITECTURE.md` §Очереди, `13-CONFIG.md` §3.

## E2-02 · Клиент SERP API
**Размер:** M · **Зависимости:** E2-01 · **Фаза:** 1

**Зачем.** Через него работают и проверка индексации, и gray scan —
две самых частых рутины.

**Что делаем.** Абстракция над провайдером (DataForSEO или Serper),
учёт расхода в `api_usage`, кеширование одинаковых запросов в пределах
суток.

**Детали реализации.**
- Интерфейс: `search(query, depth, country) -> list[SerpResult]`.
  Провайдер задаётся конфигом, смена — без правки вызывающего кода.
- Кеш по хешу `(query, depth, country)` на 24 часа: один и тот же
  `site:domain` за день запрашивается многократно.
- Стоимость каждого запроса пишется в `api_usage` сразу, а не
  агрегируется потом.
- Стандартная очередь (дешевле, ~5 минут ожидания) для плановых
  проверок; live-режим — только там, где человек ждёт результат.

**Критерии приёмки.**
- запрос `site:domain` возвращает структурированный результат;
- стоимость записана в `api_usage`;
- повторный идентичный запрос в тот же день не тратит деньги;
- при превышении дневного лимита задачи встают, а не жгут баланс.

**Подводные камни.**
- Google убрал параметр `num=100` в сентябре 2025 — глубокая выдача
  требует нескольких запросов и стоит дороже. Для `site:` глубина
  обычно не нужна.
- Счётчик «примерно N результатов» приблизителен. Не использовать его
  как точное число (см. E2-06).

**Смотри также:** `02-ARCHITECTURE.md` §Внешние интеграции,
`13-CONFIG.md` §1.

## E2-03 · Проверка индексации
**Размер:** M · **Зависимости:** E2-02, E1-02 · **Фаза:** 1

**Зачем.** Сейчас это делается вручную и держится на «не забыть».
Неиндексируемая статья — выброшенные деньги.

**Что делаем.** Задача по расписанию: через 3 дня после публикации,
далее ежедневно до успеха, после успеха — раз в месяц.

**Детали реализации.**
- Проверка через `site:article_url` — точное совпадение URL в выдаче.
  Проверять именно URL статьи, а не домен.
- Результат в `checks` с `check_type = indexation` и корректным
  `next_check_at`.
- Успех снимает размещение с ежедневного цикла и ставит
  `placements.is_indexed = true`.
- Если статья не индексируется дольше 30 дней — алерт: скорее всего
  страница закрыта от индексации или площадка её удалила.

**Критерии приёмки.**
- для опубликованного размещения статус обновляется автоматически;
- запись в `checks` содержит `next_check_at`;
- успешная проверка переводит задачу в месячный цикл;
- 30 дней без индексации дают алерт в Telegram.

**Смотри также:** `04-DOMAIN-RULES.md` §4, часть первого вертикального
среза в `07-ROADMAP.md`.

## E2-04 · Краулер статей
**Размер:** M · **Зависимости:** E2-01, E1-02 · **Фаза:** 2

**Зачем.** Основа сразу трёх вещей: проверки живости ссылок, досье для
аудита и валидаторов статьи.

**Что делаем.** Загрузка страницы, разбор HTML, поиск ссылок на наши
продукты, извлечение `rel`, позиции в символах, окружающего предложения.

**Детали реализации.**
- Извлечение **тела статьи**, а не всей страницы: меню, подвал и
  сайдбар не должны попадать в подсчёт позиции ссылки. Это главная
  сложность задачи. Начать с эвристики (`article`, `main`, крупнейший
  текстовый блок), при промахах — ручное указание селектора для
  конкретного домена.
- `char_offset` считать по тексту без тегов, с пробелами — то же
  определение, что в E1-02.
- Сохранять предложение вокруг ссылки в `placement_links.context_sentence`:
  понадобится критику и при
  разборе качества интеграции.
- Корректно обрабатывать редиректы (до 5), 404, таймауты, кодировки.
- Уважать `robots.txt` и не долбить домен чаще раза в секунду.

**Критерии приёмки.**
- по URL статьи возвращается список найденных ссылок с `rel` и
  позициями;
- на 10 реальных статьях позиция первой ссылки совпадает с ручным
  подсчётом (допуск ±50 символов);
- 404 и таймаут не роняют задачу, а возвращают статус.

**Подводные камни.** Часть площадок отдаёт контент через JavaScript.
Для них обычный запрос вернёт пустоту. Решение на первое время —
пометка «требует ручной проверки», а не тащить браузер в стек.

**Смотри также:** `03-DATA-MODEL.md` §placement_links.

## E2-05 · Проверка живости ссылок
**Размер:** M · **Зависимости:** E2-04 · **Фаза:** 2

**Зачем.** Прямая боль: неизвестно, сколько размещённых ссылок ещё
существует. Площадки со временем их подчищают.

**Что делаем.** Регулярный обход опубликованных размещений всех
продуктов, включая исторические ссылки на Clideo.

**Детали реализации.**
- Расписание: через 7 дней после публикации, далее раз в 14 дней первые
  3 месяца, потом раз в месяц.
- **Пропажа подтверждается, а не фиксируется с одного раза.** Страница
  отдала 200, а ссылки в теле статьи нет — это кандидат. Повторная
  проверка не раньше чем через сутки; снова нет — пропажа подтверждена,
  `lost_at` пишется один раз. Таймаут, пустой ответ JavaScript-страницы,
  защита от ботов — не пропажа, а ошибка проверки со статусом `error`.
- **404 или недоступная страница — вопрос человеку**, а не вывод: запись
  в `checks` со статусом `warning` и в очередь ручных решений (до E9-05 —
  алертом в Telegram). Так
  требует промпт аудитора для ссылки на Clideo; для Convertio то же самое.
- **Размещения Clideo из импорта** приходят без строк ссылок — анкор
  неизвестен. Первый обход ищет любую ссылку на `clideo.com`: нашлась —
  создаёт строку ссылки; не нашлась при 200 и подтвердилась — фактор
  `CLIDEO_LINK_REMOVED`.
- Проверяется не только наличие, но и `rel`: замена dofollow на
  nofollow — такая же потеря, как удаление.
- Подтверждённая пропажа ссылки на **Convertio** создаёт запись
  `site_audits` с блокером `STOP_LINK_REMOVED` и `author = system` — это
  стоп-фактор для будущих размещений на площадке.
- Пропажа ссылки на **Clideo** — не стоп, а фактор `CLIDEO_LINK_REMOVED`
  в гибкой зоне: запись в `checks` со статусом `failed`, аудит учтёт её
  как сильный минус (`04-DOMAIN-RULES.md` §1.1).

**Критерии приёмки.**
- исчезновение ссылки фиксируется и даёт алерт только после
  подтверждения; один неудачный обход стопа не ставит;
- 404 уходит человеку, а не в стоп;
- пропажа ссылки на Convertio даёт стоп, на Clideo — минус в гибкой зоне;
- смена `rel` на nofollow фиксируется отдельно от исчезновения;
- площадка после пропажи попадает в список на пересмотр;
- проверка 500 размещений укладывается в ночное окно.

**Открытый вопрос.** Что делает система при пропаже — только алерт,
автоматический blacklist, или задача написать владельцу (Q9).

**Смотри также:** `04-DOMAIN-RULES.md` §1.1, ADR-007.

## E2-06 · Gray scan
**Размер:** M · **Зависимости:** E2-02 · **Фаза:** 2

**Зачем.** Сейчас это самая муторная часть ручного аудита: длинный
запрос с двумя десятками терминов, потом ещё один, потом деление в уме.

**Что делаем.** Проверка по категориям из `04-DOMAIN-RULES.md` §1.4 с
подсчётом доли и сохранением примеров URL.

**Детали реализации.**
- Алгоритм — `04-DOMAIN-RULES.md` §1.4. Коротко: доля = оценка Google по
  **одному** запросу со всеми терминами через `OR` / оценка по
  `site:domain`. Запросы по категориям — отдельно и только для разбивки:
  их сумма считает одну страницу несколько раз.
- Категорий восемь: шесть из запроса в `flow.txt` плюс форекс и дейтинг
  из промпта аудитора (термины — Q13). Список берётся из
  `domain_settings`, ключ `GRAY_TERMS`.
- Оценка Google «примерно N» неточна, но другой нет: у сайта тысячи
  страниц. Серых результатов меньше 100 — пролистать и посчитать точно,
  расхождение с оценкой сохранить в `breakdown`.
- Доля в пределах ±3 п. п. от порогов 10% и 25% — флаг «проверить
  глазами» на карточке.
- Сохранять 3–5 примеров URL на категорию: человек захочет глянуть
  глазами.
- Отдельно учитывать декларацию площадки из поля «Особые тематики» —
  площадка, официально принимающая казино, рискованнее даже при чистом
  индексе.

**Критерии приёмки.**
- для площадки считается доля с разбивкой по категориям;
- на 5 контрольных доменах доля совпадает с ручной проверкой по методу
  `flow.txt` (тот же запрос, та же оценка Google) с допуском ±2 п. п.;
- одна страница, подходящая под две категории, в долю попадает один раз;
- сохранены примеры URL.

**Смотри также:** `04-DOMAIN-RULES.md` §1.4, `12-IMPORT-MAPPING.md` §1.6.

## E2-07 · Клиент Ahrefs API
**Размер:** M · **Зависимости:** E2-01, **Q2** · **Фаза:** 3

**Зачем.** Убирает ручное перебивание метрик и скриншоты в чат.

**Что делаем.** Получение DR, трафика, ключей, позиций, топ-страниц
с их главными ключами (для фактора «живые небрендовые запросы» из
`flow.txt`). Учёт юнитов в `api_usage`, батчинг, защита от цикла,
сжигающего квоту.

**Детали реализации.**
- **Заблокировано вопросом Q2**: не подтверждён доступ к REST API v3 на
  текущем тарифе. До подтверждения реализовать фолбэк — ручной ввод и
  импорт CSV-выгрузок. Архитектурно это одна таблица с разным `source`.
- `AHREFS_ENABLED=false` по умолчанию, чтобы на этапе разработки не
  сжечь юниты.
- Батчинг: обновление метрик пачками, а не по одному домену.
- Предохранитель: дневной лимит юнитов из конфига, при превышении
  задачи встают.
- MCP-сервер Ahrefs использовать нельзя — правилами запрещено дёргать
  его из собственных скриптов.

**Критерии приёмки.**
- метрики площадки обновляются одной задачей;
- расход юнитов виден в `api_usage`;
- при `AHREFS_ENABLED=false` система работает на ручных данных без
  ошибок.

**Смотри также:** `09-OPEN-QUESTIONS.md` Q2, `02-ARCHITECTURE.md`
§Внешние интеграции.

## E2-08 · Планировщик перепроверок
**Размер:** S · **Зависимости:** E2-03, E2-05 · **Фаза:** 2

**Зачем.** Собирает все виды проверок в один список «что сегодня».
Это и есть замена «не забыть».

**Что делаем.** Единая задача по `v_overdue_checks`, утренняя сводка.

**Детали реализации.**
- Приоритизация: индексация свежих размещений важнее квартального
  gray scan.
- Сводка содержит счётчики, а не простыню: «12 проверок индексации,
  3 просроченных обхода ссылок, 1 упавшая задача».
- Ничего успешного в сводку не попадает, кроме итоговых цифр.

**Критерии приёмки.**
- утренняя сводка приходит ежедневно;
- за две недели работы ни одна проверка не потеряна — контрольная
  точка конца фазы 2.

**Смотри также:** `07-ROADMAP.md` §Контрольные точки,
`02-ARCHITECTURE.md` §Правила алертов.
