# E1. Ядро данных

**Цель эпика.** Перенести источник правды из Excel в Postgres так, чтобы
ни одна строка не потерялась и появилась история, которой сейчас нет.

**Зависит от:** E0 · **Блокирует:** почти всё остальное

---

## E1-01 · Схема: площадки и метрики
**Размер:** L · **Зависимости:** E0-01 · **Фаза:** 0

**Зачем.** Основа всего. Пока площадки живут в таблице, любой модуль
вынужден быть костылём поверх файла.

**Что делаем.** Django-модели `products`, `sites`, `product_sites`,
`site_metrics`, `site_prices`, `gray_scans`, `site_audits` по
`schema.sql` 1.2 (несколько продуктов, ADR-030) и админка для них.

**Детали реализации.**
- Домен хранить нормализованным: нижний регистр, без схемы, без `www.`,
  без хвостового слэша. Нормализация — в одном месте (метод модели или
  утилита), а не в каждом импортёре.
- Перечисления — типы Postgres (ADR-029): `CREATE TYPE` в миграции,
  своё поле модели, значения — `TextChoices`.
- Как модели повторяют `schema.sql` — ADR-029: `db_table`,
  `db_default`, индексы и ограничения с именами из схемы, автоиндексы
  внешних ключей выключены, `on_delete=PROTECT`.
- Строки `product_sites` создаёт одна функция: новая площадка — строки
  под все продукты, новый продукт — под все площадки, статус `new`.
  Повторный вызов ничего не дублирует.
- Продукты заводит человек в админке.
- Снапшоты в админке (ADR-008, уточнение): новый замер — «Сохранить
  как новый объект», править можно только последний снапшот, старые —
  только чтение.
- `site_metrics.raw` (JSONB) заполнять всегда, даже если сейчас
  используются четыре поля из двадцати. Через полгода понадобится
  пятое — оно уже будет в истории.
- Мягкое удаление: `is_deleted`, менеджер по умолчанию фильтрует.

**Критерии приёмки.**
- миграции применяются на чистой базе;
- `sqlmigrate` просмотрен глазами перед применением;
- индексы и ограничения из `schema.sql` присутствуют, лишних нет —
  тест сравнивает их со списком из схемы (ADR-029), плюс `\d+` в psql;
- модели видны в админке, объекты создаются и редактируются;
- новая площадка получает строки `product_sites` под все продукты,
  новый продукт — под все площадки; повторный вызов не создаёт дублей;
- нормализация домена покрыта тестами: `HTTPS://WWW.Example.com/` и
  `example.com` дают одно значение.

**Подводные камни.**
- Соблазн положить цены прямо в `sites`. Не класть: цены меняются, а
  история нужна (ADR-008).
- Соблазн сделать `dr`, `traffic` полями `sites` для удобства запросов.
  Тот же ответ: это снапшоты. Для удобства есть `v_site_latest` (E1-05).
- «Пишем ли мы статью» тоже не хранить колонкой — это производное от
  последних цен и порога продукта, живёт в `v_product_site_latest`.
- Статус площадки — не в `sites`: решение своё у каждого продукта,
  оно в `product_sites`.

**Смотри также:** `03-DATA-MODEL.md` §Блок 1, `schema.sql`, ADR-008,
ADR-029, ADR-030.

## E1-02 · Схема: размещения, ссылки, ключи
**Размер:** M · **Зависимости:** E1-01 · **Фаза:** 1

**Зачем.** Без этого нельзя ни импортировать историю, ни считать
покрытие ключей.

**Что делаем.** Модели `placements`, `placement_links`, `keywords`,
`keyword_positions`.

**Детали реализации.**
- `placements` всегда привязано к продукту. Размещение Clideo —
  такая же строка, как размещение Convertio (ADR-007).
- `article_url` хранится как есть и может быть на поддомене площадки:
  площадка `example.com`, статья — `blog.example.com/...` (реальный
  случай). Совпадения хоста статьи с `sites.domain` не требовать —
  ни здесь, ни в краулере и проверках (E2-03…E2-05).
- `placement_links.char_offset` — позиция в символах **с пробелами** от
  начала тела статьи, без учёта HTML-тегов. Определение зафиксировать
  в докстринге: от этого зависит правило `LINK_POSITION_FIRST`, и любое
  расхождение в трактовке даст расхождение в проверках. **Уточнение
  (27.09.2026):** считается как «Статистика» Word, заголовок входит,
  хранятся оба числа — с пробелами и без (ADR-032, `schema.sql` 1.3).
- `keyword_id` у ссылки может быть `NULL` — это нормально для
  безанкорных и брендовых ссылок.
- `keywords.tool` — текст, а не перечисление: разделы сайта у каждого
  продукта свои, допустимые значения — локальная настройка
  `TOOL_CATEGORIES` (ADR-030, `13-CONFIG.md` §2.3).
- `lost_at` заполняется один раз, при первом обнаружении пропажи;
  повторные проверки его не перезаписывают.

**Критерии приёмки.**
- можно создать размещение с двумя ссылками и привязать их к ключам;
- уникальность `(keyword_id, country, checked_at)` в позициях работает —
  повторная запись за ту же дату не создаёт дубль;
- размещения не удаляются: отмена — статусом `cancelled`; удаление
  доменных объектов в админке отключено (принцип «ничего не удаляем
  физически», `02-ARCHITECTURE.md`).

**Смотри также:** `03-DATA-MODEL.md` §Блок 2–3, ADR-007.

## E1-03 · Схема: наблюдаемость
**Размер:** S · **Зависимости:** E1-01 · **Фаза:** 0

**Зачем.** Без `llm_calls` не построить E8: не на чем будет считать,
какой вариант промпта работает лучше и сколько стоит одна статья.

**Что делаем.** Модели `checks`, `llm_calls`, `task_runs`, `api_usage`,
представление `v_overdue_checks`. Вместе с ними — `prompt_templates` и
`prompt_variants` в `apps/content`: на них ссылается `llm_calls`
(ADR-031).

**Детали реализации.**
- Делается **в первой волне миграций**, а не когда дойдёт очередь.
  Ретроактивно протягивать `run_id` через готовые цепочки больно.
- `checks` полиморфна: `entity_type` + `entity_id` без внешнего ключа.
  Это сознательный компромисс ради единого журнала и единого запроса
  «что проверять сегодня».
- Индекс `(check_type, next_check_at)` обязателен — на нём стоит вся
  система напоминаний.
- В `llm_calls` хранится `prompt_variant_id`, а не текст промпта.
  Ответ храним целиком.

**Критерии приёмки.**
- таблицы созданы, `run_id` присутствует во всех четырёх;
- тестовая запись в `checks` с `next_check_at` в прошлом попадает в
  представление `v_overdue_checks`.

**Подводные камни.** Хранение полного текста промпта в каждой записи
`llm_calls` раздувает базу за месяцы до неприличия. Только ссылка.

**Смотри также:** `03-DATA-MODEL.md` §Блок 6, ADR-011.

## E1-04 · Импорт из Excel/CSV
**Размер:** M · **Зависимости:** E1-02 · **Фаза:** 1

**Зачем.** Первая боевая задача. После неё все площадки видны в браузере
с фильтрами, и Excel перестаёт быть рабочим инструментом.

**Что делаем.** Management-команда разбора выгрузок по правилам из
`12-IMPORT-MAPPING.md`: рабочая база с решениями (568 строк, 17.09),
пул кандидатов (1978 строк, 23.09) и «Распределение анкоров».

**Главный риск задачи.** Рабочая база и пул — разные наборы данных, они не
пересекаются. Импорт только текущей вкладки молча потеряет все решения и
размещения. Сначала закрыть Q11.

**Детали реализации.**
Полный маппинг колонок вынесен в отдельный документ — здесь только то,
что определяет архитектуру команды:

- **Идемпотентность.** Ключ сопоставления — `sites.domain`, для
  `product_sites` — `(site, product)`, для позиций `(keyword, дата)`.
  Повторный запуск обновляет, а не дублирует.
- **Решения — под Convertio** (ADR-030, маппинг §0): статусы и отказы
  из таблицы ложатся в `product_sites` этого продукта. Продукты
  Convertio и Clideo заведены в админке до импорта; нет — импорт
  останавливается, ничего не записав.
- **Сухой прогон** (`--dry-run`) показывает, что произойдёт, без записи.
- **Транзакция** на весь импорт: либо всё, либо ничего.
- **Отчёт** обязателен: создано / обновлено / пропущено, список строк с
  проблемами разбора, расхождения расчётных `links_placed` с файлом.
- Ни одна строка не теряется молча.

**Критерии приёмки.**
- рабочая база: все 568 строк в базе; 10 размещённых и 28 отправленных
  заявок стали `placements` с правильными статусами;
- пул: 1978 строк → 1494 площадки; 466 идентичных дублей слиты, 18
  конфликтных — в отчёте;
- площадки рабочей базы пулом не перезаписаны — добавился только новый
  снапшот метрик и цен;
- ссылки на Clideo стали размещениями продукта Clideo, строки этих
  площадок для Clideo в `product_sites` — `placed`;
- расчётные `links_placed` / `links_waiting` сверены с колонками файла
  анкоров, расхождения — в отчёте;
- позиция `101` легла как `NULL`, две битые ячейки Volume — в отчёте;
- повторный запуск не создаёт дублей;
- отчёт содержит строки, где `US Traff` равен `Top Geo Traff` при не-US
  гео: 3 в рабочей базе, 15 в пуле (маппинг §1.3);
- категории разобраны без обрывков: в пуле 44 тематики и 4 особые
  (маппинг §1.1);
- 10 площадок с опубликованными размещениями получили статус `placed`,
  28 с заявками — `approved` (строки Convertio в `product_sites`).

**Подводные камни.**
- Числа приходят строками с запятыми: `84,307,672`. Наивный `int()`
  упадёт.
- `Цена анонса` смешанного типа: число или слово «бесплатно».
- `Индексация` в разном регистре: `да`, `Да`, `Нет`.
- Две разные колонки называются похоже: `Тип ссылки` (Guest Post /
  Link Insertion) и `Тип ссылки статья` (dofollow / nofollow). Перепутать
  легко, последствия серьёзные — вторая участвует в стоп-факторе.
- `Особые тематики` — это декларация площадки о принимаемых тематиках,
  а не результат проверки индекса. Не путать с gray scan.

**Смотри также:** `12-IMPORT-MAPPING.md` целиком, `10-BASELINE-STATS.md`.

## E1-05 · Расчётные поля и представления
**Размер:** M · **Зависимости:** E1-04 · **Фаза:** 1

**Зачем.** Устраняет главный источник расхождений в текущей таблице:
`links_placed` больше не проставляется руками.

**Что делаем.** SQL-представления из `03-DATA-MODEL.md`:
`v_keyword_coverage`, `v_site_funnel`, `v_monthly_spend`,
`v_article_funnel`, `v_overdue_checks`, `v_link_health`, `v_site_latest`,
`v_product_site_latest`. Всё готово в `schema.sql`, задача — перенести
в миграции и проверить.

Ещё модель `domain_settings` (перенесена из E5-01: из неё
`v_product_site_latest` читает порог написания) и настройки в админке:
- на странице продукта — блок «Настройки продукта»: ценовой ориентир,
  порог написания, цена анонса (`PRICE_REFERENCE`), тематики продукта
  (`PROJECT_TOPICS`), разделы сайта (`TOOL_CATEGORIES`), белый список
  доменов (`AUTHORITY_DOMAINS`). Заводя продукт, человек сразу видит,
  что нужно заполнить; править — там же. Значения Convertio —
  `13-CONFIG.md` §2;
- общие настройки — отдельным разделом «Настройки».

**Детали реализации.**
- Представления создаются миграцией с сырым SQL, а не собираются в ORM
  (ADR-003).
- `links_waiting` считается по статусам `planned`, `ordered`, `writing`,
  `review`; `links_placed` — только `published`.
- Цены считают `v_site_latest` (`reference_total`) и
  `v_product_site_latest` (`we_write`, `expected_spend` по порогу
  продукта), формулы и обоснование — в `03-DATA-MODEL.md` §site_prices.
  Главное: с ценовым ориентиром продукта (у Convertio 550 EUR)
  сравнивается только размещение + анонс; написание не входит никогда.
  Фактическая цена — `price_paid_cents`.

**Критерии приёмки.**
- цифры по 10 выбранным вручную ключам сходятся с расчётом глазами;
- настройки продукта вводятся и правятся на странице продукта; после
  ввода порога написания у площадок продукта считается
  `expected_spend`, без него — пусто;
- `v_overdue_checks` возвращает пусто на свежей базе и заполняется при
  наступлении `next_check_at`.

**Смотри также:** `03-DATA-MODEL.md` §Отчётные представления, ADR-003, ADR-009.

## E1-06 · Экспорт в Excel/CSV
**Размер:** S · **Зависимости:** E1-05 · **Фаза:** 1

**Зачем.** Excel остаётся форматом обмена: отчёт партнёру, выгрузка для
разбора вне системы.

**Что делаем.** Выгрузка по кнопке: полная база, срез по статусу, отчёт
за месяц.

**Детали реализации.**
- Названия колонок в выгрузке — привычные русские, а не имена полей
  базы. Файл читает человек, а не программа.
- CSV в UTF-8 с BOM, иначе Excel показывает кракозябры.
- Экспорт — это выгрузка, а не синхронизация. Обратного импорта
  отредактированного файла не делаем: это вернёт все проблемы, ради
  которых уходили от Excel.

**Критерии приёмки.**
- файл открывается в Excel без искажений кириллицы;
- выгрузка 1500 площадок занимает меньше 5 секунд.

**Смотри также:** ADR-001.
