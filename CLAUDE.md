# SEO-система линкбилдинга convertio.co

Внутренний инструмент на двоих: аудит донорских площадок из каталога
Collaborator.pro, учёт размещений, проверки индексации и живости ссылок,
подбор анкоров, генерация статей. Разработчик один: опыт в PHP-легаси,
Python на уровне джуна. Когда в коде встречается неочевидная для
PHP-разработчика вещь (дескрипторы, контекстные менеджеры, ленивые
QuerySet, async), объясняй её коротко, одной-двумя фразами.

Общаемся по-русски. Код и идентификаторы — на английском, документация —
на русском.

## Где что лежит

Читай по необходимости, не всё подряд.

- `PROGRESS.md` — где мы сейчас: сделанное, текущая задача, следующие.
  Читать в начале каждой задачи.
- `docs/06-BACKLOG.md` — индекс задач, Definition of Done, задачи E0.
  `docs/backlog/E<N>-*.md` — задачи остальных эпиков.
- `docs/specs/<ID>.md` — ТЗ задачи, если есть. Оно главнее описания
  в бэклоге.
- `docs/03-DATA-MODEL.md` и `schema.sql` — модель данных. `schema.sql` —
  эталон: миграции Django должны давать ту же схему.
- `docs/04-DOMAIN-RULES.md` — правила аудита, стопы, анкоры, проверки статьи.
- `docs/08-DECISIONS.md` — ADR. Не предлагать то, что там отклонено.
- `docs/09-OPEN-QUESTIONS.md` — открытые вопросы; часть блокирует задачи.
- `docs/13-CONFIG.md` — переменные окружения и настройки.
- `docs/15-USER-DOCS.md` — правила пользовательской документации
  (`user-docs/`, MkDocs).
- `source/` — исходные материалы заказчика. Только чтение.

Код (ADR-024):

- `apps/<домен>/` — Django-приложения: `sites` (площадки, метрики, цены,
  аудиты — блок 1 модели данных), `placements` (размещения и ссылки —
  блок 2), `keywords` (ключи и позиции — блок 3), `content` (статьи, пул,
  правила, промпты — блоки 4–5), `observability` (проверки, вызовы LLM,
  запуски задач — блок 6), `integrations` (клиенты внешних API).
- `config/settings/` — `base.py` общее, `local.py` и `prod.py` по
  `DJANGO_ENV`; `config/env.py` — чтение переменных окружения.
- `tests/` — тесты.

## Команды

Всё идёт в контейнере `app` (ADR-023). Нужен `.env` — копия
`.env.example` с заполненными значениями.

- Поднять окружение: `make up` (приложение — http://localhost:8000/admin/),
  остановить: `make down`, логи: `make logs`
- Тесты: `make test`
- Линтер и типы: `make check` (ruff lint + ruff format --check + mypy strict)
- Автоисправление стиля: `make fmt`
- Миграции: `make migrate`, пользователь админки: `make superuser`
- Django-команды: `docker compose run --rm app python manage.py <команда>`
- Зависимости: `uv add <пакет>` / `uv add --dev <пакет>`, затем `make up`
  (пересборка образа)
- Документация: `python tools/check_user_docs.py`, `mkdocs build --strict`

## Правила кода

Нарушать нельзя, обоснования — в `docs/02-ARCHITECTURE.md` и ADR.

- Python 3.12, Django 5. mypy в строгом режиме, ruff. Аннотации типов везде.
- Django-приложения делятся по доменам: `sites`, `placements`, `keywords`,
  `content`, `observability`, `integrations`. Не по слоям.
- ORM — для жизненного цикла объектов, сырой SQL — для отчётов (ADR-003).
- Снапшоты вместо перезаписи: метрика, цена, позиция — новая строка с датой.
- Ничего не удаляем физически: статус или флаг. В админке удаление отключено.
- Деньги — целые центы плюс код валюты. Никакого float.
- Производные признаки (последние метрики, «пишем мы», итог цены) берутся
  только из `v_site_latest`, отдельными колонками не дублируются.
- Числа порогов — из `domain_settings`, проверки статьи — из `rules`.
  В коде чисел не хардкодить.
- Схема БД меняется только миграциями. Перед применением — `sqlmigrate`.
- Фоновые задачи идемпотентны, `run_id` протягивается через всю цепочку.
- Модули общаются только через базу и очередь, без прямых вызовов друг
  друга. Ограничение скорости внешних API — на уровне очереди, не в коде
  задачи. LLM вызывается только через абстракцию из E4-01.
- Стоп-факторы проверяет код, гибкую зону оценивает LLM. Не смешивать.
- Секреты только из переменных окружения. `.env` не читать и не выводить.

## Как работаем

- Одна сессия — одна задача. Начало: `/start-task <ID>`, конец: `/close-task`.
  Между задачами — `/clear`.
- Сначала план, потом код. Код не писать, пока план не подтверждён.
- Не выходить за рамки задачи. Найденное по дороге — в «Технический долг»
  в `PROGRESS.md` или вопросом мне.
- Документы противоречат друг другу или решения не хватает — остановиться
  и спросить, не придумывать. Принятое решение — записью в `08-DECISIONS.md`.
- Каждая новая логика — с тестами. Критерии приёмки проверяются явно,
  по списку из описания задачи.
- Коммитить только после моего «ок». `git push` делаю сам.
