# SEO-система линкбилдинга convertio.co

Внутренний инструмент для аудита донорских площадок из каталога
Collaborator.pro, учёта размещений, проверок индексации и живости ссылок,
подбора анкоров и генерации статей.

Стек: Python 3.12, Django 5.2, PostgreSQL 16, Redis 7, Docker Compose.
Интерфейс первой версии — Django Admin.

---

## Запуск

### Что нужно

- **Docker** с Compose v2 (`docker compose version`). На Windows — Docker
  Desktop с интеграцией WSL, проект лежит и запускается внутри WSL.
- **make** и **git**.
- **python3** на хосте — только чтобы сгенерировать секретный ключ.

Python, Django и остальные пакеты ставить на хост не нужно: приложение,
тесты и проверки работают в контейнере (ADR-023).

### Первый запуск

1. Склонировать репозиторий и перейти в папку проекта.

2. Создать `.env` из шаблона:

   ```bash
   cp .env.example .env
   ```

3. Заполнить в `.env` два значения, без которых приложение не стартует:

   - `DJANGO_SECRET_KEY` — сгенерировать:

     ```bash
     python3 -c "import secrets; print(secrets.token_urlsafe(50))"
     ```

   - `POSTGRES_PASSWORD` — любой пароль, локальная база создастся с ним.

   Остальные пустые значения — ключи внешних API. Для запуска они не
   нужны, их заполняют к задачам, которые с этими API работают.
   Пояснения ко всем переменным — `docs/13-CONFIG.md` §1.

4. Поднять окружение. Первый раз соберётся образ, это несколько минут:

   ```bash
   make up
   ```

5. Применить миграции и создать пользователя для админки:

   ```bash
   make migrate
   make superuser
   ```

6. Открыть http://localhost:8000/admin/ и войти.

Остановить — `make down`. Данные базы при этом сохраняются в томе
Docker `pgdata`.

### Команды

| Команда | Что делает |
|---|---|
| `make up` | поднять окружение, пересобрать образ, если менялись зависимости |
| `make down` | остановить окружение |
| `make logs` | логи всех сервисов |
| `make migrate` | применить миграции |
| `make superuser` | создать пользователя для админки |
| `make test` | тесты |
| `make check` | ruff, проверка форматирования, mypy strict |
| `make fmt` | автоисправление стиля |
| `make shell` | Django shell |

Любая команда Django:
`docker compose run --rm app python manage.py <команда>`.

Новая зависимость: `uv add <пакет>` (или `uv add --dev <пакет>`), затем
`make up` для пересборки образа.

### Окружения

`DJANGO_ENV` в `.env` выбирает модуль настроек: `local` —
`config/settings/local.py`, `prod` — `config/settings/prod.py`. Общее —
в `config/settings/base.py`. Значения по умолчанию нет: без
`DJANGO_ENV` приложение не стартует. Всё, что различается между машинами,
берётся из переменных окружения.

### Логи и ошибки

Три слоя, не смешиваются (ADR-011):

- **технические логи** — stdout. Локально читаемая строка, в проде JSON:
  ```
  14:02:11 INFO    apps.sites.audit [7f3a1c2e] аудит запущен site=example.com
  ```
  В квадратных скобках начало `run_id` — идентификатора запуска цепочки.
  Все строки одного запуска собираются `grep 7f3a1c2e`, в проде —
  `jq 'select(.run_id=="…")'`;
- **доменный аудит** — таблицы `task_runs`, `llm_calls`, `api_usage` и
  другие, с той же колонкой `run_id`;
- **ошибки** — Sentry-совместимый сервис: до прода GlitchTip, в проде
  sentry.io (ADR-026). Включается переменной `SENTRY_DSN` — DSN проекта
  в любом из двух, пустая — выключен. Тесты туда не пишут никогда.

Секреты (переменные с именами на `_KEY`, `_PASSWORD`, `_TOKEN`, `_DSN`,
`_LOGIN` и ключи вроде `api_key`, `password` в словарях) в логах и
событиях Sentry заменяются на `***`.

В коде: логгер — `logging.getLogger(__name__)`, данные — через
`extra={...}`, а не в тексте сообщения. Точка входа цепочки создаёт
`run_id` через `config.run_id.new_run_id()` и оборачивает работу в
`with bind_run_id(run_id):`. Всё, что пишется внутри, помечается им.

Проверить всё разом: `docker compose run --rm app python manage.py
observability_check --raise` — тестовая цепочка, дамп конфига с
замаскированными секретами, тестовая ошибка в Sentry.

### Если что-то не так

| Симптом | Причина |
|---|---|
| `env file … .env not found` | не выполнен шаг 2 |
| `задайте POSTGRES_… в .env` при любой команде `docker compose` | в `.env` пустое значение переменной базы |
| `Переменная окружения DJANGO_SECRET_KEY не задана` | пустой `DJANGO_SECRET_KEY` в `.env` |
| `DJANGO_ENV: ожидается local \| prod` | в `.env` нет `DJANGO_ENV` или там опечатка |
| `port is already allocated` на 8000 или 5432 | порт занят другим процессом или другой копией проекта |

## Две документации — не путать

| | Проектная | Пользовательская |
|---|---|---|
| Папка | `docs/` | `user-docs/` |
| Про что | как строить систему | как работать с системой |
| Читатель | разработчик и агент | пользователь в разделе «Документация» интерфейса |
| Когда меняется | при решениях и планировании | с каждой задачей, меняющей то, что видит пользователь |
| Правила | `docs/14-WORKFLOW.md` | `docs/15-USER-DOCS.md` |

Посмотреть пользовательскую документацию локально:

```bash
pip install -r requirements-docs.txt
mkdocs serve          # http://127.0.0.1:8000
python tools/check_user_docs.py
```

`mkdocs serve` занимает тот же порт 8000, что и приложение: либо
остановить приложение, либо запустить `mkdocs serve -a 127.0.0.1:8001`.

## Порядок чтения

**Самое первое:** `docs/14-WORKFLOW.md` — как устроена работа между
сессиями. Сразу за ним — `docs/16-AGENT-SETUP.md`: рабочее место, Claude
Code и PyCharm.

**Первый раз:** `00-VISION` → `02-ARCHITECTURE` → `07-ROADMAP` →
`06-BACKLOG`. Этого хватает, чтобы понять, что строим и в каком порядке.

**Каждый раз:** `PROGRESS.md` — где мы сейчас, что дальше и что требует
действий вне кода.

**Перед кодом:** `03-DATA-MODEL` + `schema.sql` + `13-CONFIG`.

**При работе над задачей:** её описание в `06-BACKLOG.md` (E0) или в
`docs/backlog/`, ТЗ в `docs/specs/`, если есть. В описании — ссылки на
всё остальное, что понадобится.

**При споре «почему так»:** `08-DECISIONS`.

## Дисциплина ведения

- Документы живут в git вместе с кодом.
- После каждого значимого решения — запись в `docs/08-DECISIONS.md`.
- Закрытые вопросы из `docs/09-OPEN-QUESTIONS.md` переезжают в ADR, а не
  просто вычёркиваются.
- Замеры в `docs/10-BASELINE-STATS.md` не редактируются, а дополняются
  новыми на новую дату.
- Каждая задача закрывается по `docs/templates/task-close.md`: код,
  пользовательская документация, `PROGRESS.md`.
