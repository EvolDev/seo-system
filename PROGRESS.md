## Где мы сейчас

Локальное окружение готово (E0-01): Django 5.2 в Docker Compose с
Postgres 16 и Redis 7, тесты и проверки — `make test`, `make check`.
Структура на месте (E0-02): шесть доменных приложений в `apps/` (пока
без моделей), настройки local/prod по `DJANGO_ENV`, README проекта.
Логи и ошибки (E0-03): логи в stdout с `run_id` и маскировкой секретов,
ошибки — в GlitchTip (до прода, ADR-026), механизм `run_id` для цепочек.
Пользовательская документация (E0-04): `make docs-check` и
`make docs-serve` в контейнере, pre-commit не пропускает коммит с битой
документацией (ADR-028). Эпик E0 закрыт.
Схема блока 1 (E1-01): продукты, площадки, статус площадки по каждому
продукту (`product_sites`, ADR-030), метрики, цены, серость, аудиты —
модели, миграция, админка со снапшотами. Миграции сверяются со
`schema.sql` тестом (ADR-029).
Схема наблюдаемости (E1-03): журнал проверок `checks` с представлением
просрочек `v_overdue_checks`, вызовы LLM, запуски задач, расход API —
везде `run_id`, по умолчанию из текущей цепочки; таблицы промптов, на
которые ссылается `llm_calls` (ADR-031).
Схема размещений и ключей (E1-02): размещения со ссылками, ключи
продукта и снапшоты позиций — модели, миграции, админка без удаления.
Позиция ссылки в статье считается как «Статистика» Word, два числа — с
пробелами и без (ADR-032, `schema.sql` 1.3).
Импорт таблицы (E1-04): команда `import_workbook` загружает таблицу
ручной работы — площадки, замеры, решения, размещения Convertio и
статьи Clideo, ключи с позициями; сухой прогон, отчёт, одна транзакция,
повторный запуск без дублей. Таблицу ведём до подключения API, импорт
регулярный, главнее админка (ADR-033). Каждая загрузка — рабочий список
площадок (`schema.sql` 1.4). Пометка «реклама» из карточки — не
стоп-фактор (ADR-034). Файл от 27.09 загружен в локальную базу списком
«Сентябрь 2026».
Расчёты и настройки (E1-05): семь отчётных представлений — покрытие
ключей (`links_placed` и `links_waiting` больше не руками), площадка «на
сегодня» с плановыми расходами по порогу продукта, воронка, живость
ссылок, расходы по месяцам; `v_article_funnel` — вместе с таблицами
статей. Настройки `domain_settings`: основные — на странице продукта,
любую общую продукт переопределяет своим значением (ADR-035), общие —
раздел «Настройки». Продукт, с которым не работали, удаляется
(ADR-036).
Админка как база (E9-01): тема django-unfold для всей админки
(ADR-037), экран «Площадки продукта» поверх `v_product_site_latest` —
продукт и самый новый рабочий список по умолчанию, фильтры «уже
работали / новые для нас», статус, DR и трафик диапазоном, язык,
«пишем мы», размещения; поиск по вставленному адресу; 8 запросов на
страницу.
Админка причёсана (E9-08): тема Admin Interface вместо unfold (ADR-038),
четыре расцветки и переключатель **Оформление** в шапке («Apple —
светлая», «Google — тёмная», «Изумрудная», «Ahrefs — тёмная»), переходы
между страницами без моргания (View Transitions), меню по работе —
«Работа / Справочники / Настройки / Служебное», главная с карточками
рабочих экранов, человеческие названия и заголовки. Рабочий экран теперь
называется «Площадки». Тема выбрана на стенде из шести; цвета графиков
для будущего дашборда проверены (ADR-038).
Очередь (E2-01): Celery и Redis — воркер и beat в compose, очередь
Redis переживает перезапуск. Базовый класс задачи `QueueTask`
(`config/queue.py`): `run_id` через очередь, одна строка `task_runs` на
задачу, три попытки — повторы через 1 и 2 минуты, после третьей —
«Ошибка» и событие в GlitchTip; ограничение скорости по ключу в Redis;
задачи не теряются при остановке воркера. Пульс очереди раз в час,
`manage.py queue_check`, экран «Запуски задач» в «Служебном» (ADR-039).
Выдача Google (E2-02): клиент Serper — `search()` из
`apps/integrations/serp`, одинаковый запрос сутки из кеша, каждый
платный запрос сразу в `api_usage`, стоимость — центы с долями
(`numeric`, `schema.sql` 1.5). Дневной лимит ставит задачи на паузу до
полуночи — `Postpone` в `QueueTask`, колонка «пауза» в «Запусках задач».
Экран «Расход API» в «Служебном», `manage.py serp_search`. DataForSEO
отклонён (ADR-040). Оценки «примерно N» у Serper нет — Q20 до E2-06.
Проверка индексации (E2-03): кнопка ↻ в колонке «в индексе», действие
для отмеченных строк и кнопка в карточке — без перезагрузки, ход и итог
всплывающим окном. Статья ищется по `site:`, не нашлась — по самому
адресу; метки вроде `?srsltid` не мешают. По расписанию в 06:00 — кому
подошёл срок (настройка `INDEXATION_SCHEDULE`, пока выключена), 30 дней
не в индексе — одна сводка в день в GlitchTip. Флажок «Не проверять»
(`schema.sql` 1.6). История проверок в карточке (ADR-042).

Ближайшая цель: **первый вертикальный срез** (фаза 1) — импортировать
рабочую базу и пул в Postgres, увидеть площадки в админке, нажать кнопку
«проверить индексацию» и получить результат. После этого Excel перестаёт
быть рабочим инструментом.

**Таблица ручной работы** — `Линкбилдинг Convertio.co.xlsx` в корне
проекта (в git не идёт). Загружать — `import_workbook` с датой выгрузки
и именем списка, сначала `--dry-run`; как читать отчёт — инструкция
«Как загрузить таблицу в систему».

### Сессия 16 · 01.10.2026

**Задача:** E2-03 (Opus 5.5, high)
**Сделано:** при планировании согласовано: сроки — настройка
`INDEXATION_SCHEDULE` (с выключателем, заведена выключенной — первый
прогон проверит 651 статью разом, включает пользователь); алерт до E9-04 —
одно событие GlitchTip в день (бесплатный тариф ограничен числом
событий); флажок «Не проверять» вместо статуса «Отменено». Код:
`apps/placements/indexation.py` — сравнение адресов, отбор «кому пора»
одним запросом (`Subquery`), запись проверки, серия неудач и пометка
`alert`, сводка с отпечатком по дате; `tasks.py` — `indexation_schedule_run`
(06:00), `check_indexation` (плановая, которой уже не пора, ничего не
делает), `indexation_alerts` (06:30, с прошлого удачного запуска);
`Throttle("serp", 5/с)`. Срок — от полуночи: сутки до секунды сдвигали
бы ежедневную проверку на день. `search(fresh=True)` — мимо кеша.
`IndexationSchedule.parse` и `SETTING_PARSERS` — форма значения
проверяется в обеих формах настроек и в `set_product_setting`. По
ходу живой проверки, по просьбе пользователя: кнопка ↻ в списке,
массовое действие и кнопка в карточке без перезагрузки — пачка одним
POST, состояние одним GET по `task_runs`; окна хода и итога (зелёное /
жёлтое / красное); «в индексе» и время в карточке — только чтение.
После скриншотов пользователя: метки отслеживания в адресах из выдачи
(`?srsltid` у Shopify) не мешают совпадению; второй запрос по самому
адресу, если `site:` не нашёл (debutify.com: `site:` у Serper за 40 минут
сменил ответ, у пользователя — пусто, поиск по адресу находил);
в истории — «в выдаче: …» и «найдена поиском по адресу». 668 тестов.
**Критерии приёмки:**
- статус обновляется автоматически — тест «расписание → проверка →
  `is_indexed`»; вживую временный beat раз в 10 с четыре раза поставил
  обе задачи, воркер выполнил (расписание выключено — 0 проверок, без
  трат). Настоящий запуск в 06:00 не дожидались;
- запись в `checks` с `next_check_at` — тест; вживую у всех проверок
  (около 80 строк от кнопок пользователя);
- успех — месячный цикл — тест: `next_check_at` +30 дней от полуночи,
  на следующий день не берётся;
- 30 дней без индекса — алерт: тест — одна пометка на серию, новая серия
  после успеха — снова; вживую с `alert_after_days: 0` проверка
  whattimewasit.io (не найдена обоими запросами) → сводка → одно событие
  GlitchTip SEO-SYSTEM-I со списком, `run_id`, `placement_ids`
  (скриншоты `screens/img_8–10.png`). Telegram — E9-04, до неё письмо
  GlitchTip (согласовано).
**Документация:** новая инструкция «Как проверить индексацию статьи»
(экраны `placement_list` — новый в `15-USER-DOCS.md` §3.4,
`placement_card`, `settings`), «Пороги и ориентиры» — раздел «Проверки»,
«Фоновые задачи» — три задачи, оглавление инструкций, журнал изменений.
Проектная: ADR-042, `04-DOMAIN-RULES.md` §4, `13-CONFIG.md` §2.4 и §3,
`03-DATA-MODEL.md` (`skip_checks`, `checks.result` индексации),
`02-ARCHITECTURE.md` (правило алерта, SERP), бэклог — E2-03, E2-05
(«Не проверять»), E9-04 (пометки `alert`), README и `CLAUDE.md` —
`make restart-queue`.
**Решения:** ADR-042 — два запроса, сравнение адресов, `fresh`, сроки в
настройке от полуночи, «Не проверять», сводка оповещений раз в день,
кнопки без перезагрузки.
**Проблемы:** первое нажатие кнопки пользователем «ничего не сделало» —
воркер ходил в Serper со старым ключом ScraperAPI (403): `docker compose
restart` не перечитывает `.env`, контейнер был создан 30.09 до исправления
ключа. Найдено сравнением хешей ключа без вывода; `make restart-queue`
теперь пересоздаёт контейнеры. Временный beat сначала шёл по настоящему
расписанию — `app.conf.beat_schedule` не действует, нужен
`CELERY_BEAT_SCHEDULE` (та же ловушка, что в E2-01). Нарезкой файла
случайно удалена `_history_row`, `ruff --fix` следом убрал «лишние»
импорты — восстановлено, тесты поймали. Playwright нет (ставить пришлось
бы вне проекта) — интерфейс проверял пользователь, скрипт — `node
--check` и тестами адресов.
**Следующий шаг:** E1-07.

**Задача:** E2-02 (Opus 5.5, high)
**Сделано:** провайдер выбран по ходу планирования: DataForSEO отклонён
заказчиком (ещё и `site:` у него стоит ×5), взят Serper — ~$0,001 за

колонки под представлением; `sqlmigrate` просмотрен). Клиент
`apps/integrations/serp/`: `search(query, *, depth, country) -> SerpPage`
(результаты и `total_estimate`), провайдеры — словарь `PROVIDERS`,
`SerperProvider` на `httpx` (кредиты из ответа × `SERPER_CENTS_PER_1000`;
нет `credits` — ошибка). Кеш — Django cache на Redis, база очереди + 1;
в тестах — память процесса, пустая в каждом тесте. Дневной лимит
`SERP_DAILY_BUDGET_CENTS` — `SerpBudgetExceeded` до полуночи, одно
событие Sentry за сутки. `QueueTask`: `Postpone(until, reason)` —
пауза без траты попытки, строка «Выполняется» с `payload.waiting`, за раз
не дольше 30 минут (visibility timeout). `env_int`. Экран «Расход API»
(суммы в долларах, над списком — выдача за сегодня против лимита),
колонка «пауза» в «Запусках задач», команда `serp_search`,
`queue_check --pause`. 571 тест.
**Критерии приёмки:**
- `site:domain` — структурированный результат: тесты на ответе формы
  Serper; вживую `serp_search "site:convertio.co"` — 10 результатов;
- стоимость в `api_usage` — тест; вживую строка `serper · search · 1 ·
  0.1000 ¢ · USD` с run_id запроса;
- повтор в тот же день бесплатен — тест; вживую повтор с лишними

## Технический долг и известные проблемы

- Ошибки до прода идут в GlitchTip, не в sentry.io (ADR-026): с машины
  разработчика sentry.io недоступен. При E10-02 переключить прод на
  Sentry и проверить `manage.py observability_check --raise` — Q15.
- Заметность ссылки (`LINK_NOT_VISIBLE`) в v1 проверяет человек.
  Автоматизация требует headless-браузера — отдельная задача, когда
  дойдут руки.
- Копирование из Claude Code в терминале PyCharm: в `/etc/wsl.conf`
  выключен interop, поэтому встроенное копирование не доходит до буфера
  Windows. Обход — выделять с `Shift` или `/tui default`. Дописать в
  `16-AGENT-SETUP.md` §9.
- PyCharm не видит интерпретаторы в WSL: при добавлении интерпретатора
  «No interpreters were found» (даже системного `/usr/bin/python3`),
  кнопки выбора файла не работают. Возможно, связано с выключенным
  interop в `/etc/wsl.conf` — не проверено. Нужен только для подсказок
  IDE: проверки идут в контейнере. Путь к окружению —
  `/mnt/r/web/www/seo-system/.venv/bin/python`.
- Движок документации — MkDocs 1.6 с ограничением `<2`. Переход на
  Zensical, когда он выйдет в 1.0 (`15-USER-DOCS.md` §6.1).
- Общие значения `domain_settings` заполняет E5-02 (фаза 4a), а читают
  их раньше: `GRAY_TERMS` — E2-06 (фаза 2), зоны — E4 (фаза 3). Таблица
  и раздел «Настройки» есть с E1-05, значения до E5-02 придётся вводить
  руками в админке или перенести заполнение общих значений раньше.
  Решить до E2-06.
- Таблицы промптов есть с E1-03 (ADR-031), но админки для них и выбора
  варианта («локальный шаблон перекрывает общий») нет ни в одной
  задаче. Нужны к E4-01: без них промпт аудитора некуда ввести.
- `keywords.tool` не сверяется со списком `TOOL_CATEGORIES` продукта:
  настройка есть с E1-05, а проверки нет ни в одной задаче.
  Опечатка в разделе («Vidoe») пройдёт молча, и ключ выпадет из
  фильтров по разделу. Добавить проверку в форму ключа после E1-05.
- Контрольные числа предфильтра (848 из 1494, `10-BASELINE-STATS.md`
  §8.3, ADR-020, E4-05) посчитаны по выгрузке 23.09 и с пометкой
  «реклама» как условием, которое отменено (ADR-034). Пересчитать по
  текущей базе при планировании E4-05.
- «База Starmedia» (679 площадок другого продавца, свой формат, цены в
  $) загрузится как прайс продавца в E1-08 (ADR-041). «Дополнительные
  площадки» (контакты линкбилдеров) импортом не загружаются.
- Таблицы статей (`articles`, `article_versions`, `article_reviews`,
  `validation_results`) не создаёт ни одна задача: E6-01 уже пишет в
  `articles.brief`, E7-01 — в `validation_results`. Вместе с ними —
  `v_article_funnel` (из E1-05 перенесено). Назначить задачу до E6-01.
- У площадки без замера цен `v_site_latest.reference_total_cents` = 0
  (`coalesce`), и `expected_spend_cents` при заданном пороге тоже 0. В
  админке с E9-01 показывается пусто (ADR-037), но в представлении, а
  значит в отчётах и экспорте E1-06, остаётся 0. Поправить
  представление (`schema.sql` 1.5), если такие площадки появятся —
  например, при загрузке из API.
- `site_audits.run_id` заполняется только явно. У таблиц наблюдаемости
  он по умолчанию берётся из текущей цепочки (ADR-031) — сделать так же
  к E4, где аудит пишется из цепочки.
- Моргание при переходах между страницами в Opera (в Edge нет): View
  Transitions включены (ADR-038). Если после проверки настроек браузера
  (приватное окно, принудительная тёмная тема, блокировщик) останется —
  разобраться отдельно.
- Хлебные крошки без уровня приложения Django — только в списках и
  формах. На страницах истории и подтверждения удаления они штатные, со
  средней крошкой-приложением («Площадки»).
- Очередь в прод-compose (E10-01): том для состояния beat (иначе
  пропущенный из-за перезапуска запуск не догоняется), Redis с AOF и
  томом, число процессов воркера и время на его остановку (ADR-039).
- Проверщик документации (`tools/check_user_docs.py`) и хук pre-commit
  берут «сегодня» по часам контейнера — UTC. С 00:00 до 03:00 по Москве
  сегодняшняя дата в `updated` для них «из будущего», и коммит не
  проходит. Поправить: `TZ` контейнеров из `TIME_ZONE` или дата в
  проверщике по `TIME_ZONE`. У страниц E2-01 из-за этого
  `updated: 2026-09-28`.
- `llm_calls.cost_cents` пока `integer`: вызов дешёвой модели стоит доли
  цента и округлится до нуля. Перевести на `numeric(14,4)`, как
  `api_usage`, в E4-01 (ADR-040).
- Строка `api_usage` пишется в транзакции того, кто ищет: если задача
  откатит свою транзакцию после `search()`, деньги потрачены, а строки
  нет. Индексация (E2-03) ищет до транзакции записи; в E2-06 — так же.
- Состояние проверки для кнопок ищется по `task_runs.payload->>'task_id'`
  без индекса (окно — сутки, `task_name` в индексе). При ~700 строк в
  день незаметно; если экран начнёт тормозить — индекс по выражению.
- Сводка оповещений берёт пометки с начала прошлого удачного запуска:
  пометка, записанная в те же миллисекунды, когда шла прошлая сводка,
  попадёт в две сводки подряд. Потерь нет, повтор возможен.
- Статьи без даты публикации (599 из 651) считают «30 дней не в индексе»
  от первой неудачной проверки: давно мёртвая статья даст оповещение не
  сразу, а через 30 дней после включения расписания.
- Два одинаковых запроса одновременно (кеша ещё нет) оба идут к Serper и
  оба платятся. Для индексации несущественно; для массового gray scan
  (E2-06) — замок на ключ кеша (`cache.add`).
